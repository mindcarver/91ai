# dsh 的 Inspector：给运行中的插件树配一个 DevTools

> 全插件化的麻烦在故障时刻才显形：插件树是活的，会热载、会动态挂载、横跨宿主进程和浏览器客户端两个世界，静态配置导出看到的是启动时的树，不是现在这棵。实验性 Inspector 把正在运行的 `dsh` 暴露进 Chrome DevTools：Console 里既能执行宿主代码也能执行浏览器端代码，Sources 里下断点，Network 面板里看宿主打过的每一个请求，Elements 面板里看的就是那棵 Cordis 插件树本身。架构上它守一条铁律：所有 CDP 状态关在一个 Worker 线程里，Worker 永远不碰活的 Cordis 对象，对象先被投影成校验过的快照再运输。代价是明牌的：这套东西等于远程代码执行加全量抓包，所以只绑回环地址，抓包不脱敏，2026 年 9 月下旬的版本起默认不再随产品附带。

## 问题：活的插件树没法用死工具看

从一个具体场景进。你给自己的组合挂了个动态插件，运行中加载、用完卸载，某天行为不对。你怀疑是插件注册的顺序问题：它卸载时注册没撤干净，或者它依赖的服务被另一个插件的卸载顺带撤掉了。此刻你手里的工具全是静态的：配置导出显示的是启动时叠出来的树，日志显示的是插件自己愿意说的话。而你要看的是**现在这一刻**：树上有谁、谁是谁的父节点、哪个 fiber 处于什么状态、浏览器那头的客户端里同一个问题长什么样。

传统调试器也帮不上忙，因为它理解的是 JavaScript 对象，不是"一棵由 fiber 和 context 组成、随时会变形的插件树"。需要的是一个会讲 Cordis 语言的调试器，而且得同时覆盖宿主和浏览器两个执行世界。

Inspector 的答案是不发明新工具，站到 Chrome DevTools 这个最成熟的调试器背后，把 `dsh` 翻译成它听得懂的协议。

## 三十秒模型

三个运行时角色一条数据流。

宿主插件起一个 Worker 线程，Worker 里住着**全部** Chrome DevTools 协议状态；宿主插件和 Worker 之间一条专用消息端口。浏览器侧插件读到宿主注入的启动全局，开一条独立的带令牌 WebSocket 直连 Worker 上报数据。Chrome DevTools 连的是 Worker 的 CDP 端口。

数据流单向且收敛：宿主和浏览器两侧的采集器把各自世界的运行状态**投影成校验过的快照记录**发给 Worker，Worker 验证每一帧、持有状态、把认识的主题翻译成标准 CDP 域。DevTools 永远不直接接触任何一方的活对象。

## 快照投影：为什么 Worker 不许碰活对象

这套设计里最值得搬走的一条规矩：**被观察者和观察协议之间隔着一次投影。**

宿主里的 Cordis 对象是活的：fiber 会挂载卸载，context 的服务会被替换，任何外部线程直接抓着这些对象遍历，都在和数据面竞争。Inspector 的做法是采集器在对象所属的线程里把它们转换成带版本的快照（树形的快照类型，fiber 带唯一标识，context 跟在 fiber 下面），快照经过校验才进传输。Worker 拿到的是一份可以随便缓存、比对、重发的静态数据，两边跑的是同一份浏览器安全的采集器代码。

插件树进的是 Elements 面板。固定两个容器：宿主的根 context 一棵，每个连接的浏览器客户端一棵。fiber 节点带唯一标识，context 是它的子节点，挂载卸载在树上就是节点的增删。Worker 按稳定的后端节点身份做比对，快照没变化不发任何事件，变了才按节点级事件通知，已展开的层级和节点号保持稳定。你在 Elements 里展开的那棵树，就是此刻真实挂载的插件树，树的变化是增量推送的。

配套还有一个不依赖 CDP 的查询接口，读 Worker 里最新的语义快照，不需要开任何调试会话。编排脚本和人类各取所需。

## Console 双世界与一个诚实的边界

Runtime 域里发布两类执行上下文：宿主的真实上下文一个，外加每个连上来的浏览器客户端一个合成上下文。在 DevTools 的下拉里选中哪个客户端，求值、取属性、调函数、等 Promise 就路由进那个浏览器世界。Console 于是变成一个双世界控制台：上一行还在查宿主的注册表，下一行已经在浏览器页面里看渲染状态。

宿主侧的调试是完整的：Worker 用每连接一个的调试会话挂回宿主主线程，断点、单步、源码、恢复都可用，宿主 JS 暂停期间调试通道依然活着（因为提问的是另一个线程）。

浏览器侧有一条诚实的不对称：客户端代码**没有**断点和单步，Console 求值和只读源码是全部。这不是没做完的功能凑合上线，错误会显式报"不支持"，而不是假装成功。客户端源码目录也只覆盖 Inspector 自己的产物束，不索引页面其他脚本。做产品调试器时"哪些能力是真的"这条线划在哪里，这是个可抄的样本。

## Network 面板：抓的是宿主的手

网络捕获默认开启，包住宿主的 `fetch`：完整 URL、全部请求响应头、请求体、响应体、状态、时序、错误、取消，一样不少。重要的是它**不脱敏**：凭证、cookie、查询参数、载荷，原样进面板。捕获靠克隆流，调用方拿原始响应的时间不受影响；保留量有明确上限（请求体前缀 8 MiB、响应体前缀 32 MiB、总量账本 256 MiB、活跃请求 2000 条），超限保前缀并标记截断。

不脱敏是刻意的。这是一个开发者诊断工具，脱敏后的抓包对定位"到底发了什么"基本无用。真正的控制在外面一圈：这个能力太危险，所以整个 Worker 只许绑 127.0.0.1，浏览器上报通道要求宿主注入的随机令牌并拒绝非回环来源，CDP 插座本身没有令牌，回环绑定就是它全部的访问控制。一句话概括安全模型：**等于本机任意代码执行加上全量抓包，所以永远不出本机。**

## 边界与落点

已知限制值得挑重的说。Worker 没有自动重启，意外退出则整个 Inspector 实例失败，恢复属于后续工作。浏览器客户端的页面 CSP 可以挡住动态求值，此时 Console 对那个世界失效。客户端身份仲裁依赖 Web Locks，没有这个 API 的浏览器分不清两个同源的活标签页。抓包只覆盖 `globalThis.fetch`，Undici 直连和插件激活前留下的引用不在视野里。

落点上还有一个使用侧的变化：2026 年 9 月下旬的 0.1.7 候选版起，Inspector 不再默认随产品附带，要用就显式组合。这个方向跟整套工具的气质一致：它是给读源码的人用的手术灯，不是给日常用户配的客厅灯，默认不亮。

对做框架的人，这套东西的启示不在调试器本身，在它证明的两件事：一个全插件化的运行时，其可调试性可以做到"树即 UI"的程度；而观察一个活系统的安全做法，是投影快照而不是伸手进去。
