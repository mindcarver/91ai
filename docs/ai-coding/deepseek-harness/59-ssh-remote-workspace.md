# dsh 的 SSH 远程工作区：一次补丁搬走整个执行世界

> "换一个 provider 等于换整个产品"是接缝设计的招牌承诺，2026 年 9 月它有了正式的载体。远程沙箱实验（E2B）在 0.1.6 被整个移除，接棒的是 SSH 家族：一个连接主人 `dsh-ssh` 加 `fs-ssh`、`subprocess-ssh`、`sandbox-ssh` 三个 provider，全部走同一条部署方持有的 OpenSSH 连接。文件、命令、沙箱、终端、LSP 乃至代码运行时随一次配置层补丁整体迁往远程机器，模型可见的工具一个不变。信任模型全部前置：主机别名和凭证启动前配好，远程 helper 和 Node 用 SHA-256 摘要钉死，断线不重连不重放，待决操作直接失败。本篇按 2026 年 9 月下旬的仓库状态拆这条链，以及它接替 E2B 的那条分界线。

## 问题：agent 的手够不着那台机器

从一个具体场景进。你的项目在一台 Linux 构建机上：依赖装在那里、编译器版本钉在那里、测试数据躺在那里的磁盘上。你在笔记本上开 agent，让它改代码、跑构建、看测试结果。文件接缝管的是本地磁盘，shell 接缝起的是本地进程，两边都够不着那台机器。把仓库 clone 到本地跑，构建环境和数据环境都对不上。

这件事的远征实验版大家见过：租一个一次性的云端沙箱，把 agent 关进去跑，沙箱超时销毁。`dsh` 早期带过这样一条 E2B 路径，2026 年 9 月中旬的 0.1.6 版本把它整个移除。实验暴露的问题不在技术而在语义：一次性沙箱里没有"你的工作区"这个概念，宿主的会话状态进不去，沙箱里的文件改动也回不来，它演示了 provider 可替换，却没有回答真实需求。

真实需求是：远程那台机器就是工作区，文件是持久的，环境是你配的，认证是你自己的。这个原语每个人都已经有，叫 SSH。0.1.6 之后落地的是它。

## 三十秒模型

分工一句话：**本地进程管脑子，远程机器管手。** harness、模型调用、会话存储、插件树全在本地；文件读写、命令进程、沙箱、终端在远程。

机制三件套。`dsh-ssh` 是连接主人，持有一条部署方预先配好的 OpenSSH 连接，别的什么都不做。`fs-ssh`、`subprocess-ssh`、`sandbox-ssh` 三个 provider 各自认领文件、进程、沙箱接缝，全部消费 `ctx.ssh` 提供的这条连接，不自己开通道。最后一层传导是白送的：沙箱 provider 本来就消费子进程接缝去启动受限运行器，把子进程指向 SSH 之后，shell、沙箱、终端自动跟着远程化，它们全部通过同一个子进程接缝委托，根本不知道进程已经跑在别的机器上。

于是"搬到远程"在组合层面就是几行补丁的事：换掉 fs 和 subprocess 的 provider 行，接上 ssh 服务，整棵执行世界连根移过去，消费者一行不改。这是接缝设计第一次用一条正式发布的路径兑现它的招牌承诺。

## 部署面：信任全部前置

这套设计对"信任怎么建立"的回答非常保守：运行时零交互，全部前置。

连接层用的是一个现成的 OpenSSH 主机别名。认证、主机身份、known_hosts 条目，都要求启动前配好；服务自己启用 BatchMode、强制严格主机密钥检查、禁用 agent 转发，不添加任何交互式认证流程。翻译过来：连不上就失败，不弹框、不提示、不降级。

远程那头要求预装一个 helper（附带匹配的运行时依赖），以及一个 Node 可执行文件。两样东西的安装路径必须在远程工作区和可写临时根之外，也要在任何后端替换的临时树（比如 bwrap 的私有 /tmp）之外。就绪之前服务会校验已安装产物的 SHA-256 摘要，摘要不匹配不上线。要远程跑代码运行时（PTC），再配一对 bootstrap 路径加摘要，代码执行也从远程走。

这套校验的边界同样写在明处：摘要校验能发现"装上去的东西被动过"，不能把一个可写的部署文件变成可信执行体，更不能把一个恶意 SSH 主机变成善类。它防篡改，不防坏人。

## 通道：一条连接，多条私有车道

OpenSSH 主连接上跑的是一条私有的管理 RPC。每个程序流（一次命令、一个终端会话）走各自独立转发的 Unix 套接字和独立 SSH 通道。这个切分不是为了好看：程序的标准输出永远无法伪造管理回复，也占不掉控制流的通道窗口。一个疯狂输出的远程命令，撑坏的是自己的车道。

每个流的预约还带一把随机的 256 位 TLS 预共享密钥，密钥只经管理 RPC 传递、从不作为流的前缀发送，流的每个字节都经 TLS 双端认证。本地套接字目录私有（0700）、套接字 0600。攻击者替换一个可写套接字路径，冒充不了端点也偷不到流密钥，能做的只剩打断服务或转发不透明的 TLS 记录。

helper 侧的生命周期同样收敛：连接关闭、终止信号、心跳租约（默认 30 秒）过期，helper 自己启动远程清理。没有"连着但半死"的悬空状态。

## 语义：不重连、不重放

断线语义是这套设计里最需要使用者读懂的部分。传输一断，待决操作全部拒绝，整条连接作废。**不自动重连，不自动重放。** 理由是原理性的：一个断线的客户端无法确认远程那头最后一次操作的真实结局，此刻重放等于赌"它没执行过"。赌错一次，一个"创建目录"变成两个，一个"删文件"变成删两次。

正确姿势是把重试决策交还给调用方：进程重新拉起、连接重建、状态从会话日志重放，然后由人或编排逻辑决定哪些操作值得再来一遍。这跟会话日志"模型可见即可重建"的承诺是一对：日志保证你知道自己做过什么，SSH 层诚实告诉你"最后那下成没成我不知道"。

## 边界与代价

两端都只支持 Linux 和 macOS，没有 Windows 端点，没有自动开通（远程机器自己装 helper）。Web 界面的工作区路径仍假设本地文件系统，官方给的建议是用 headless 或自定组合让消费者尊重 provider 路径。也就是说，浏览器界面里那个文件树，看到的还是本地，远程工作区的完整体验目前在命令行侧。TLS 流密钥保护的是传输，防不了远程操作系统级别的进程内存窥探。文件效果策略沿用所选沙箱后端的限制语义，沙箱接缝指向 SSH 后，受限运行的语义就是远程那侧的实现。

对评估者还有一条值得记的对比。E2B 路径的教训不是"云沙箱不好"，是它把"远程执行演示"和"远程工作区"混在一层里：沙箱是一次性的，工作区需要是持久的，两个语义塞进同一个 provider，哪个都做不真。SSH 家族把持久性还给真实机器，把一次性留给上层按需组合。E2B 时代文章里那句"这不是 workspace 同步功能"的自我声明，成了它退场的注脚。
