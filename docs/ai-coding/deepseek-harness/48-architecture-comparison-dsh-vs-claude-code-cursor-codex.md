# dsh 与 Claude Code、Cursor、Codex 的架构横评

> 把三个闭源或半闭源的 coding agent 产品和一个全插件化的开源 harness 放在一起，比什么？不比功能清单，不比模型能力，不比 benchmark 分数，比六个架构维度：定位、内核归属、模型锁定、扩展方式、可组合性、抽象代价。最值得带走两个结论。第一，开源有两种含义：Codex CLI 的 Apache-2.0 意味着代码可读，dsh 的全插件化意味着内核可换，前者并不蕴含后者。第二，可组合性是一笔前期交税、后期收息的账，选哪边取决于你是要用工具，还是要做基础设施。外部事实统一取 2026 年 9 月下旬的公开口径，dsh 部分对齐 v0.1.7 候选版的仓库状态，"适合谁"的部分是我的归纳。

## 先说比什么

不比三样东西。

功能清单不比。功能是版本的函数，三个产品以周为单位发版，任何清单写下来三个月就过期。模型能力不比。模型是外部变量，四个工具接的模型能力此消彼长，今天测出的强弱明年就换位。benchmark 分数不比，这一条值得单独解释。

SWE-bench 上的名次量的是模型加 harness 的合成表现。一个任务解出来了，你分不清分数里多少来自模型本身的推理能力，多少来自 harness 给它的工具设计、上下文管理、错误恢复路径。而一个准备选型 harness 的读者，要选的恰恰是后者。把模型当控制变量、把架构当观察对象，是横评能做的事；反过来把架构当背景板去比分数，什么也选不出来。dsh 自己的仓库里有一份 BENCHMARK.md，内容只有一段话：教你怎么用 Python SDK 起隔离的 benchmark 任务，如何跑法一个字不提。这个姿态本身就是答案：harness 项目把测法交给你，因为它知道分数不属于自己。

比的是六个维度：架构定位（这个工具本质上是什么）、内核归属（agent 的核心循环谁说了算）、模型锁定（锁不锁模型）、扩展方式（怎么扩展能力）、可组合性（能力能不能组合和替换）、抽象代价（复杂度和开箱即用怎么换）。这些维度比功能清单有预测力，因为功能是版本函数，架构是天花板函数：一个工具能长出什么功能，早被它的架构位置框住了。

写作纪律只有一条：事实和判断分开。说 Claude Code 是闭源 CLI，这是事实，有官方口径背书；说它适合什么样的团队，这是判断，我会标明是我的归纳。横评的可信度全部押在这条纪律上。

## 三十秒：产品，还是运行时

先给一个不用任何项目名词的框架。

市场上的 coding agent 分两种身份。一种叫产品：安装、打开、输入任务、拿到结果，从交互到内核都替你做好了决定，你消费的是这些决定的质量。另一种叫运行时：它自己没有面向终端用户的完整形态，你把它装进自己的程序里，在它上面搭出你要的东西，界面归你、用户归你、发行节奏归你。

这个区分无关优劣，两边服务的对象不同。产品服务用工具的人，运行时服务造工具的人。同一家公司可以两边都做，一个工具也可能在两个身份之间迁移，但任何一个时刻，它的机制细节都在为其中一个身份优化。

四个工具里，Claude Code、Cursor、Codex 是产品，dsh 是运行时。dsh 也有 Web 界面，但那个界面只是它多个 profile 中的一个，和 headless、SDK、ACP 平级，都是插件树上的一种组装方式。记住这个分野，后面六个维度的每一条差异，背后都是"为用户优化"和"为构造者优化"这两个目标在机制上的投影。

## 四个工具各是什么

按开源程度从深到浅过一遍，事实冻结在 2026 年 9 月下旬。

dsh 是 DeepSeek AI 开源的 agent harness，MIT 许可，TypeScript 写成，pnpm monorepo 组织，截至 2026 年 9 月 24 日的发布版本是 v0.1.7-rc.2，packages/ 目录按能力域切出两百多个包：core、llm、sandbox、session、mcp、acp、ssh、browser-use、computer-use、bundle、subagent 各成体系。它处在 developer preview 阶段，README 用全大写提醒"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"。定位上没有特权核心，agent loop 本身是插件树上的一个可替换节点，这句断言的机制落点后面展开。

Claude Code 是 Anthropic 的 agent 客户端，闭源。形态是 CLI 加 VS Code 扩展，扩展里打包的是同一个 `claude` 内核。另有一个开源的 Claude Agent SDK，提供编程入口，但它是驱动闭源内核的客户端库，不是内核本身。agent loop、工具签名、context 压缩策略由 Anthropic 写死，用户通过 CLAUDE.md 项目指令、skills 技能目录、hooks 生命周期钩子在外层定制。官方 GitHub 仓库（anthropics/claude-code）托管 issue、插件和文档，不含产品源码。2026 年 3 月，它的打包 source map 意外泄露了约 51 万行源码，安全厂商拿它当闭源边界之外的阅读材料分析过；泄露不改变许可状态，但这个事件正好是后面一节的活教材。

Cursor 是 AI 代码编辑器，基于 VSCode fork，闭源。agent 能力嵌在编辑器里，Tab 补全、Chat、Agent 多种交互形态，支持 Claude、GPT、Gemini 多家模型，但 agent 的行为逻辑由 Cursor 控制。2026 年 1 月起它有了自己的 CLI，带 Plan 与 Ask 两种模式和到云端 agent 的 handoff。入口在扩张，内核归属没变。

OpenAI Codex 是 OpenAI 的 coding agent，入口覆盖 CLI、云端环境、VS Code 扩展与 GitHub 集成。这里要纠正一个流传很广的误读：Codex CLI 不是闭源的。它的仓库 openai/codex 在 GitHub 上以 Apache-2.0 发布，主体用 Rust 写成，源码可读、可提 PR、可自行编译。闭源的是云端服务和模型本身。所以"Claude Code 和 Codex 封闭、dsh 开源"这个三分法不成立，成立的是更细的辨析，下一节就是它。

## 内核归属：开源不等于内核可换

先把两个术语落到白话。harness 圈子里把 agent 的支撑结构分成两层：inner harness 是厂商内置、你改不了的部分，典型如 agent loop（决定下一步做什么的循环）、工具执行管线、context 压缩策略；outer harness 是你和团队自建的部分，项目指令文件、技能目录、钩子脚本、CI 集成。四个工具的差别，本质是这条分界线画在哪。

| 工具 | inner harness | outer harness |
|---|---|---|
| dsh | 不存在，全是插件 | 整个插件树 |
| Claude Code | Anthropic 写死的 loop、工具、压缩 | CLAUDE.md、skills、hooks、Agent SDK |
| Cursor | Cursor 控制的 agent 行为与补全逻辑 | 项目规则、settings |
| Codex | OpenAI 控制的 loop 演进 | AGENTS.md、Rules、Hooks、Skills |

dsh 的官方架构文档有一句原话："There is no privileged core to patch"。扩展 dsh 的方式是在别的插件旁边再挂一个插件。它的 core/agent 提供 Agent 接口和注册表，core/agent-loop 是实现这个接口的默认驱动。注意"默认"这个词：驱动是插件树上一行可以被 patch 替换的配置，不是焊死的地基。这条分界线不是修辞，是包结构本身。

现在讲本篇最重要的辨析：开源的两种含义。

第一种是可读的开源，Codex CLI 属于这类。Apache-2.0 给你读源码、审计安全性、提交贡献、自行编译的权利。但产品路线、默认行为、架构演进的方向盘在 OpenAI 手里；你 fork 一份改出自己的分支，就要永远追着上游跑。inner harness 对你是透明的，但不服从你：你能看，不能换。

第二种是可换的开源，dsh 属于这类。开源在这里甚至不是重点，重点是没有任何一个部件拥有特权地位。想换掉 context 压缩，写一个插件挂上去，原插件卸载；想改 agent loop 的重试节奏，patch 掉那一行配置。

可读和可换是两个正交的属性，四种组合在市场上都存在：闭源且不可换（Claude Code、Cursor），可读但不可换（Codex CLI），理论上可换但闭源（这个格子是空的，闭源堵死了替换的工程路径），可读且可换（dsh）。

2026 年 3 月那次泄露把这件事推到了极致。五十万行可读的 Claude Code 代码摆在所有人面前，可读性一夜之间拉满，替换权一毫米也没增加。为什么？因为替换依赖的不是文件的可见性，而是架构许可：模块边界是不是接口化、扩展点是不是插件化、注册是不是可撤销。这些属性写在代码的结构里，不写在 LICENSE 里。你能把泄露的源码逐行读懂，然后呢？你没有可以挂载进去的插槽，没有可以 patch 的配置行，没有可以卸载的默认实现。

把可读和可换的区别再压成一句可以带走的话：可读性回答"我能不能看懂它"，可替换性回答"它离了我行不行"。看懂一个系统不需要它的许可，GitHub 上点开就能读；让一个系统离了你继续运转，需要它在设计时就为"被换掉"留好插槽、写好撤销逻辑、备好测试。前者是信息问题，后者是权力结构问题。

这条辨析直接改变选型动作。你的需求是理解工具行为、做安全审计、学一个工业级实现，可读就够，Codex CLI 的仓库满足你，Rust 写的 agent 核心本身就是好教材。你的需求是换掉压缩策略、换沙箱后端、重排 loop 行为，可读帮不上忙，你要的是替换权，那是 dsh 的赛道。拿着审计需求去要求可替换性，或者拿着替换需求去满足于可读，都是维度错配。

两个中间地带也在这条光谱上。Claude Code 完全闭源，但 outer 层做得厚：CLAUDE.md、hooks、skills 三件套加一个开源 SDK，能覆盖相当多定制场景，这是刻意的产品化投入。Cursor 闭源且 outer 层最薄，定制面基本由编辑器暴露的配置项决定。outer 层的厚度是闭源产品对"改不了内核"的部分补偿：厚度越大，越少人需要碰内核。

升级的不对称也藏在这条分界线里。闭源产品发新版，agent loop 可能整个变了，你的 hooks 和项目指令要跟着适配，不适配就留在旧版本上。dsh 的等价变更是插件树里的一次替换，你可以选择不跟：把那一行配置钉在当前实现上，其余部分照常升级。可组合性在这里兑现成一种很实际的权力，对变更节奏的否决权。代价是行使否决权的人要自己承担分叉的维护成本，永远钉住等于永远追不上主干，这笔账没有免费的一边。

## 模型锁定：商业设计，不是技术缺陷

dsh 的模型接入是一个叫 `ctx.llm` 的接缝。能力图谱上挂在这个接缝下的官方实现有三个：llm-deepseek（自家模型）、llm-pi-ai（多 provider 适配层）、llm-replay（测试用回放）。因为是接缝，任何 OpenAI 兼容端点都能写个适配器挂上，或者直接在配置里声明一条路由。换 provider 是换一条配置行或一个插件的事。

Claude Code 绑定 Claude 家族。企业部署可以走 Amazon Bedrock 或 Google Vertex AI，路由到的仍是 Claude 模型；社区还有 Bifrost 一类的网关，用 OpenAI 兼容代理把 Claude Code 接到第三方端点。但这些是外挂技巧，不在产品承诺之内，版本升级随时可能破坏。Codex 绑定 OpenAI 模型，云端和 CLI 一致。Cursor 支持多家模型，在它集成的清单里切换，清单外的加不进来。它在这条谱系的中间位置：多模型是产品策略换来的弹性，但弹性的边界由集成清单划定，你拿到了选择权的一部分，选择权的主人仍然是产品方。

判断这件事时容易踩一个坑：把模型锁定当成技术缺陷。它其实是商业设计，而且有正当理由。厂商客户端的存在意义之一，是把自家模型的特性（思考预算的控制、缓存命中的口径、工具调用的方言）压进 inner harness 的调优里。Claude Code 对 Claude、Codex 对 OpenAI 模型的深度适配，正是闭源产品体验流畅的来源。锁定还有一层性能含义：provider 侧的 KV 缓存按请求前缀复用，厂商客户端可以保证自己的每一版系统提示、工具目录、上下文组装方式都维持前缀稳定，缓存命中率是深度调优的直接收益。dsh 放弃这份单模型深度调优，换来对任何 provider 的开放性，它对前缀稳定的追求只能做在通用层（比如模型目录不渲染进工具描述，避免目录变化重写缓存前缀），做不到针对单一 provider 的极限压缩。两边的账都算得过来，看你站在消费侧还是构造侧。

开放接缝的另一面也该写出来：接缝把自由给了你，也把义务给了适配器作者。dsh 的适配器契约要求守三组承诺。流的形状：用量事件先于终态到达，工具参数在流式过程中全程保持原始字符串。token 的三桶口径：缓存命中的部分要从总数里减出来，否则依赖用量信号做触发的压缩，其压力曲线是斜的。错误的稳定 code：重试和压缩按 code 路由，不读报错原文。闭源产品里这些义务由厂商内部消化、内部测试兜底；开放生态里它们散布在每个适配器作者手里。一个第三方适配器漏守一条，故障就藏进计费漂移或压缩失效这种难复现的地方。开放不是免费的，它把质量责任从单一厂商重新分配给接缝两侧的所有参与者，选开放生态之前要先问自己接不接得住这份责任。

## 扩展方式：改行为参数，还是改能力结构

这是四个工具差异最实质的维度，拿一条具体需求来走：让 agent 每次改文件前自动留一份备份。这条需求会贯穿本节和下一节。

Claude Code、Cursor、Codex 的扩展是配置级和脚本级：项目指令、规则文件、钩子脚本。它们改变的是 agent 的行为参数，用什么提示、遵守什么规范、在哪个生命周期节点跑哪段脚本。在 Claude Code 里，备份需求是一个 before-hook 脚本的事：钩子在文件编辑前跑一段 shell，把目标文件复制走。配置级扩展的典型解法，够用。

dsh 的扩展是插件级。写一个 Cordis 插件，实现 apply(ctx, config)，用 ctx.tools.register() 注册工具、ctx.on() 监听事件，卸载时所有注册按序撤销。插件改变的是能力结构本身：新增一个 service、替换一个子系统、改变事件流的形状。备份需求在这里有两条路。浅的一条是监听工具事件，在写入前做备份，和 hook 等价。深的一条是实现一个在写入路径上先备份的 fs provider：dsh 的文件系统是一个接缝，官方就有 fs-local、fs-sandbox、fs-ssh 等实现并存，你完全可以再挂一个。备份一旦成为文件系统能力本身的默认行为，之后任何走 fs 的工具，包括你将来才装上的，自动继承。

两条路的差别不在代码量，在改动的层次。前一种改的是某次调用的行为，后一种改的是能力的默认值。再往上还有 hook 根本够不着的层：给遥测换自建后端、给审批接内部工单系统。这些在配置级产品里连对应的旋钮都不存在，谈不上难度，产品压根没把这层开放成配置。

同一条备份需求在另外两个产品里的遭遇，能把这条分界线拉得更直。Codex 有 hooks，写一个编辑前钩子能解决，和 Claude Code 同层。Cursor 的 outer 层是四个工具里最薄的：项目规则文件改变的是提示内容，settings 改变的是产品开放的行为开关，两者都没有"文件将被修改"这个生命周期锚点。想在 Cursor 里做自动备份，你得在产品之外想办法，比如文件系统层的 watch 脚本，那已经不是对 agent 的定制，是对操作系统的定制。同一个需求，四个工具给出从"一段脚本"到"换一个 provider"的四种答案，答案的深度不由需求决定，由工具把哪一层开放出来决定。

两级扩展对应两级需求。想让 agent 知道项目的编码规范、提交前跑个检查、给某个框架加专属提示，配置级足够，这也是市场上大多数定制的真实形态，三个产品因此存在。想换一个文件系统实现、换沙箱后端、重定义审批链路，配置级无能为力，因为你要动的东西在产品里根本没有暴露成配置项，必须插件级。这是基础设施形态的需求，dsh 因此存在。

一个实用的自问：把你的定制需求写下来。如果每一项都能表述成"告诉 agent 某件事"或"在某时刻触发某脚本"，用产品；只要有一项表述成"替换某子系统"，你就需要运行时。

## 可组合性实测：换一个 provider，搬走整个执行世界

可组合性容易停留在口号层，所以拿两个测试用例实测。

第一个用例是远程执行。dsh 的做法源自一条架构约束：filesystem 和 subprocess 两个 provider 共享同一个执行世界。能力图谱上，fs-ssh 和 subprocess-ssh 都只消费同一个 SSH 连接主人，那个包负责共享的认证连接、远程 helper 和销毁。把 `ctx.fs` 和 `ctx.subprocess` 指向远程 SSH 主机，Bash、PTY、LSP 整体跟着迁移过去，不需要为远程执行在任何工具里写 provider 分支。一个 provider 的替换，移动了整个产品的执行位置。这个用例的历史本身还是一条证据：dsh 早期用 E2B 云沙箱做过同一件事，2026 年 9 月中旬的 0.1.6 把整套 E2B 后端移除、换成 SSH 家族，执行世界的实现被整个替换过一次，消费者一行没改。可替换性到什么程度？连"远程执行"这个能力的实现本身都被替换过。

对照另外三条路径。Claude Code 的远程执行靠 Docker 容器或 SSH，这是运行环境的替换，不是 harness 结构的替换，agent 对"我在哪执行"没有结构性认知。Codex 的云端入口提供远程执行，但那是 OpenAI 的基础设施，你选择用或不用，不能换成自己的。Cursor 的云 agent 同理，2026 年起的 CLI handoff 把任务递给 Cursor 自己的云。三条路都通向"能远程"，都不通向"远程能力是我可替换的一等公民"。

第二个用例回到备份需求，看它在配置层怎么落地，因为这是"可组合"落到工程上的具体形状。dsh 的组合是分层的：bundle 按列出顺序叠成基线，profile 的 patch 改在其上，home 目录的 patch 再改一层，命令行 `--patch` 最后覆盖。patch 按行 id 定位，整行替换或插入新行，任何一层插入的东西仍然可以被更上层的 patch 再改。想换掉默认的压缩插件，写一小段 patch 把那一行指向你的实现，其余几十行原样不动。这套机制的隐性代价是：最终生效的配置不再是任何单个文件，它是多层叠加的结果。所以 `--dump-config` 在 dsh 里不是便利功能，是理解系统的必经入口。

支撑这个替换能力的，是两条容易被口号掩盖的底层机制。

第一条，注册是可逆副作用。注册一个工具、一段提示、一个监听器，都是框架追踪的 effect，插件卸载时按序撤销。这不是"开发者记得在 dispose 里手动清理"的编码约定，是运行时保证，每个 registry 都有热重载安全的测试压着。没有这条，"换插件"会留下监听器泄漏和幽灵注册，组合就是空中楼阁。你换上自己的 fs provider 再换回来，世界必须和没换过一样干净。

第二条，拦截靠事件链组合。`agent/pre-step`、`agent/request-error`、llm 流式事件、工具事件这些 waterfall 的监听器必须调用 `next()`，多个拦截者因此能串成链。重试策略、限流、审计都是链上的插件，不是写死在 loop 里的 if 分支。想改恢复行为，挂一个监听器，不用改任何核心代码。

还有一条常被忽略的保障值得单独说：dsh 有一条"模型可见即可重建"的运行时不变量，任何进入模型请求的东西，必须能从会话日志重建出来，运行时有断言压着这条规矩。它和可组合性的关系是制约与兜底。插件可以自由改变模型看到的世界，但每次改变必须留痕、可重放。开放内核之所以不失控，是因为自由度被审计能力包着。没有这条不变量，插件越自由，调试越接近玄学。

这个架构还有一个推论落在 agent 自己身上：既然 agent loop 是插件，运行时修改插件树的通道打开之后，agent 就能编辑自己的组合。仓库的 web-cordis 示例演示了这件事，agent 在对话里挂载、卸载、调整插件，改变自己下一步的能力面。"一切皆插件"走到逻辑尽头，就是自我修改。这在闭源产品里没有对应物：内核不可换的系统，自指只能停留在提示词层。

## 复杂度的账

dsh 的代价是结构性的，不随版本迭代消失。

概念门槛。Cordis 的 fiber 和 effect、profile、bundle、patch、接缝、waterfall，做深度定制前每一个都要过。这串名词不是随手堆的，每一个都对应一类你在封闭产品里遇不到的问题。fiber 和 effect 回答"插件卸载时谁负责清理"；profile 和 bundle 回答"配置从哪些层叠出来"；接缝回答"这个能力有几个实现、换的时候动哪里"；waterfall 回答"多个拦截者谁先谁后、谁能短路"。学它们的成本是一次性的，但不是小额的，一个没有插件框架经验的团队按周计。

调试链长。一个行为的根因可能穿过多个插件。拿一次真实排障走一遍：症状是一个 MCP 工具不生效。在配置级产品里，路径基本是重启、查凭证、翻日志。在 dsh 里，第一站是 dump 配置确认那一行真的被加载了，patch 层叠里它可能被更高层整行替换掉；第二站查 serverName 是否和别的 server 冲突，注册期会拒绝重复的名字；第三站看 MCP 客户端的重连预算是否已经耗尽，预算烧完之后工具静默消失。三站都有确定答案，代价是你要知道有这三站。封闭产品把这几站藏在厂商运维里，开放系统把它们交给用户，这就是复杂度暴露的具体形状。复杂系统的第一故障源往往不是某段代码错了，而是你以为装上的东西根本没装上，这条规律在所有组合系统里成立，dsh 只是用 dump-config 把它变成了一个显式动作。

再叠加 developer preview 阶段的明示不兼容变更，深定制要预留迁移成本。版本管理的坑有实测记录：全仓两百多个包锁步发版，但 npm 的 latest 标签不跟着预发布走，单独安装某个 `@deepseek-ai/dsh-*` 包会安静地装到旧版本；错配不报安装错误，以类型错误的形式延迟爆炸，运行时才爆，没有一条可搜索的报错串。

性能是另一笔税。全插件化把热路径摊薄了：一次工具调用要穿过接缝、注册表、waterfall、事件投影好几层间接，每一层都为可替换性付费。闭源产品可以对热路径做一体化优化，开放系统的优化受接缝边界约束。对 agent 这种单步以秒计的负载，多数场景感知不到；做高频自动化的场景，要先量再选。

还有一笔组织税：可组合性要求团队里有理解插件框架的人。产品形态下，定制知识止于配置文件；运行时形态下，定制知识要下探到 Cordis 的生命周期语义。团队规模小或流动大，这份知识留不住，钉住的插件树会退化成没人敢动的遗产，可组合性的收益随之清零。

回报侧对称地写全。任何子系统可替换可组合；可以在它上面做二次开发搭自己的产品；不锁模型，任何 OpenAI 兼容端点；全开源，连 Cordis 框架层都 vendor 进来，可审计到地基。产品侧的账：内核不可改，模型锁定（Claude Code、Codex），扩展面受限于产品暴露的配置项；回报是开箱即用，装上就能干活；体验经过大量用户打磨，编辑器集成、错误恢复、交互细节都有专人负责；inner harness 针对特定模型的深度调优，是闭源产品的体验护城河。

## 什么时候选什么

以下是判断，是我的归纳。

选 dsh，如果：你要搭自己的 agent 产品，需要一个可组合的运行时做底座；你要替换某个子系统，远程沙箱、自定义遥测后端、自定义审批流；你研究 harness 设计对 agent 行为的影响，需要在 loop 层做实验；你用 DeepSeek 模型但不接受被锁死。

选 Claude Code，如果：你用 Claude 模型，想要一个打磨成熟的命令行或 IDE 内 agent；你的定制停留在项目指令、技能、钩子层，或者用 Agent SDK 把它嵌进自己的脚本；你不想维护任何基础设施。

选 Cursor，如果：编辑器原生体验对你最重要，Tab 补全和 inline 编辑是日常主力；你的工作流和 IDE 深度绑定，2026 年起的 CLI 也够用；你想在多家模型间切换且不需要自己写 provider。

选 Codex，如果：你在 OpenAI 生态里，要多入口（CLI、云端、IDE 扩展、GitHub 集成）的 agent；你的团队需要 GitHub 侧的自动化；你想读一个工业级 agent 实现的源码，Apache-2.0 的 codex 仓库本身就是好教材，四个里唯一用 Rust 写的。

三种具体处境做快速映射。独立开发者赶一个下周上线的功能：三个产品里挑顺手的就是正确答案，别碰 dsh，学习曲线会吃掉你全部余量。平台团队要给公司搭内部 coding agent，要接自有审批、自有审计、自有模型网关：从 dsh 起步，或者至少按它的接缝划分来设计自己的系统，因为这类需求迟早走到"换 provider"这一步，产品挡在那里。研究者要对比不同 loop 设计对任务表现的影响：dsh 把 loop 变成了可替换的变量，这是实验台属性，产品给不了。

趋势上再给一个归纳。产品侧在成熟度和体验上领先，这个差距还会拉大，因为闭源产品的迭代速度由专职团队保证。架构侧的组合能力是 dsh 独有，产品侧短期内不会跟进，因为可组合性和体验打磨争夺同一份工程预算。dsh 自己的能力面也在往产品的传统领地伸：2026 年 9 月的版本里，浏览器与桌面控制（三个可换的浏览器后端加 Cua Driver 驱动）、SSH 远程工作区、桌面应用陆续进场，全按接缝和 provider 的形状落地，GUI 操作这种产品级能力被做成了可替换件。变量在开放协议：dsh 同时站在两个开放协议的两端，作为 MCP 客户端能接所有 MCP 兼容的工具服务器，作为 ACP 可驱动方能被任何 ACP 兼容的客户端当引擎用，它的生态不限于自家仓库里的插件，还包括两个协议各自生长的工具网络。协议生态起来，开放性的回报按网络效应复利；起不来，可组合性再好也只是单机优势。

## 权衡

先把横评自身的局限摆出来。四个工具的公开信息密度不对等：dsh 可以读到每一行源码和内部决策文档，Claude Code 和 Cursor 只能读到官方文档与泄露的只言片语，Codex 居中。信息不对称会系统性地扭曲判断，闭源工具的能力被低估（内部机制看不到）或高估（营销话术没法验证），本文所有关于闭源产品内部实现的描述都停留在公开口径，读者取用时按层打折：表格里的行会过期，架构位置的变动慢得多。

时点是第二个局限。外部事实冻结在 2026 年 9 月下旬，三个产品的功能面半年一变，dsh 自己还在 developer preview。这一篇的方法比数字耐用：六个维度、可读可换四象限、"告诉它"和"换掉它"的自问，拿这套框架去看任何一个新版本、任何一个新入场的工具，比记住本文的任何一句结论更有用。

dsh 自身的代价前面已经摊开：概念税、调试链长、preview 阶段的迁移成本、性能税、组织税。它换来的东西同样真实。这笔交换没有普适答案，只有立场答案。

## 结论

四个工具的差别可以压成一句话：产品卖的是"体验已经替你做好决定"，运行时卖的是"决定权交给你"。Claude Code、Cursor、Codex 各自在自己的位置上把体验做到了高水平，outer 层的厚度（指令、技能、钩子、SDK）还在持续加厚；dsh 用两百多个包的工程量回答了"开放内核怎么做"。它把"一切皆插件"从口号落到有运行时保证的事实，靠的是三件事：注册即副作用，卸载按序撤销；依赖即声明，加载顺序由需求推导；替换即迁移，一个 provider 换掉，整个执行世界跟着走。口号和工程的距离，就在这三条保证有没有被测试压着。

从它的实践里挑可迁移的经验，我选四条，因为它们不依赖你用不用 Cordis。第一，让框架追踪副作用，别靠人记得清理，泄漏的监听器是长生命周期系统最常见的慢性病。第二，能力用接缝组织，不用直接 import，定义、提供者、消费者三角色让替换成为结构允许的操作而不是重构手术。第三，恢复策略用事件链表达，不硬编码在主循环里，可插拔的重试比写死的重试活得久。第四，外部世界不可靠是常态，为每一类不可靠设计具体规则，而不是一层笼统的 try-catch。还有两条实践不起眼但都在省钱：文档是构建产物，一致性靠门禁验证；测试测真实入口，mock 只 mock 昂贵边界。

dsh 不是唯一答案。封闭 harness 在产品成熟度上领先，在开箱即用上更好，大多数场景下它们是正确选择。但 dsh 证明了另一种可能在工程上成立：agent 的核心基础设施可以是开放的、可组合的、可审计的，代价是一笔明码标价的复杂度税。这个可能值不值得追求，取决于你相信 agent 基础设施的未来由谁提供。dsh 押了开放那边，这篇横评拆的就是这笔押注的工程含义和它的价格标签。
