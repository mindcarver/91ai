# 文档即代码：用脚本自动生成图、目录和校验

> 如果你只能从这篇带走一句话，带走这句：`dsh` 仓库的 `scripts/` 目录有 80 多个脚本，一半是从源码生成文档（gen-*），一半是验证文档和源码一致（verify-*），两边配合让文档无法漂移：源码改了但文档没改，门禁就挂。
> 这一篇拆这套 docs-as-code 系统的设计逻辑，看生成脚本怎么工作、校验脚本怎么门禁、以及为什么这种投入对一个开源项目值得。

## 为什么文档要当代码

软件项目最常见的文档问题是**漂移**：文档写的时候是对的，代码改了之后文档没跟着改，文档就变成了谎言。漂移的文档比没有文档更糟，因为它误导读者。

`dsh` 的解法是 docs-as-code：文档不是手写的静态文件，而是从源码生成的，或者从源码校验的。如果源码和文档不一致，CI 门禁失败。

这需要大量脚本投入。`dsh` 仓库的 `scripts/` 目录有 80 多个 TypeScript 和 shell 脚本，分成两大类：生成脚本（`gen-*`）和校验脚本（`verify-*`）。另有少量迁移脚本（`migrate-*`）和工具脚本。

这不是过度工程。一个 221 个包的 monorepo，如果靠人肉维护文档一致性，要么文档永远过时，要么没人有时间写代码。自动化的代价是写脚本的时间，回报是文档永远可信。

## 生成脚本：从源码产出文档

生成脚本通过 AST 遍历或运行时反射，从 TypeScript 源码提取信息，写成 Markdown 或 JSON 文件。主要的生成脚本：

**`gen-config-catalog.ts`**：扫描每个可加载包的 config 声明，生成 `docs/config-catalog.md`。这个文件包含每个插件能接受的全部配置字段，JSDoc 原样保留。生成器还做交叉校验：runtime Schemastery schema 的每个 key（包括嵌套 key）都必须能在声明的 config 类型上定位到。这防止了"schema 接受一个字段但文档没写"的漂移。

**`gen-cordis-catalog.ts`**：生成 Cordis 服务目录。每个 `ctx.*` service 的方法签名、事件声明、JSDoc 都从这个脚本产出到各子系统文档的 `## Cordis API` 区域。一个包改了方法签名，重新生成后文档就更新了。

**`gen-cordis-api.ts`**：生成 Cordis 框架级 API 参考（`docs/cordis-api/`），包括框架继承的 `ctx` 表面（`ctx.on`、`ctx.effect`、`ctx.loader` 等）。

**`gen-tool-catalog.ts`**：生成模型可见工具的 schema 目录（`docs/tool-catalog.md`）。每个工具的 name、description、parameters schema 都从这个脚本产出。

**`gen-module-graph.ts`**：生成模块依赖图（`docs/module-graph.md`），展示包之间的依赖关系。

**`gen-doc-graphs.ts`**：生成文档里用的 mermaid 图。架构图、流程图、时序图都是从源码或配置生成的，不是手画的。

**`gen-client-catalog.ts`**：生成浏览器端 slot 目录，让模型知道有哪些 UI 座位可以贡献组件。这个脚本在自指工具集（34 篇）里被提到过。

**`gen-scoped-events.ts`**：生成 scoped 事件参考。

**`gen-persistence-catalog.ts`**：生成持久化目录。

**`gen-third-party-notices.ts`**：生成 `THIRD_PARTY_NOTICES.md`，从依赖的 package.json 自动收集许可证信息。

所有生成文件的顶部都有标记，比如：

```markdown
<!-- Generated by scripts/gen-config-catalog.ts, do not edit by hand.
     Run `pnpm run gen-config-catalog` to regenerate. -->
```

这个标记做了两件事：告诉读者别手编，告诉 CI 怎么重新生成。

## 校验脚本：门禁

校验脚本不生成内容，只检查一致性。它们是 CI 门禁的核心。

**`verify-type-equiv.ts`**：检查文档里 `ts type-equiv` 围栏标记的类型声明和源码一致。用 TypeScript parser 从源码提取声明，断言文档里的粘贴匹配。改了源码但没改文档？门禁失败。

**`verify-md-links.ts`** / **`verify-md-wrap.ts`**：检查 Markdown 内部链接有效、格式正确。

**`verify-mermaid.ts`**：检查文档里的 mermaid 图语法正确，能渲染。

**`verify-doc-refs.ts`**：检查文档之间的交叉引用有效。

**`verify-doc-budgets.ts`**：检查文档长度在预算内。过长的文档是信号：要么该拆分，要么该精简。

**`verify-package-readme-limitations.ts`** / **`verify-package-readme-model-experience.ts`**：检查每个包的 README 包含必需的 section（Known Limitations、Model Experience 等）。

**`verify-export-jsdoc.ts`**：检查导出的 API 有 JSDoc。

**`verify-package-invariants.ts`**：检查每个包有 invariant companion（38 篇拆过）。

**`verify-config-source-ownership.ts`**：检查配置来源归属清晰。

**`verify-vendored-links.ts`**：检查 vendored 代码的链接有效。

**`verify-runtime-closure.ts`**：检查运行时闭包完整。

这些校验脚本和生成脚本配合使用。比如 `gen-config-catalog.ts` 生成文件，`verify-config-catalog`（通过 doc-sync 跑）检查它是最新的。你改了一个包的 config 声明但没重新生成 catalog，verify 就失败。

## 具体案例：config-catalog 怎么工作

拿 config-catalog 做例子，看完整的生成和校验链路。

1. 你在 `packages/llm/llm-deepseek/src/index.ts` 里给 `Config` 接口加了一个字段 `streamIdleTimeoutMs`。
2. 跑 `pnpm run gen-config-catalog`。脚本用 TypeScript AST 遍历所有包的 config 声明，提取 `Config` 接口和 JSDoc，写到 `docs/config-catalog.md` 的 `@deepseek-ai/dsh-llm-deepseek` 条目下。
3. 同时，脚本把 runtime Schemastery schema 和声明的 config 类型做交叉检查，确认 `streamIdleTimeoutMs` 在 schema 和类型声明里都存在。
4. 跑 `pnpm run verify-config-catalog`（doc-sync 的一部分）。如果 `docs/config-catalog.md` 和源码不一致，门禁失败。

这个链路保证了：文档里的每个配置字段都来自源码，源码里的每个配置字段都在文档里。

## type-equiv：文档里的类型和源码 1:1 对应

这是 docs-as-code 里最精细的一层。

`dsh` 的子系统文档（`docs/subsystems/*.md`）里粘贴了大量源码声明。这些声明用 `ts type-equiv` 围栏标记，注册在 `scripts/type-equiv.manifest.json` 里：

```json
{
  "doc": "docs/subsystems/session.md",
  "symbol": "SessionEvent",
  "source": "packages/core/session/src/types.ts"
}
```

`verify-type-equiv` 用 TypeScript parser 从 `packages/core/session/src/types.ts` 提取 `SessionEvent` 的声明和 JSDoc，断言 `docs/subsystems/session.md` 里的 `ts type-equiv` 围栏内容匹配。比较忽略空白和非 JSDoc 注释，但要求每个原始 JSDoc 注释都在。

这意味着：你改了 `SessionEvent` 类型的一个字段，`docs/subsystems/session.md` 里的粘贴必须同步更新，否则门禁失败。文档里的类型定义和源码永远是 1:1 对应的。

还有一个 `ts public-api` 变体，用于类的公开 API 投影（保留 public 字段、构造器、accessor、方法和 JSDoc，省略 body 和 private/protected 成员）。

## doc-sync：一次跑完所有文档检查

`dsh` 把所有文档相关的生成和校验收拢到一个命令：

```sh
pnpm run doc-sync
```

这个命令运行所有 verify-* 脚本（type-equiv、config-catalog、cordis-catalog、tool-catalog、doc-graphs、client-catalog 等），检查文档和源码一致。

如果你想重新生成所有产物：

```sh
pnpm run gen-cordis-catalog   # 或其他 gen-* 脚本
```

`doc-typecheck` 是另一个相关命令，检查文档里的 TypeScript 代码块能编译通过。它对 `ts type-equiv` 和 `ts public-api` 围栏跳过编译（因为它们是声明片段，不是独立可编译的），对普通 `ts` 围栏编译。

## 这个系统的工程纪律

这套 docs-as-code 系统背后有几条工程纪律。

**文档是构建产物。** 生成的文档文件不放在版本控制的手编区，而是有明确的 "Generated by" 标记。读者知道别手编，CI 知道怎么重新生成。

**校验是 CI 门禁。** 文档不一致不让合并。这把"文档漂移"从"代码评审时容易漏"变成了"CI 自动抓"。

**交叉校验防止隐藏漂移。** config-catalog 不只生成，还把 schema 和类型声明做交叉检查。这防止了"schema 接受但类型声明没有"或"类型声明有但 schema 不校验"的不一致。

**分层校验。** type-equiv 管类型声明，config-catalog 管配置，cordis-catalog 管 service API，tool-catalog 管工具 schema。每个维度独立校验，一个问题不影响其他维度的检查。

**生成有测试。** 生成脚本本身有 `.spec.ts` 测试（`gen-config-catalog` 没有，但 `gen-cordis-catalog` 有 `gen-cordis-catalog-partition.spec.ts` 和 `gen-cordis-catalog-record.spec.ts`）。这保证了生成逻辑正确。

## 代价和回报

这套系统的代价是什么？

**初始投入大。** 写 80 多个脚本是一个巨大的工程投入。每个生成脚本要理解源码结构、提取正确信息、格式化成文档。每个校验脚本要定义一致性规则。

**维护成本持续。** 源码结构变了，生成和校验脚本也要跟着变。一个新的声明模式可能需要更新生成器才能被正确提取。

**学习曲线。** 新贡献者需要理解哪些文档是生成的、哪些是手编的、怎么重新生成。这增加了 onboarding 成本。

回报是什么？

**文档永远可信。** 读者看到的类型声明、配置字段、API 签名和源码一致。没有"这个文档可能过时了"的猜疑。

**变更评审更高效。** Code review 不用花时间检查文档和代码是否一致，CI 做了。reviewer 可以专注于逻辑正确性。

**重构更安全。** 改了一个类型声明，所有引用它的文档自动报错。你不用人肉找哪些文档提到了这个类型。

**文档质量可量化。** doc-budgets 检查文档长度。package-readme-limitations 检查必需 section。文档质量从主观判断变成了客观门禁。

对于一个 221 个包、50 多个 service、几十个工具的 monorepo，这个投入是值得的。没有 docs-as-code，文档要么是过时的废话，要么是没人有时间维护的空壳。
