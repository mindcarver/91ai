# Python 与 TypeScript：同一引擎的两种手感

> 更新日期：2026/10

**TL;DR：** 两门语言的 SDK 包着同一个引擎，机制完全一致，差异全部在语言层：类型判断方式、事件类型体系、环境变量的传递语义、若干单侧独有的能力。选语言看团队栈，跨语言协作看这份对照。最有价值的不是记清单，是理解差异的三个来源：类型系统风格、运行时模型、成熟度节奏不同步。

## 同与不同：先立框架

两门 SDK 的关系一句话：机制层同一（同一引擎、同一协议、同一行为），语言层两套（类型、习惯用法、能力节奏）。

差异的来源有三，记住来源就不用背清单。来源一，类型系统风格：TS 用判别联合（按 type 字段分派），Python 用类继承（按类型判断分派），同一个事件流在两边长成不同的类型形状。来源二，运行时模型：TS 的异步迭代器和上下文约定对比 Python 的异步生态和客户端对象约定，API 形态跟着各自生态走。来源三，成熟度节奏：两边不是同步发版，TS 侧常常先拿到新事件类型或新选项，Python 侧随后补齐，某个时点的差异多数属于节奏差不是设计差。

拿着这三个来源，下面所有具体差异都能"猜到为什么"。

## 消息与类型：分派的两种写法

事件流的消费是差异最集中的地方。

TS 侧：事件是一个联合类型，分派按消息的 type 字段 switch；模型消息和用户消息的内容嵌在包装层里（内容取值要多钻一层），部分系统子类型被拆成了独立类型而不是同一类型的子类型字段。这意味着 TS 的分发代码要在类型收窄上花功夫，编译器会推着你写对。

Python 侧：事件是一组类，分派用类型判断；消息的字段平铺（少一层嵌套），系统子类型统一在一个类型下按子类型字段区分。写起来更直，但没有编译期强制，漏分支不报错。

跨语言移植分发逻辑的固定坑位：TS 的嵌套取值翻译到 Python 容易多钻或少钻一层；Python 的子类型字段判断翻译到 TS 要先查这个子类型是不是已被拆成独立类型。移植后第一件事跑一遍全类型冒烟（构造能触发各类消息的任务），让漏分支当场暴露。

## 环境变量：替换与合并的世纪分叉

全系列重复过三次的差异，对照表里排第一：环境变量选项的语义，TS 是替换（传了就整个换掉，不继承任何东西，PATH 和认证变量都会没），Python 是合并（同名覆盖，其余继承）。

同样的需求（给子进程加一个变量），两边的正确写法完全不同。TS 要先展开继承原环境再改，Python 直接加。这个差异在认证配置和遥测配置上最容易咬人：TS 侧"加了代理变量之后突然没登录了"是它的标准症状。团队跨语言时，把这段写进两边的代码模板里，让正确写法成为默认。

## 单侧独有能力：清单与影响

TS 独有（截至本文时间线）：更多的钩子事件类型（会话起止等一批生命周期事件，Python 侧类型层未暴露）、提示的缓存切分能力（静态动态分段各自缓存断点，且仅直连部署有效）、若干选项增强（运行时设置更新、长提示的文件路径形态等场景）、部分返回内容的完整处理（音频内容存盘给路径，Python 侧丢弃）。

Python 独有或更顺手：选项的文件形态（超长系统提示写文件避免命令行参数长度限制）、Pydantic 生态的 schema 生成（结构化输出的 schema 从模型类一键出）。

节奏差要单独理解：TS 曾有过的第二套会话接口已被移除（两语言最终又回到同一形态），Python 侧历史上还修过空列表语义的偏差。所以清单本身有时效，用的时候对照两边的参考文档核对，别把本文清单当永久事实。

选型时独有能力清单的权重别放太高：它们多数是锦上添花，核心机制两边全量对等。真正的选型依据是团队栈和运维生态（你们的主力语言、观测栈的 SDK 成熟度、现有服务形态）。

## 客户端与会话：对象模型的两种手感

Python 的客户端对象是显式的伙伴：连接、发消息、收回复、断开，生命周期清晰，会话在客户端内自动延续。TS 没有常驻客户端的形态，会话延续靠每次调用的显式参数（continue 或 resume），"当前会话"是你要自己管理的状态。

两种手感各自的坑：Python 的坑是把客户端当永生对象（长驻服务里客户端意外重建，隐式延续断裂），TS 的坑是忘了传延续参数（多轮对话莫名失忆）。前面会话篇给过的建议在对照语境里再立一次：把会话 ID 当显式业务状态管理，两种语言都别依赖隐式延续，坑就都绕开了。

Python 还有一个节奏约定要背：客户端上一条消息配一对发送与接收调用，接收循环在第一条结果处停。TS 的异步迭代器没有这个节奏问题但也没有客户端的复用便利。各有各的账。

## 逐项对照速查表

高频差异的速查，按"踩坑概率"排序。

| 项目 | TypeScript | Python |
| --- | --- | --- |
| 环境变量选项 | 替换，须展开继承 | 合并，直接加 |
| 事件分派 | type 字段加类型收窄 | 类型判断加平铺字段 |
| 消息内容 | 包装层嵌套一层 | 直接平铺 |
| 会话延续 | 显式参数，无常驻客户端 | 客户端内自动延续 |
| 钩子事件面 | 更宽（会话起止等） | 较窄（类型层未暴露部分） |
| 结构化 schema | Zod 生成，注意目标版本 | Pydantic 一键生成 |
| 长系统提示 | 切段缓存（直连限定） | 文件路径形态 |
| 音频类返回 | 存盘给路径 | 丢弃并警告 |

表的用法是写代码前扫一眼，特别是跨语言移植和双语言团队：每一行都是一个已知的坑位，十行扫完，八成的跨语言事故提前免疫。

## 双语言团队的协作模式

两边都要用的团队（比如 TS 的产品壳加 Python 的数据工具），两个实践显著降低维护成本。

共享判断核心：钩子和事件归约这类纯逻辑（数据进出、无 SDK 依赖的部分）抽成语言内共享模块，钩子壳和归约壳两边各自薄薄一层。业务判断一份逻辑一份测试，语言差异被壳隔离。

机制层差异文档化：把这张对照表扩充成团队自己的文档（加上你们踩过的具体案例），新成员入职第一天读。跨语言 bug 的复盘结论回写进表，让表成为活的 institutional memory。

## 两种写法的取舍

**新项目选哪门？** 团队栈优先于一切。栈对半开时看集成点：产品主体是 TS（Web 服务）选 TS（进程模型亲和），数据与脚本生态重 Python 的选 Python。性能上两边无实质差异（瓶颈在模型调用不在语言层）。

**一边先用新能力，另一边怎么跟？** 短期用边车（先发的能力包在主力语言的服务里，另一边经接口调用）；长期等节奏差收敛（多数能力数月内对齐）。评估独有能力是否值得为此架构加层，多数时候不值得。

**同任务的输出在两门语言下一致吗？** 机制行为一致（同一引擎），逐字节输出不保证一致（模型调用的采样本来就有随机性，两边时间线上微小的差异也会放大它）。跨语言的一致性测试断言机制不断言文本（结果子类型、会话行为、成本量级）。

**从一门迁到另一门，工作量多大？** 机制层的知识百分之百平移（这篇全系列的内容不挑语言），代码层的迁移是重写调用面（分发、回调、选项的形态各语言不同），复杂度正比于你的集成深度。浅集成（发任务收结果）一两天，深集成（全套钩子加工具加适配器）按周计，且要重跑全套测试。

## 同一条任务流的两边走读

用一条具体任务流把差异串起来：处理"查这个仓库的测试覆盖并汇报"的任务，流式模式、带自定义工具、带审批。

任务启动：两边都构造选项对象传任务。TS 传一个异步生成器作为输入源（流式形态），Python 建客户端对象再调用。第一处手感差：TS 的输入源是函数形态（你的生成器随时可注入新消息），Python 是对象方法调用（发一条调一次）。

事件消费：初始化消息到达，两边都取会话 ID。TS 在消息的字段上直接读，Python 在消息的数据层里取。工具调用块到达，TS 要钻包装层拿内容，Python 平铺直取。写分发循环时这段的差异最密集，前文的类型对照是这段的地图。

审批到达：工具调用走到批准，回调触发。两边回调签名里的上下文对象不同（TS 带取消信号，Python 预留位），返回的放行决定里 TS 可带抑制提示规则的选择。写跨平台的审批逻辑时，把"取哪些字段、返回什么形状"抽成共享数据结构，两边各自翻译。

自定义工具执行：工具函数跑在你的进程里，两边手感反而是最接近的（普通异步函数）。差异在返回内容的处理边界（音频块一边存盘一边丢弃）和 schema 的写法（一边链式定义一边类型标注加字典）。

结果到达：字段语义两边一致（子类型、成本、用量、会话 ID），字段拼写个别有大小写差异（驼峰与下划线的历史分歧正在收敛，选项层多数已统一驼峰，但历史字段名仍要对照参考文档确认）。收尾异常语义一致（错误结果后单发抛异常）。

走读结论：差异密度从高到低依次是事件分派、回调签名、输入模式形态；工具定义和结果处理最接近。写跨语言代码时精力分配照这个密度排。

## 安装与运行的差异

环境层的差异小但开局就会遇到。

安装面：TS 经 npm 装（注意可选依赖别跳过，二进制在里面），Python 经 pip 或 uv 装（个别平台源码包不带二进制要原生安装）。运行时门槛：Node 十八以上，Python 三点十以上。Windows 上的差异最明显：引擎的批处理垫片在 Python 侧被拒绝执行（安全加固），TS 侧的路径解析习惯不同，Windows 团队开局先跑一次两侧的启动自检再选型。

开发迭代手感：TS 的直接运行（解释器跑 TS）加类型检查（编译器当免费测试），改完保存即验；Python 的 REPL 适合探索事件形状（打印真实消息对象比读文档快）。两边各自的迭代优势正好互补：TS 快在结构正确，Python 快在形状探索。

## 双语言协作的追问

**团队两门都在用，回归测试要不要两边都建？** 分层建：机制回归（录制回放）两边各一套（事件形状有语言差异，夹具不通用）；业务逻辑测试（工具、归约）测共享核心一份加两边薄壳的接口测试。别试图写一套"语言无关"的测试框架，抽象成本高于收益。

**一边踩了坑，怎么让另一边提前免疫？** 跨语言的坑登记进团队的对照表文档（踩坑记录：现象、根因、两边各自的修法），评审代码时对照表是 checklist。事件驱动的知识管理，表比文档比口口相传都可靠。

**两边的依赖版本怎么对齐？** 引擎与 SDK 的版本组合两边分别记录在案，别假设同一天对齐（成熟度节奏不同步是常态）。跨语言桥接的部署（比如边车形态）在清单里把两侧版本写进同一行，升级任何一侧时对照另一侧的变更说明。版本组合的漂移是双语言系统里最隐蔽的"两边代码都没改但行为变了"的来源，先对版本再查代码。

**两边各自最值得用的生态优势是什么？** Python 侧：Pydantic 全家桶（schema 与数据模型一体）加数据科学生态（工具函数直接包分析库）。TS 侧：与 Web 服务同进程的自然性（产品壳直接嵌）加类型系统对分发逻辑的编译期保护。把工具逻辑放在生态优势侧（数据处理工具用 Python 写、产品交互逻辑用 TS 写），通过边车或独立服务桥接，是双语言团队的常见最优解而不是妥协。

**新版本发布两边的参考文档要不要同步读？** 发版说明各看各的（变更面不同），但遇到单侧的新能力时先查另一侧的等价物再决定是否启用（节奏差的存在意味着另一侧可能数周内有对等实现）。把"启用新能力前做双侧核对"当成习惯，可以避免围绕单侧能力构建出难以移植的架构。

**这张对照表怎么保鲜？** 三个更新触发点：双边任一发版（扫参考文档的变更日志，对照表过一遍）、团队踩到新的跨语言坑（当场回写）、季度例行复核（独有能力清单的节奏差部分变化最快）。表头的"截至本文时间线"标注同步更新。一张过期的对照表比没有更危险（它给人错误的确定感），保鲜机制和表本身一样重要。

## 关键要点

- 机制同一语言两套；差异的三个来源：类型风格、运行时模型、成熟度节奏。
- 最大的单点差异是环境变量语义：TS 替换要展开继承，Python 合并直接加，症状是加了变量丢了登录。
- 分派写法各随生态：TS 按类型字段加收窄、内容多一层嵌套；Python 按类型判断、字段平铺；移植后先跑全类型冒烟。
- 独有能力是节奏差多于设计差，选型看团队栈不看清单；会话 ID 显式管理在两门语言里都绕开各自的坑。
- 双语言团队两实践：共享判断核心加薄壳，对照表文档化并持续回写。
