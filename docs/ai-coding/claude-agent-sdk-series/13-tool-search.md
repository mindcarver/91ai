# Tool Search：大规模工具面的上下文经济学

> 更新日期：2026/10

**TL;DR：** 工具定义是要吃上下文的：五十个工具能吃掉一两万 token，模型的选择准确率在装载三五十个工具后开始下滑。Tool search 把"全部定义常驻"改成"目录常驻、定义按需"，agent 先看工具摘要，需要哪种能力再搜索装载。默认开启，目录上限一万个工具，代价是每次搜索多一个来回。小工具面、不支持的平台和某些代理场景该关掉它。

## 问题：工具面是上下文的第一大盗

算一笔账。一个中等规模的企业 agent：内置工具十几个，接三台 MCP 服务器共八十个工具，自家自定义工具二十个，合计一百出头。每个工具的名字、描述、参数 schema 都要进上下文模型才知道怎么用，平均一个工具一两百 token，一百个工具就是一两万 token 起步。

这不是钱的问题，是两个更硬的问题。第一，窗口被挤压：留给任务本身的上下文变少，长任务提前撞压缩线。第二，也是更隐蔽的：**模型的选择准确率随装载工具数下降**。摆在它面前的一百个工具里挑对一个，比十个里挑对一个难，误调用、幻觉参数、在相近工具间摇摆，都随工具数上升。装载三五十个之后，这个退化开始可感。

Tool search 解决的就是这两件事：上下文成本和选择精度。手段是把装载改成检索。

## 机制：目录常驻，定义按需

开启后的工作方式分三步。

启动时，agent 拿到的不是全部工具定义，而是一份目录（每个工具一行摘要）加上少数核心内置工具的完整定义。读、写、执行这几个骨干工具始终装载，它们是几乎所有任务的起点，也作为"工具长什么样"的范例。

任务进行中，agent 发现需要某个未装载的能力，就调用工具搜索工具（它本身就是内置工具之一），按任务描述检索目录，最相关的若干个工具（默认一次最多五个）的完整定义被装载进上下文。

装载的工具持续可用，直到一次上下文压缩把"发现它们的那批消息"摘要掉，之后需要时再次搜索。这个细节决定行为的可预测性：一次任务里反复用某工具，它稳稳在上下文里；跨过一次压缩，它可能要重新发现。

目录的容量上限是一万个工具。这个数字把"接多少台服务器"的焦虑基本打消：正常工程到不了这个量级，瓶颈回到别处。

## 成本模型：一次搜索换每轮瘦身

天下没有免费的目录。每次搜索是一个额外的来回：模型发起搜索调用，装载结果返回，然后才能发起真正的工具调用。任务要用的工具不在预装里，就要先付这个来回。

于是判据自然浮现：**工具少，预装更便宜；工具多，检索更便宜**。官方给的经验值是十个左右：工具面在十个以内、总量轻松塞进上下文的，关掉工具搜索，直接全装，每个工具调用都省一次潜在搜索。超过这个量级，检索的每轮瘦身开始压倒偶发的搜索开销，且工具越多优势越大。

还有一个容易忽略的收益方向：准确率。装载的工具少了，模型在更小的候选集里选择，误调率下降。对"接了大仓库工具集但每次任务只用其中一小撮"的 agent，这个收益可能比 token 节省更值钱。

## 开关与分档

控制开关是一个环境变量，四档取值。

默认档（不设或设为真）：开启，带下面讲的回退规则。设为真值有一个代理陷阱：它会把能力声明头发给后端，不认识这个头的代理会直接失败。

自动档：按比例激活，可装载定义占到上下文窗口的一成时自动启用工具搜索。可以自定义比例，比例越低激活越早。这是给"工具面中等、拿不准要不要开"的场景准备的，让系统自己算。

关闭档：全部定义每轮装载，回到老世界。小工具面、代理不支持、或者你要可预测的最大兼容性时用它。

除了这个总开关，每台 MCP 服务器上还有个别豁免：标记为始终加载的工具不参与延迟装载，也不计入激活比例的分母。延迟敏感的核心工具（会话必用的那两三个）值得豁免，让它们跳过搜索直达。

## 回退：哪些环境用不了

工具搜索依赖模型和后端的支持，不满足时自动回退到全装模式，判断不用你操心，但要知道有哪些情况，免得疑惑"为什么没生效"。

第三方代理是最大一类：能力声明头和工具引用块需要后端配合转发，多数代理不转发，SDK 检测到非第一方后端就回退。个别云平台明确拒绝这个能力，或旧代模型不认识相关协议头，同样回退。极端保守的环境变量（禁用实验能力）也会连带你关不掉。

回退是无声的。你以为开了，实际在跑全装。验证方法是看首轮的上下文占用或初始化消息里的工具装载情况，别只看配置文件里写了什么。

## 与权限的交互

一个常见的担心：工具定义延迟装载了，授权怎么办？会不会工具没装载时允许列表失效、装载后又要批准？

不会。权限和装载是两个平面：允许列表对"工具"生效，不对"工具此刻在不在上下文"生效。整服务器的通配授权写下去，无论工具定义什么时候被搜索装载，调用都免批。设计权限时完全不用考虑装载时序，这是这套机制工程上成熟的地方。

## 什么时候关掉它

有四个场景该把搜索关掉。工具面小于十个，搜索开销是纯支出。走不支持的自建代理，开了也是回退，还占一个故障面。任务模式高度固定（每次都用同一批工具），预装那批加豁免标记比反复搜索直接。做基准测试需要可复现的上下文形态，检索引入的时序差异污染数据。

关的方式是总开关设否。已经豁免标记的工具不受影响（豁免语义独立于搜索开关存在）。

## 一个调优实例

把机制串起来看一个调优过程。企业 agent 一百二十个工具，默认开搜索后观察到：任务平均多一到两次搜索来回，token 总量降了三成，误调率明显下降。进一步优化：把每任务必用的四个工具（读、搜索、核心查询、日志）标记始终加载，搜索次数再降一半；给内部大仓库服务器的低频工具保持延迟。最终形态：核心工具即调即用，长尾工具按需检索，目录本身只占几百 token。

这个形态的通用配方就三件事：骨干豁免、长尾检索、目录瘦身。骨干是高频必需工具，长尾是大仓库低频工具，目录瘦身是指服务器侧裁掉没人用的工具让目录本身变短。三步做完，工具面从负担回到资产。

## 权衡与局限

工具搜索把工具面的扩展性从"上下文大小决定"解放到"目录质量决定"。代价是行为多了一层间接性：同一种能力可能因为搜索时机的不同在不同任务里表现不同，排障时要多问一句"这个工具当时装载了吗"。时序敏感的确定性场景（回归测试、审计回放）里，这层间接性是噪音源，固定工具面的场景建议关搜索求稳定。

目录质量成为新的功课：工具描述写得好，检索才找得准。描述模糊的工具在检索范式下比在全装范式下更惨：全装时模型至少看得见它，检索时它可能在目录里就落选了。工具数量上去之后，描述的维护标准要相应提高，这层成本经常被漏算。

## 把账算成数字

工具面的上下文账值得一笔一笔算清，这是判断开不开的唯一可靠依据。

单工具成本：一个工具的定义等于名字加描述加参数 schema，写得规整的平均两百 token，带长描述和复杂 schema 的能到五百。五十个工具的全装账单就是一万到两万五，这笔钱每一轮都付（系统提示是每请求必发）。

搜索成本：一次搜索是一个额外来回。来回的直接开销是搜索调用加装载结果的几千 token（一次性，不是每轮），加上一次模型往返的延迟（一两秒量级）。任务用到十个未预装工具，就是十次来回的延迟税。

盈亏平衡点：全装的每轮成本等于工具数乘单工具成本；搜索的每轮成本等于目录成本（每工具十 token 上下，五十个工具五百）加摊销的搜索开销。五十个工具的量级下，全装每轮一万到两万五，搜索每轮五百加摊销，每轮省下的 token 在五到十轮内就覆盖掉搜索的额外来回。十个工具以下，全装每轮两千上下，搜索省的钱付不起来回费。这就是官方经验值十个的来历：它是那两个多项式的交点。

准确率账没法这么精确，但方向明确：候选集从五十缩到装载的十个以内，误调率的下降在实测里普遍可感。对准确率敏感的任务（医疗、金融类查询），这个收益单独就能支持开启。

## 搜索是否生效的核对问题

**怎么确认搜索真的生效了而不是回退了？** 看行为指纹：生效时模型消息里会出现工具搜索调用块，首轮上下文占用明显小于全装的理论值；回退时两者都不出现。配置写了什么不算数，行为才算数。

**搜索结果的稳定性怎么样，同样的任务每次找到的工具一样吗？** 大体一致但非确定：检索是按相关度排序的语义匹配，任务措辞变化可能让第五名和第六名互换。对"必须用某个工具"的硬要求，用豁免标记（始终加载）或提示词点名，别赌检索。

**自定义工具也会被延迟装载吗？** 会，工具搜索对全部注册工具生效（远程 MCP 和自定义都在内）。核心自定义工具标始终加载，其余交给检索，前文配方。

**开了搜索后允许列表的通配符还有用吗？** 有，权限与装载是两个平面。整服务器通配授权照常生效，无论工具定义何时装载。

**代理环境下我能做什么？** 三选一：回退到全装接受 token 成本；让代理转发能力头和工具引用块（问平台方）；绕开代理直连（合规允许的话）。判断顺序：先问平台支不支持，再决定架构让步。

## 决策流程：一屏走完

把全篇的判断收成一条流程，新会话配置工具面时从上往下走。

第一步数工具：内置加自定义加 MCP 全部加总。十个以内，流程到头，关搜索全装，收工。十个以上进第二步。

第二步看环境：走的官方直连或第一方端点吗？是，进第三步。走自建代理或特殊平台，先确认能力头和工具引用块能转发（问平台方或实测），不能就接受回退全装，流程到头；能转发进第三步。

第三步分级：从工具清单里挑出"每次任务几乎都用"的骨干（通常三到五个），标始终加载豁免；其余长尾交给检索。判断骨干的标准是延迟敏感度：会话中间环节必经的工具是骨干，低频增强型的是长尾。

第四步配权限：整服务器的通配授权照常写（权限与装载两平面互不干扰），逐工具的精确授权不受影响。这步基本是确认既有配置不用改。

第五步验证：起冒烟会话，看两个指纹（搜索调用块出现、首轮水位低于全装理论值），跑一轮典型任务确认目标工具能被检索到。两个指纹都在，配置生效。

第六步留档：把工具总数、豁免名单、验证结果记进会话配置的画像日志。半年后工具面变了要重新走流程时，上次的决定就是基线。

六步里最容易被跳过的是第二步的确认（"应该支持吧"）和第五步的验证（"配置写了就是开了"）。回退是无声的，这两步是无声回退的唯一防线；跳过它们，后面的四步做得再细也是白做。

## 目录质量：检索时代的隐藏功课

装载机制解决了体积问题后，检索的命中率成为新的天花板。命中率取决于目录质量，两件事决定目录质量。

描述的区分度。目录里每个工具一行摘要，模型靠这一行决定查不查它。描述之间高度相似（三个"查询数据库"工具）时，检索就是抽签。修法在描述里写差异化信息：查什么库、什么场景、返回什么形态。工具描述的写作标准在检索范式下要从"能用"提高到"可检索"。

命名的表意性。工具名的语义权重比描述还高（它是第一匹配信号）。内部命名习惯（handler2、query_v3）在检索时代的代价直接可见：命中率下降。改名的成本（权限规则、调用方适配）和收益（检索命中）要摆在一起算，新工具从命名抓起，存量工具在影响面小时逐步改。

这两件事没有机制强制，属于"不做不报错但慢慢变差"的慢性债：描述不改，引擎照常跑，只是命中悄悄变差、搜索来回悄悄变多。把工具的检索命中率（被搜到且被调用的比例）放进工具治理的观测里，债才可见。

还一条与自定义工具作者的衔接：进程内工具同样进目录受检索管理，因此自定义工具的描述质量在检索范式下翻了倍地重要。工具篇强调的"描述是提示词"，在工具搜索开启后同时是"描述是检索索引"，一份投入两个回报：既教模型什么时候用，又决定检索能不能找到它，写好它从来没有这么划算过。

## 关键要点

- 两个问题：五十个工具吃一两万 token；装载三五十个后选择精度下滑。tool search 用"目录常驻、定义按需"同时解两题。
- 启动给目录加骨干内置工具；任务中按需检索，默认一次装五个；压缩会触发重新发现。
- 成本判据：十个工具以内全装更优，超过走检索；目录上限一万个。
- 四档开关加每服务器豁免；权限与装载是两个平面，授权不受装载时序影响。
- 代理和特定平台无声回退到全装；调优配方是骨干豁免、长尾检索、目录瘦身。
