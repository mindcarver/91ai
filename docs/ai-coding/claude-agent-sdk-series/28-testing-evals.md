# 测试与评估：给会变聪明的系统写测试

> 更新日期：2026/10

**TL;DR：** Agent 的测试难点在于被测对象是三层叠加：你的代码（确定）、引擎机制（大体确定）、模型行为（概率）。策略是分层剥离：确定性部分（工具、钩子、适配器）按普通软件测，机制部分用录制回放测，模型部分用评估体系测。三层的测试成本和稳定性完全不同，混在一起测是所有"agent 没法测"抱怨的根源。

## 为什么 agent 测试让人绝望

先给绝望命名。团队第一次给 agent 服务写测试，通常模仿单元测试：固定输入、断言输出。然后发现三件事：同一输入两次输出不同（模型的概率性）；测试跑一次几分钟（真实任务要真跑引擎真花钱）；失败原因说不清（是代码坏了、引擎变了、还是模型今天状态差）。

绝望的根源是把三层东西当成一层测。拆开看：你的自定义工具和钩子是普通代码，完全确定；引擎机制（会话、权限、事件流）是确定性逻辑加文档化行为；模型行为是概率分布，每次调用都是采样。三层该用三种测试形态，用错了形态就是上面三种症状。

## 第一层：确定性代码的常规测试

工具函数、钩子逻辑、适配器实现、事件分发的归约逻辑，这些是普通代码，按普通标准测。

工具的测试要点：输入 schema 的边界（模型会填各种奇怪参数，工具的防御性靠测试保证）、错误路径（外部服务挂掉时返回的错误消息质量，那是给模型的提示词）、返回体积（大结果落盘逻辑）。工具函数是纯逻辑（进参数出结果），不需要起会话就能测，测试成本和普通函数同级。

钩子的测试要点：决定语义的穷举（放行、拒绝、改参数每条路径）、超时行为（模拟慢调用）、异常兜底（抛异常的钩子按什么处理）。钩子篇说过核心判断逻辑写成纯函数，纯函数可直接测，这是钩子可测性的来源。

适配器：一致性测试套件官方直接提供（存储篇讲过），套进 CI 就行，自己再补后端特定的测试（断连重连、并发写）。

归约逻辑：录制的真实事件流做夹具（进度篇的做法），纯函数进出，回归测试零成本。

这一层的纪律只有一条：**凡是能不起会话就测的，绝不起会话测**。会话是昂贵资源，把它留给必须用的地方。

## 第二层：机制层的录制与回放

引擎机制（会话恢复、权限链、事件顺序、检查点）需要真引擎参与，但不需要真模型发挥。这层的测试形态是录制回放。

做法：测试会话用钉死的配置（低档模型、确定性选项、固定工具集）跑典型场景，把完整事件流录制存档；回归测试重放场景，断言机制行为（会话 ID 正常分配、恢复后上下文在、权限链按序走、检查点标识齐）。模型的文本输出不断言（那是第三层的事），机制的形状断言（事件类型序列、字段存在性、错误子类型）。

这层测试抓的回归：SDK 升级改变事件形状、配置漂移改变加载行为、权限规则修改意外影响链路。它们是升级事故的最大来源，录制回放是性价比最高的防线。

夹具的维护有个诀窍：按场景而非按版本存夹具（修 bug 场景、审批场景、恢复场景各一套），每套夹具标注录制时的版本。SDK 升级后夹具行为变了，先判断是夹具过期（更新录制）还是真回归（提工单），这个分诊动作本身就是升级流程的核心。

## 第三层：模型行为的评估体系

模型输出没法断言相等，只能评估好坏。评估体系三件套。

任务级评估：一组代表性任务加每个任务的质量判据（不是标准答案，是可检查的性质：修复的 bug 真修了吗、审查报告指出的行号真实存在吗、结构化输出字段齐全吗）。判据尽量机械化（测试真的过了吗、文件真的改了吗），机械判据覆盖不了的用模型评模型（一个评审 agent 按评分细则打分）。跑一组任务出分布（通过率、质量分、成本、耗时），版本间的分布对比就是评估结论。

对比评估：任何重要变更（提示词、模型、工具面）前后各跑一轮评估，看分布移动。单轮绝对分数意义有限（判据本身有噪声），前后对比的相对结论可靠得多。评估结果进版本库随变更记录，半年后"那次改动到底有没有变好"有据可查。

插件评估：引擎自带插件评测的通道（命令行跑插件的评测套件，出可复现的打分报告）。团队自己包装的插件值得配一套：定义插件的评测任务集，插件每次变更自动跑。它和任务级评估的分工：任务级评产品整体，插件级评组件增量。

评估体系的工程经济账：评估任务集的规模按变更频率定，日更的系统几十个任务每晚跑一遍（成本可控），月更的十几个任务手动触发就够。评估不是越全越好，是和变更节奏匹配就好。

## 确定性策略：压概率性的三个手段

测试要稳定，模型要概率，三个手段把概率压进可控范围。

手段一，降低自由度：测试场景用结构化输出（输出形状固定，断言容易）、用窄工具面（行为空间小）、用明确判据的任务（少开放生成）。

手段二，温度换稳定：评估任务能用低档模型就用（成本低、行为稳），判据机械化的任务甚至不需要最强模型发挥。

手段三，多次采样：关键路径的验收测试跑三次取多数（通过两次算过），单次失败不判死。三次的成本换取八成的闪断消除，划算。

三招之后剩下的概率性是本质的（这正是要用评估不用断言的原因），接受它，别追求全绿幻觉：评估大盘的合理状态是分数带波动、趋势稳定，追求每日全绿要么是判据太松要么是自欺。

## 混沌与演练：故障路径也要测

正常路径之外，故障路径的测试常被彻底遗忘，出事时现学。四个必演练项。

依赖故障：MCP 服务器挂掉（工具篇讲过接入演练）、外部 API 超时，断言 agent 行为（合理报错而非死循环重试）。认证过期：令牌到期现场，断言状态正确传递（needs-auth 类）且产品层有出口。存储故障：适配器后端不可用，断言 mirror_error 告警与数据缺口可量化（存储篇的上线演练）。注入攻击：安全篇的上线演练，被操纵的 agent 走多远被哪层拦住。

四项演练每季度跑一次（依赖变化快于代码变化），演练脚本和结果进版本库。它们是"出事时你已经知道会怎样"的全部来源。

## CI 的组装

三层加演练装进流水线：每次提交跑第一层（分钟级，确定性测试）；每晚跑第二层加评估（小时级，机制回归加质量分布）；每次大版本跑演练（半天，故障路径）；插件变更触发插件评估（按需）。分级的关键是反馈速度与覆盖深度的交换，提交等不了小时级，夜晚等得起全量。

CI 里 agent 测试的账要算给团队看：第一层几乎免费，第二层每晚几美元，评估层取决于任务集规模。这个成本结构支持一个重要实践：**测试环境的用量独立核算**（独立 key、独立预算），别让测试流量混进生产账单，也别让生产限额影响测试稳定性。

## 测试债的台账

agent 系统的测试债增长得比普通项目快（机制在变、模型在变、任务分布在变），没有台账的团队半年后就说不清哪些角落从来没测过。台账记三栏：未覆盖项（哪个机制、哪类任务没有测试）、已知不稳定项（哪些测试是 flaky 的、属于哪层、什么处方）、豁免项（明确决定不测的，带理由和复审日期）。三栏季度盘一次，未覆盖的补或显式豁免，flaky 的按层归因清零或降级，豁免过期的复审。

台账的价值在一个具体场景里最明显：大变更前的风险评估。翻台账而不是凭记忆，"这次改动影响面里有多少已测多少裸奔"三十秒有答案，测试策略（跑什么不跑什么）从拍脑袋变成查台账。

## 测试策略的几个疑问

**评估的判据怎么起步，没有历史基线？** 从机械判据起步（测试过了、文件改了、结构化字段齐了），它们无需调优立即能用。模型评模型的细判据等积累了失败案例再加（每个误判案例变成一条细则），评估体系从粗到细自然生长，别一开始就造完美判据。

**怎么测提示词？** 提示词变更走对比评估（前文），另加对抗测试（安全篇的注入演练是子集）。提示词的"单元测试"不存在，它的测试形态就是评估。

**测试里的模型调用能不能 mock 掉？** 能但只对第二层的部分场景：引擎不支持官方的模型 mock，社区做法是代理层拦截模型请求回放假响应。这让你能测机制不花钱，代价是机制与真实模型的交互面（重试、流式边界）测不到。mock 层适合高频跑的冒烟，真模型的录制回放每周跑一轮校准。

**flaky 测试怎么治理？** 按层归因：第一层的 flaky 是代码问题（修）；第二层是环境或版本问题（钉版本、隔离环境）；第三层的 flaky 是本质，用多次采样和提高判据鲁棒性吸收。治理动作是给每个 flaky 测试标注层位，不同层不同处方，别用同一种 retry 糊弄所有层。

**发布前要跑全套吗？** 分级发布：日常变更过第一二层，模型或提示词变更加评估对比，架构变更（工具面、权限、拓扑）加演练。全套只在大版本跑。发布检查表按变更类型定制，这是 agent 服务 CI 与传统服务最不同的地方：变更的类型差异极大，检查表不能一张通用。

## 评估任务集的选集方法

评估体系的最大杠杆不是判据而是选集：选哪几十个任务代表你的产品，直接决定评估结论的有效性。一套选集方法。

配额法选集：按产品的真实任务分布配额。流量分析给出任务类型分布（比如代码类四成、问答类三成、数据处理类三成），评估集按同比例选（四十个任务的集子里各类型十六、十二、十二）。分布对齐的评估分数才能外推到真实通过率。

边缘配额：除常规配额外，专门给边缘场景留三成配额（最长的任务、最怪的输入、最容易翻车的历史案例）。边缘任务是回归的重灾区，按自然分布选会严重欠采样。历史失败案例库（每个线上事故转化成一个评估任务）是边缘配额的首选来源，事故库越厚评估越准。

难度分层：每个任务标难度（高中低），评估报告按层出分。总体分平掉结构变化（简单任务占比升了总分自然高），分层分才暴露"哪档能力退化了"。

选集的维护节奏：季度审一次（任务是否过时、分布是否漂移），线上新模式出现时增量补（新任务类型加两三个代表）。评估集是活文档，不是一次性题库。

## CI 分级的落地形态

分级的流水线落到具体的门禁形态。

提交门（分钟级）：第一层全部加冒烟（起一个会话跑通最小任务，断言结果子类型），引擎与配置的显性故障在提交时就拦。预提交脚本里本地也能跑同款（开发者本机五分钟内知道破坏没有）。

夜间门（小时级）：录制回放全套加评估任务集（成本按任务集规模核算，前面算过独立 key 的账），晨报给分数分布与昨夜对比，超阈值自动开单。

发布门（半天级）：架构类变更（工具面、权限、提示词大改、SDK 升级）触发演练四项加对比评估，人工确认后放行。

三个门的钥匙是变更分类标签：每个 PR 标类型（普通代码、机制相关、模型行为相关、架构），标错级别的门禁漏放，所以标签纪律写进 PR 模板。标签机制听起来土，它是分级门禁里唯一需要人来把关的环节，值得一点流程投资。

## 评估运行的追问

**评估跑一次的预算怎么批？** 按任务集规模一次算清：四十个任务乘单任务成本（从画像来）乘采样次数，得出单轮评估成本，夜间门按月报预算，发布门按次报。数字摆出来，"测试太贵"的讨论就从情绪变成参数（要么缩任务集要么降采样，都是显式决策）。

**模型官方更新（不是你变更）也要跑评估吗？** 要，而且要快：模型侧的静默更新是行为漂移的隐形来源，晨间冒烟加每周小规模评估抽检（十个任务）是性价比最高的守望。发现了漂移再决定适配还是固定模型版本，发现不了就只能等用户报障。

**抽检发现漂移后，回滚还是适配？** 看漂移的方向和你的余量：行为退化且没有绕法，先固定模型版本稳住生产，把适配排进迭代；只是输出风格变化且判据不受影响，更新判据里的过时假设即可。决策要留痕，固定版本是有到期日的欠账，写进台账的豁免栏并设复审日期。

**评估的判据里"模型评模型"可靠吗？** 单次不可靠，工程化后可用：评审提示词固定（评分细则逐条化，不给自由发挥空间）、评审模型与被评模型异构（避免同源偏袒）、抽样人工校准（每周抽十个评审结果人核对，漂了就修细则）。三点做到，机器评审与人工评审的一致率能到八九成，剩下的一两成误差在趋势监控里无伤。

## 关键要点

- 三层拆分是全部策略：确定性代码常规测、机制层录制回放、模型层评估体系；混层测是绝望的来源。
- 能不起会话就不起会话：工具、钩子、归约全是纯函数级成本；机制回归靠夹具，按场景存按版本标。
- 评估三件套：任务级出分布、变更走对比、插件配专评；判据从机械化起步向细生长。
- 压概率三招：降自由度、低档模型、多次采样；接受分数带波动，别造全绿幻觉。
- 演练四项（依赖、认证、存储、注入）季度跑；CI 分级组装，测试用量独立核算。
