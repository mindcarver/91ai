# 权限系统全解：六道门与六种模式

> 更新日期：2026/10

**TL;DR：** 每次工具调用都要过一条固定的评估链：钩子、拒绝规则、询问规则、权限模式、允许规则、审批回调，六道门按序检查，拒绝最优先。六种权限模式是链条第四道门的不同默认策略，从全都问到全放行再到分类器自动裁决。规则语法支持工具名、参数模式、路径锚定和通配符，其中允许通配符比拒绝通配符限制多。理解这条链，权限行为全部可推导。

## 一次调用要过几道门

设想一次编辑文件的调用，从发起到执行之间发生了什么。官方文档给了一条精确的评估链，六道门按固定顺序：先钩子（事前钩子可以放行、拒绝、改参数），再拒绝规则（命中即毙），再询问规则（命中转人工），再权限模式（模式的默认策略），再允许规则（命中放行），最后审批回调（兜底裁决）。任何一道门给出终局决定，调用就不再往后走。

这条链有两个容易被忽略的性质。其一，拒绝的优先级贯穿全局：拒绝规则在第二道门，而且即使在全放行模式下依然生效，这是安全设计的底线逻辑：显式说不的地方，任何宽松配置都翻不了案。其二，钩子的放行不跳过后续检查：钩子说"可以"只是过了第一道门，后面五道照走。钩子是加严的口子，不是绕过后面检查的捷径。

把链条记牢，所有权限行为都能现场推导，这是权限篇要交付的核心心智模型。

## 六种模式逐个看

模式是链条第四道门的策略，决定"没被规则显式处理的调用默认怎么办"。

默认模式：没有模式级自动放行，需要批准的调用流向审批回调。最保守，交互成本最高，开发的起点。

接受编辑模式：文件编辑和常见文件系统命令（建目录、移动、复制、删除等）自动放行，但有边界限定：只在工作目录和追加目录范围内生效，出范围、保护路径、关键路径的删除操作依然要问。原型开发和隔离目录里的自动化常用它，省掉百分之九十的批准点击又不至于放权无边。

计划模式：只读工具正常运行，文件编辑永不自动放行，改文件的 shell 命令同样要经审批。名字里的"计划"指的是它支持的工作流：先读先分析、动改动前必须过人。审查型场景的标准配置。

别问模式：把所有"要问"的调用直接转成拒绝。注意它不是"放行所有"，是"拒绝所有需要批准的"，预授权规则仍然生效。它还有三处硬拒绝：需要用户交互的工具、组织设定为须询问的连接器工具、关键路径的删除命令，**即使有允许规则也拒**。无人值守服务的首选：不挂起等人，缺权限就明确失败。

全放行模式：到达这道门的调用全部批准，关键路径删除除外；拒绝规则、询问规则、钩子依然有效（链条的优先级设计）。它拒绝在 root 或 sudo 下启动（除非在受认可的沙箱里），这是一道内建保险。使用要极度谨慎，只在受控环境用。还要知道一件事：允许列表约束不了它，全放行下没列的工具照样批，想堵具体工具必须用禁用列表或拒绝规则。

自动模式：由一个模型分类器逐动作审查（shell、网络类动作），自动放行或拦截。它是"别问"和"全放行"之间的智能档，代价是分类器的判断不是确定的规则。一个要记住的行为：以自动模式启动的会话会丢弃宽泛的允许规则（比如裸的 shell 工具名），依赖这类规则的程序要显式传默认模式。

六种模式的选择不是一次性的：流式会话里可以运行时切换（配置篇讲过），典型节奏是计划模式做分析、确认后切接受编辑动手。

## 规则语法的三个层次

允许和拒绝规则不止写工具名。第一层裸工具名：整工具放行或拦截。第二层参数模式：工具名挂参数模式（如删命令配特定前缀），只匹配特定调用的规则，权限粒度从工具级细化到用途级。第三层通配符：拒绝侧可以用全量通配和 MCP 全量通配一刀切；**允许侧的通配符必须锚定在具体服务器前缀后**（某台服务器的全部工具可以，裸通配符不行），这是防"一条通配符放行全世界"的护栏，写错不报错而是被忽略加启动警告，配置时看日志。

路径规则有两个锚定语义，写错方向差之千里：双斜杠开头是磁盘绝对路径；单斜杠开头锚定到规则来源的工作目录。同一条规则两种写法覆盖的范围完全不同，规则进版本库前先过一遍这个检查。

还有一条跨工具的规则要单独记：给编辑工具配路径规则时，覆盖的是全部写入类工具（包括写入和笔记本编辑），不用每个工具各写一份。

## 与审批回调的关系

审批回调是链条的最后一道门，这个定位决定了它的可见范围：**只有走到第六道门的调用才出现在回调里**。允许规则放过的、模式自动批的，回调根本看不见。想对每一次调用都做逻辑（全量审计、统一日志），用第一道门的钩子，它在一切之前。

两道门还有一类特殊调用永远走回调：提问工具和组织设定须询问的连接器工具，无论允许规则怎么写都会流到回调（别问模式下则直接拒）。这是"涉及人的交互不可被规则静默放行"的原则体现。

SDK 还有一个阴影警告值得认识：你配了审批回调，但全放行模式或宽允许规则让它永远不被调用，SDK 发出专门的警告码提醒"你的回调被影子化了"。收到这个警告别忽略，它说明你的安全设计和实际行为已经脱节。

## 子代理的权限

子代理默认继承父会话的权限模式，这条默认保证委派不产生权限漏洞。覆盖规则有精细的边界：只有父会话处于默认、别问、计划三种模式时，子代理定义里才可以指定自己的模式；全放行永不通过这条路径继承或传播。设计"低权限父加高权限子"或反过来时，先核对父模式是否允许覆盖，否则静默不生效。

更稳的子代理权限思路是工具层面而非模式层面：给审查员子代理只配只读工具（工具篇的情报档配方），它的模式根本无关紧要，没有工具就没有权限问题。

## 两个安全配方

配方一，锁定型 agent：允许列表只列三件只读工具，模式设为别问。效果：三件工具免批直用，其他一切需要批准的调用自动拒绝，零挂起零放行。内部情报型服务的标准姿势。

配方二，全调用检查型：模式按业务选，全部安全逻辑放在事前钩子里（钩子在链条最前且拒绝全局有效），钩子里做你的审计日志和策略判断。适合"每次调用都要过我的合规系统"的企业场景，比试图用规则枚举所有情况可靠。

两个配方共同的原则：**把最强的拒绝放在链条最前的位置**（钩子和拒绝规则），把方便的放行放在中间（规则和模式），把人的裁决放在最后（回调）。安全设计顺着链条的纹理做，逆着做（用放行模式加回调拦截）就会出现影子化那类脱节。

## 权衡与局限

权限系统的表达力有边界，两处最明显。它匹配的是调用结构（工具名、参数模式、路径），不理解语义："用合法工具干坏事"（被注入后用授权工具删文件）在权限层是合规调用，防这类风险要靠沙箱和网络控制（安全部署篇的主题）。自动模式的分类器是概率性判断，同一动作两次裁决可能不同，合规场景需要确定性结论时别依赖它。

权限配置的维护成本也要认账：规则集会随时间膨胀，规则之间的相互作用（路径锚定、通配符边界、模式切换时的行为变化）越来越难心算。把权限规则当生产配置管理：进版本库、有评审、有测试（对关键规则写"这条该拒那条该放"的断言用例），配置漂移的权限系统比没有权限系统更危险，因为它制造了安全的错觉。

## 权限配置的评审流程

权限规则达到几十条后，"能不能再改"不该靠记忆判断，要靠流程。一套轻量评审四步。

第一步，变更分类。新规则属于放行还是收紧？收紧（加拒绝、删放行）低风险快速通道；放行（新增允许、放宽模式）一律评审。不对称流程的原因：权限事故几乎全部来自放行侧。

第二步，影响面推演。在六道门的模型上走一遍：这条规则在第几道门生效，之前的门会不会提前拦住（规则写了但永远轮不到它，白写）；和现有规则的叠加结果（新放行被旧拒绝压住，或更糟，新放行意外绕开了某条拒绝的原始意图）。推演工具就是那张链路图，画在白板上过。

第三步，测试断言。给规则变更配两三个用例：该放行的确实放行，该拦的确实拦住，边界值（路径锚定、通配符边缘）行为符合预期。断言进回归套件，权限集从此有了可执行规格。

第四步，发布与观测。变更进版本库随应用发布，发布后观察观测篇的工具决定比例图：放行后某类审批等待是否如预期消失、拒绝率有没有意外跳变。权限变更的效果验证靠数据不靠感觉。

四步流程的日常成本极低（收紧通道几分钟，放行评审半小时），换的是权限集长期可维护。没有流程的权限集两年后的典型状态：一半规则已死、几条互相矛盾、没人敢删。

## 权限规则与模式的疑问

**规则越写越多，有办法做大扫除吗？** 有顺序：先加遥测看每条规则的实际命中（没命中的候选删除，命中多的才是活规则）；死规则删之前查 git 历史确认当初为什么加（有的规则防的是低频高危场景，命中少不能删）；互相矛盾的按拒绝优先原则逐个解决。

**自动模式和规则集怎么共存？** 记住那两个交互：自动模式启动时会丢宽泛允许规则（裸工具名级别的），你的窄规则（带参数模式的）保留；分类器的裁决在模式这道门，你的拒绝规则在它之前永远生效。依赖宽规则的产品显式传默认模式，别默认进自动。

**子代理用更严的模式，怎么配最稳？** 双保险：模式层继承默认父模式，工具层给子代理只配它需要的最小工具集。工具层的收紧比模式层可靠（没有继承的例外规则），高危子代理（能跑命令的）两层都收。

**审批回调里的改参数能力会被权限规则绕过吗？** 不会，回调在链条最后，前面被规则放行的调用根本到不了它。想对所有调用做参数消毒，必须用第一道门的钩子（updatedInput 能力），这是钩子篇模式二的由来。

**组织的托管策略和我的规则冲突了怎么办？** 托管策略永远赢，这是设计。你能做的是让冲突显性：托管策略下发时初始化消息会反映它，CI 里跑一个冒烟会话断言关键策略生效（比如删除类操作确实被拒），策略未下发或被绕过时第一时间知道。

## 六模式的组合节奏

模式不是选一个用到底，工作流的每个阶段配不同的模式是高级用法。

计划到执行的切换节奏：分析阶段用计划模式（agent 读代码出方案，零风险），方案确认后运行时切到接受编辑（动手阶段），收尾验证阶段切回计划（只读复查）。一次任务三次切换，每次切换都对应人的一个确认点，模式切换成了流程的节拍器。

无人值守的降级节奏：正常跑在接受编辑（有产出效率），遇到异常（连续失败、预算过半）自动切别问或计划（收紧风险面），人工介入后恢复。模式切换是自动化流程里比开关工具更粗但更快的风控手段。

多代理的分层节奏：主会话计划模式把关，执行子代理接受编辑干活，审查子代理永远计划模式。同一个系统里三种模式并存，各层各司其职。这依赖前文讲的覆盖规则（父模式为计划时子代理可自定义），设计时按那张继承表核对。

节奏设计的统一原则就一条：模式跟着信任走。任务开始时你不知道它会做什么（低信任，紧模式），方案明确后知道它该做什么（中信任，中间模式），收尾时只想看结果（再收紧）。反过来全程一个模式的产品，要么牺牲了安全要么牺牲了效率。

起步模式的选择也值得过一遍脑子：交互型产品从默认模式起步，让用户在一次次批准与拒绝里积累对 agent 的信任感；自动化管道没有人在旁边，直接落别问或计划。还要记得别问模式的三处硬拒绝不受允许规则影响，切换前确认你的流程不依赖那三类调用，否则切换这个动作本身就会改变产品的功能可用性。

切换的实现细节记一笔：运行时切换只对流式输入模式的会话生效（单发会话没有中途切换的语义），每次切换你的程序要落一条审计日志（谁在什么任务阶段切的、为什么）。模式切换是高权限动作，无日志的切换等于权限系统里多了一个没人看守的后门。

## 关键要点

- 六道门固定次序：钩子、拒绝规则、询问规则、模式、允许规则、回调；拒绝全局最高优先，全放行模式也压不过。
- 六模式定位：默认全问、接受编辑限目录、计划读写分离、别问转拒绝（无人值守首选）、全放行仅限受控环境、自动靠分类器（宽允许规则会被丢）。
- 规则三层语法：裸名、参数模式、通配符（允许侧必须锚定服务器前缀）；路径单斜杠锚定工作目录双斜杠绝对。
- 审批回调只见走到第六道门的调用；提问类调用永远流到回调；全量检查用钩子；收到影子化警告说明设计与行为脱节。
- 子代理默认继承模式，仅三种父模式允许覆盖；配方：锁定型用别问加只读白名单，检查型把逻辑全放钩子。
