# 子代理与多 agent 编排：委派的艺术

> 更新日期：2026/10

**TL;DR：** 子代理是 SDK 里的任务委派机制：主会话把一块子任务连同一份专属人设（自己的系统提示、工具集、模型）派给一个独立上下文的新 agent，完成后只有最终汇报回到主会话。它解决两个问题：上下文隔离（脏活不污染主对话）和并行（独立子任务同时跑）。定义的字段、派发的两种方式、隔离的精确语义、三个资源上限、以及"什么时候不该用"，这篇一次讲完。

## 委派解决什么问题

先看没有委派的世界。主会话一个上下文装全部：读三十个文件的理解、每个方案的推理、每次搜索的结果，全部堆在同一个窗口里。任务复杂到一定程度，三个矛盾爆发：窗口不够（上下文被中间过程撑爆）、精度下降（无关信息稀释关键上下文）、串行等待（五个独立子任务排队做）。

人类组织早给出过答案：领导不亲自读所有材料，把调研任务分给专员，专员回来交一页纸摘要。子代理就是这个模式在 SDK 里的实现：主会话是领导，子代理是专员，一页纸摘要就是回到主上下文的最终汇报。

贯穿案例：一个发布审查 agent。主任务"评估这次发布能不能上"，需要三块独立调研：扫描变更日志、跑回归测试分析、检查依赖变更。三块互不依赖，各自要读大量材料，最后各交一份结论。三个子代理并行跑，主会话只收三份摘要做裁决。

## 定义一个子代理

程序化定义是推荐方式：在会话选项里传一组定义，每个定义是一个角色卡。必填两个字段：描述（告诉主会话这个专员管什么，是自动派发的依据）和提示词（专员的系统提示，它的工作方式全写在这里）。可选字段构成角色的资源面：工具限制（只给它需要的工具）、模型与努力档（便宜角色用低档，关键裁决用高档）、技能预载、权限模式、最大轮数等。字段名在两门语言里保持同样的拼写（Python 也用驼峰，对齐线上格式），这个细节写代码时省一次踩坑。

定义的另一个来源是文件：agents 目录下的 markdown 文件，团队共享的角色卡。两种来源同名时程序定义赢。引擎还自带一个通用子代理，日常委派够用，不想要可以用环境变量关掉。

角色卡设计的手感更像写职位说明而不是写代码。描述决定"什么时候被想到"，要写成可匹配的任务画像（"需要逐文件审查变更风险时使用"），泛泛的描述（"代码助手"）在自动派发时会被无视。提示词决定"想到了之后干得怎么样"，角色的工作流程、输出格式、边界约束全在这里。工具限制是最有效的安全边界：只读审查员就给三件只读工具，它想闯祸都没有工具。

高级用法是定义工厂：运行时按参数动态生成角色卡。高风险任务自动换高档模型加严提示词，批量任务用低档模型省钱。定义是普通对象，参与你程序的任何逻辑。

## 派发的两种方式

自动派发靠描述匹配。主会话面对任务时，把任务和各角色的描述对照，匹配上就委派。它是默认机制，体验顺滑，但匹配是概率性的，描述写得含糊就漏派。定位自动派发问题的方法：显式点名（下一段）能派出去，就说明定义本身没坏，是描述不够匹配。

显式派发是在任务里点名："用 code-reviewer 这个代理去审查变更"。点名绕过匹配，确定性派发。调试期用它验证角色卡，产品里对关键角色固定用点名保证不漏。

从事件流里识别委派：工具调用块的工具名是 Agent（老版本和初始化清单里叫 Task，两个名字都要认），子代理内部的消息带着父调用标识，据此把子代理的输出归到哪次委派名下。

## 隔离的精确语义

隔离是子代理的核心价值，语义值得逐条精确。

进去的只有提示词字符串。子代理开新上下文起步：没有主会话的历史，没有主会话的系统提示，任务相关的路径、报错、已做决策，全部要主会话写进委派提示词里。委派提示词写得好坏直接决定子代理的成败，"查一下安全问题"和"检查 src/auth 下本次变更的三个文件，重点看令牌校验，已知问题是 X，输出风险清单"是两个世界。

它能看到的项目层配置：项目的 CLAUDE.md 默认加载（有选项可关）、被过滤后的工具定义、必要时其他角色的名单。这些是它的公共信息面，但主对话本身对它是黑盒。

回来的只有最终汇报。子代理中间读的一百个文件、做的全部推理，都不进主上下文，只有最后一条消息回家。两个推论：其一，主会话可能对汇报做摘要改写，需要原文就在委派提示词里要求逐字输出；其二，引擎会扫描最终汇报里的可疑指令模式（伪装的控制标记、对话标记之类）并中和它们，防止子代理被中间内容操纵后向主会话注入指令，这是委派链上的安全设计。

还有一个容易被忽略的硬边界：子代理因接口错误（限流、超时）早夭时，**错误不会作为它的结果送达**，主会话视角这次委派就是没有回音。编排逻辑要把"没回来"当成一种结局处理。

## 并行与后台

子代理默认后台跑：主会话派出去就继续干自己的事，需要结果才等。这个默认让并行免费：三个调研子代理同时派出去，主会话等最慢的那个，总耗时约等于最慢子任务而非三者之和。

需要同步结果时引擎自动转前台等待；也可以强制非阻塞模式，派出去就不管，适合"顺手跑着"的旁路任务（发个通知、记个审计）。

并行收益的前提是子任务真的独立。有依赖的子任务（B 要用 A 的结论）强行并行就是灾难，老实串行或在提示词里传依赖。

## 资源上限：三个旋钮

委派不是无限的，三个上限守门，全部可用环境变量调。

深度上限默认三：子代理再生子代理最多三层。这是防递归失控的（专员再派专员再派专员）。默认值对绝大多数场景够，调深之前先问是不是设计问题。

并发上限默认二十：同时跑的子代理数。到了上限新委派被拒绝并收到明确提示。并发规划时把主会话的并行任务数控制在这以下，或者按机器资源上调。

预算：子代理的花费计入主会话预算（事件模型篇讲过的整树口径），预算耗尽时整个查询以预算错误结束，后台子代理停，新委派被拒。三个上限叠在一起构成委派经济学：每多一层委派，钱、时延、复杂度都在涨，价值要 cover 成本。

## 恢复子代理

委派是可恢复的。工具结果里带代理标识（内置的两个调研型代理没有这个字段，要恢复就自定义或用通用的），第一次查询时存下会话 ID，恢复时传会话 ID 加在提示词里点名同一个代理、给同一份定义，子代理就从自己的历史继续。轮数耗尽的子代理输出会被标记为不完整（新版本起），带着标记恢复补完，这对长调研任务是刚需：白天跑到一半，晚上接着来。

## 什么时候不该用

两条硬边界。

不要用它协调几十上百个 agent。子代理机制的主语是"会话内的委派"，主会话既是领导又是通信枢纽，规模上去主上下文先死。大规模编排有专门的工作流工具（TS 的新版本提供），它把编排逻辑放到对话之外，按计划调度而不是按对话调度。判据：子代理数在五以内、任务结构是"领导加专员"，用子代理；几十个、有复杂依赖图，换工作流。

不要为省上下文而过度切分。切分本身有成本：委派提示词的书写、摘要的信息损耗、多 agent 的协调开销。一个任务单上下文跑得好好的，切成五个子代理是负优化。切分的正当理由只有两个：上下文真的要爆，或子任务真的可并行。其他的"架构美感"都不算数。

## 权衡与局限

委派换来的隔离和并行，代价是信息损耗和调试复杂度。摘要丢细节是设计使然，重要结论要显式要求保留。调试从"一条对话流"变成"一棵对话树"，排查问题要先定位在哪个节点，事件流里的父调用标识是唯一线索，日志系统要提前按树组织。

行为面上还有个观察值得记录：高档模型更倾向主动委派（能力强的领导更敢放权），配合引擎的预设系统提示（告诫它非必要不委派）形成平衡。你的提示词可以覆盖这个平衡：想让它多委派就明说，想让它亲力亲为也明说。

## 委派提示词的写法

子代理的成败一半系在委派提示词上。一段能用的委派提示词有五个组成部分，缺一项就多一分失败概率。

任务陈述一句话：做什么、产出什么。模糊的任务陈述（帮我看看安全问题）给子代理的只有运气。

输入清单：相关路径、报错原文、已做的决策。子代理看不见主会话，你以为它知道的它都不知道。清单宁多勿少，多给的相关信息是营养，缺给的关键信息是绝症。

边界与约束：只看哪些目录、不要动什么、时间或轮数预算。没有边界的调研型子代理倾向无限展开（它没有成本压力感）。

输出格式：要什么样的报告（结构化清单、严重级别排序、逐条带文件行号）。格式写清，主会话收到才能直接用；不写，你收到一篇散文还得再加工。

上下文衔接：这个结果将被用在哪（供合并决策参考、供进一步修复）。目的明确时子代理的报告详略会自己校准。

一个完整例子（发布审查场景）：审查本次变更中 src/auth 下的三个文件（路径列出）。已知问题是令牌过期校验在并发下可能误判，报错原文附后。只做静态审查，不运行任何代码，最多二十轮。输出风险清单：每条含文件、行号、风险描述、严重级别（高中低）、建议。结果将用于合并决策，有阻断级问题必须醒目标出。

五部分写齐大约一百五十字，写它的时间远小于子代理跑偏后返工的时间。团队可以把五部分做成模板，委派质量从个人手艺变成组织资产。

## 拆与不拆的判断疑问

**怎么判断该拆几个子代理？** 按独立性切：两块工作互相不引用对方的中间结果，就能拆。典型三拆：变更审查、测试分析、依赖检查。拆完后主会话的工作只剩汇总裁决，主上下文全程低水位。

**子代理跑完的结果质量差，问题在哪一层？** 三层排查：委派提示词缺信息（最常见）、角色卡的提示词含糊、模型档位不匹配（复杂审查用了低档）。判断方法：拿同样的委派提示词自己当子代理跑一遍人脑推演，人脑都做不了的说明输入不够，人脑能做而它不能说明档位或角色卡问题。

**主会话总是不委派，怎么办？** 三个杠杆按序试：点名委派（"用 code-reviewer 审查这次变更"，绕过自动匹配验证定义本身可用）；检查描述是否写成了任务画像；提示词里显式鼓励委派。高档模型本身委派意愿更强，模型档位也是杠杆。

**子代理能再用工具搜索、技能吗？** 工具按它的工具配置来（给了就能用）；技能可以在定义里预载。注意它拿到的项目 CLAUDE.md 和工具过滤，配置齐了它就是个正常会话，只是上下文独立。

**委派出去的任务失败了要不要自动重试？** 分错误类型：因接口错误早夭（没有结果送达那种）可以原样重试一次；因任务太难失败的重试要先补委派提示词（把失败原因写进新提示词），否则同样的输入换来同样的失败。无限自动重试在委派场景比单会话更烧钱，一次为限，第二次升级处理。

## 委派经济学的三个算例

委派值不值，用三个典型算例建立数感。

算例一，纯隔离型。任务要读一个八千行的日志找线索。不委派：日志内容进主上下文，约两万 token 常驻，主任务后续每轮都背着它。委派：子代理读完交五百 token 的线索清单，成本多一次委派往返（约一千 token）加子代理自己的会话开销（它读日志的 token 在它的账上，钱没省，主上下文省了）。结论：钱上基本持平略亏，主上下文净赚一万九。这笔交易里省下的是主上下文的宽裕，花掉的约等于一次委派往返，长任务里上下文就是生命，划算。

算例二，纯并行型。三个独立检查各需十分钟。串行三十分钟，并行十分钟。成本不变（同样的工作量），墙钟时间省三分之二。并行的收益全在墙钟时间上，对延迟敏感的场景（用户在等）无脑并行，对延迟不敏感的批处理并行只增加并发管理的复杂度，未必值。

算例三，反面的过度委派。一个五分钟能完成的小任务被切成三个子代理：每个委派提示词的书写加汇总，协调开销超过任务本身；三层委派结构里每层都可能扭曲信息（摘要损耗复利）。结论：委派的固定成本（提示词加摘要损耗）决定了它有最小适用规模，低于这个规模就是负优化。

三个算例合成一张决策卡：上下文压力大山委派（算例一），独立任务多且人在等时并行（算例二），单个子任务五分钟内能完成的不拆（算例三）。卡贴在架构评审的案头。

## 关键要点

- 子代理=独立上下文加专属角色卡；必填描述和提示词，描述决定自动派发的命中率。
- 隔离语义：进去的只有提示词字符串，回来的只有最终汇报；错误早夭不会有结果送达，编排要处理"没回来"。
- 默认后台并行，等最慢不等总和；并行前提是子任务独立。
- 三个上限：深度三、并发二十、预算整树；调之前先怀疑设计。
- 五个以内用子代理，几十个换工作流工具；切分的正当理由只有上下文爆炸和真并行。
