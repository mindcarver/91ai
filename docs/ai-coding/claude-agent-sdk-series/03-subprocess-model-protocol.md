# 引擎盖下：SDK 如何驱动一个 Claude Code 子进程

> 更新日期：2026/10

**TL;DR：** Agent SDK 不是把 agent 循环编译进你的进程，而是拉起一个 Claude Code 二进制子进程，用 stdio 上的 JSON 协议遥控它。这个事实决定了 SDK 的全部工程性格：能力受引擎版本门槛约束、故障跨进程边界传播、并发按进程计资源、部署要带二进制。看懂这层，SDK 的行为从"黑盒玄学"变成"可推理的系统"。

## 为什么第一年就该掀引擎盖

多数人把 SDK 当普通库用：装包、调函数、收结果，能用就不看内部。这个策略在前三个 demo 里有效，在第四个场景崩掉：明明代码没改，升级 SDK 后行为变了；生产环境偶发子进程僵死，日志两边对不上；并发量一上来内存爆了，却不知道该按什么单位限流。

这些问题的共同根源是进程模型。SDK 的每一层 API、每一个怪异行为，都能从"你的程序在遥控一个独立进程"这个事实推导出来。推导能力比记忆文档值钱，因为文档描述行为，推导能预测行为。

## 一个会话的进程拓扑

从你的代码往下看，一次典型的 SDK 会话是这样的：你的 Python 或 TS 进程调用 query()，SDK 在后台启动一个 Claude Code 二进制进程作为子进程，父子之间接上一对管道，任务、审批决定、中断指令从你这边写进去，事件流和结果从那边读出来。会话的生命周期和子进程的生命周期基本重合：会话启动进程起，会话结束进程退。

管道上跑的是 JSON 消息。开头有一个初始化段，SDK 把配置（模型、权限、工具集、系统提示）打包发给子进程，子进程回一个带会话元数据的 init 消息；随后进入流式段，两边按消息序列通信直到任务结束。你在代码里拿到的每种消息类型，系统消息、模型消息、结果消息，都是这条管道上 JSON 的类型化投影。SDK 做的事情概括起来就两件：把你的函数调用翻译成管道上的 JSON，把管道上的 JSON 翻译成你语言里的对象。

理解这个翻译层的位置，很多"怪现象"立刻有了坐标。比如 TS 里你的输入生成器抛了异常，子进程那边收到的表现是"被用户中止"，错误信息变了一句不着边际的 process aborted by user；Python 那边更隐蔽，生成器异常只记在 debug 级别日志里，会话表面无恙地停住，不报错也不继续。两边都不是 bug，是异常没有跨进程语义，只能被翻译成对面能理解的语言：中止或沉默。排查这类问题的第一反应应该是查你自己传给 SDK 的回调代码，而不是查引擎。

## 版本绑定：能力的隐形门槛

SDK 版本和引擎版本是两条发版线，它们之间的绑定关系是隐性契约。

安装层面，绑定是物理的：npm 的 optional 依赖、pip 的平台轮子把二进制和 SDK 版本捆在一起。你的 SDK 版本钉在哪，引擎大概率就在哪个版本附近。需要精确控制时，pathToClaudeCodeExecutable 选项允许你指定一个自装的引擎路径，覆盖随包发行的那个。

能力层面，绑定是逻辑的：SDK 选项只是"愿望"，能不能兑现看引擎。两个有据可查的例子：预算上限的严格执行要求 Claude Code 2.1.217 以上；跨目录查找会话要求 2.1.223 以上。选项传了、引擎不认，行为可能是静默忽略或降级。所以"升级 SDK 后某个选项失灵"这类报告，第一步永远是确认两边版本，第二步去引擎的 changelog 里查这个能力是什么时候进的。

API 面本身的变动也要纳入预期。TS SDK 曾经实验过的第二套会话接口（createSession 那一套）在 0.3.142 版本被移除了。这不算事故，属于 SDK 快速演进期的正常收缩。工程上的对策是常规的：钉版本、锁锁文件、升级当变更管理做，不追新。

## 故障如何跨进程传播

把故障分成三档看，每档的传播路径都不同。

第一档是你的代码出错。回调抛异常、输入生成器抛异常，上一节讲过，跨进程后被翻译成中止或静默。经验法则：会话莫名停住时，先开 SDK 的 debug 日志选项把子进程输出落盘，再重跑。debug 开关两个语言都有，等级越高记录越全，是排查这一档问题的标准工具。

第二档是引擎执行任务出错。任务内部的失败（工具报错、模型拒绝）不终止会话，作为事件流过管道，由你的分发逻辑决定怎么处理。要留意的是结果语义的一个细节：单发模式的 query() 在产出错误结果之后还会再抛一次异常。也就是说你可能在循环里已经收到了 error_max_turns 的结果消息，紧接着又收到一个异常。正确写法是 try 包住整个循环，同时在循环内先取走 session_id 和结果字段，别指望异常处理里还能拿到它们。流式会话则相反，除了崩溃类的硬错误，会话在错误后保持存活。

第三档是子进程本身崩溃。进程级故障（被杀、栈溢出）之后，SDK 会合成一个结果消息来收尾，合成结果的停止原因字段为空值，这是"引擎没来得及说话"的指纹。据此你的代码可以把"结果里没有停止原因"识别为崩溃类失败，走重启或恢复路径。引擎自身也有恢复机制：存在环境变量开关可以让中断的那一轮在恢复会话时重新执行，把"崩在半路"的窗口压小。崩溃恢复的具体会话操作属于会话篇的内容，这里先记住崩溃的指纹长什么样。

## 由此得出的工程清单

进程模型不是背景知识，它直接生成下面五条工程决策。

并发按进程规划。一个会话一个子进程，内存按几十到几百 MB 量级预估，并发上限由机器资源而不是框架决定。想做一百路并发，先算一百个进程的账，再谈别的。

部署产物包含二进制。容器镜像里要确认二进制真的进来了，多阶段构建里被瘦身脚本误删是常见事故。无服务器环境装不下子进程模型时，回到选型四问的最后一问重新选。

信号处理要成对。你的进程收到 SIGTERM 时，子进程不会自动善后，养成在关闭钩子里清理会话的习惯，否则容器平台上会积累僵尸进程。

日志分两半看。你的应用日志和子进程日志是两份，靠 debug 选项和会话 ID 对齐。排障流程固定为：先对齐时间线，再看两边各自的错误，不要在单边日志里找全因果。

版本钉住并留升级窗口。SDK 和引擎的版本耦合意味着升级是双变量变更，测试覆盖要包含"升级后跑一遍完整任务流"这一项，只跑单元测试不够。

## 没有 SDK 的语言怎么办

进程模型还暗示了一条替代路线：既然通信协议就是 stdio 上的 JSON，那么任何能起子进程、读写管道的语言都能直接说这个协议。Claude Code 的 headless 模式就是为此准备的：以非交互参数启动，输入输出换成 JSON 流，协议内容与 SDK 在管道上说的一致。Go、Rust、Java 的团队用这个方式接入，代价是失去 SDK 的类型层和便利 API，换来语言自由。

判断什么时候值得从 headless 升级到 SDK 也有简单标准：当你的集成代码超过几百行、开始手写类型分发的样板时，维护成本已经高于在一个 Python/TS 边车服务里用官方 SDK 的成本。协议裸奔适合薄集成，厚集成用 SDK 包一层边车更划算。

## 权衡与局限

子进程模型的正当性来自一个 trade：用进程隔离换掉了进程内嵌入的复杂度。进程内嵌入（把引擎编译成库直接链接）会有更低的延迟和更简单的部署，但要求引擎为每种语言做绑定、管理两边的内存和线程安全，这条路上任何一边的崩溃都会带崩宿主。子进程模型里引擎是独立演化的黑盒，语言中立，故障隔离，代价是序列化开销和双倍的运维面。

对绝大多数应用这笔交易是划算的，但有两个场景例外。延迟极敏感的场景（每个事件要进毫秒级处理回路）会感受到管道开销；极端高密度并发的场景（单机几百会话）里进程开销占比上升。这两类场景的解法都在架构层：前者考虑 Client SDK 自建循环，后者考虑 Managed Agents 把进程密度问题外包。

## 故障排查的操作手册

进程模型的知识落成排查动作。四类高频故障各有一条固定路线。

最先撞上的通常是会话无声卡死。症状：没有错误、没有输出、等很久。路线：开 debug 日志选项重跑同场景，先看子进程日志的最后几行。两类典型根因：你的回调挂了（审批回调没返回、输入生成器异常被吞），日志里能看到引擎在等；引擎在等外部资源（MCP 连接、网络），日志里有对应等待。前一类修你的代码，后一类按 MCP 篇的时序调优处理。

第二类是行为随版本漂移。症状：同样的代码升级 SDK 后行为变了。路线：第一步确认两边的版本号（你的包管理器记录的 SDK 版本，引擎版本看初始化消息或命令行查询）；第二步到引擎 changelog 里搜变化点（预算门槛、会话查找范围这类版本门槛前文都点过）；第三步决定钉回去还是适配。经验：升级 SDK 的 PR 里跑完整任务流回归，比出事后考古便宜一个数量级。

第三类是进程清理问题。症状：容器里僵尸进程累积、重启后残留。路线：确认关闭钩子里清理了会话对象（优雅关闭是宿主责任，引擎不会替你杀孤儿子进程）；容器场景用进程管理器兜底（init 进程收孤儿）；检查信号传递链（容器的停止信号要到达子进程）。

第四类是日志两边对不上。症状：应用日志显示成功，用户说没结果（或反之）。路线：用会话 ID 对齐两边时间线，先看初始化消息的会话元数据（模型、配置来源），再看结果消息的子类型和停止原因。多数"对不上"其实是两份日志在看不同的会话（并发场景下会话 ID 没贯穿全链路），把会话 ID 打进每一行日志是治本。

四条路线的共同第一步都是同一个动作：先对齐事实（版本、会话 ID、日志时间线），再动假设。进程模型的故障排查里，凭印象猜的代价是双倍的：猜错一层，两层日志都要重看。

## 资源与协议边界的疑问

**一个进程能跑多个会话吗？** 一个 SDK 会话对象对应一个子进程，多会话就是多子进程。想在一个进程里"多开会话"，起多个会话对象即可，资源账按子进程算（托管篇细讲）。

**子进程的内存能限制吗？** 进程级资源限制（容器内存上限、cgroup）作用于子进程，引擎没有内部的内存上限选项。容器内存上限就是你的会话内存上限，配太低引擎会被杀，配太高单机并发上不去，托管篇的容量公式给算法。

**冷启动能压到多快？** 组成部分是子进程拉起、配置加载、MCP 连接（如果有）。前两项秒级内，第三项是大头（时序篇的三十秒等待上限）。压缩手段：预热（托管篇的长驻模式）、减少首启连接的服务器、缓存工具列表的服务器优先。

**协议本身稳定吗，能自己实现客户端吗？** 协议随版本演化（headless 文档是它的公开面），自己实现客户端等于自己承担协议跟踪成本。真需要时优先考虑"边车服务"：一个薄薄的 TS 或 Python 服务用官方 SDK 说协议，你的主语言和它说 HTTP，协议风险隔离在边车里。

**升级引擎但 SDK 不动，可行吗？** 用路径选项指定自装引擎可以组合出版本错配，但这是自担风险：SDK 选项与引擎能力的不匹配前文讲过（静默忽略或降级）。支持的组合以官方的兼容说明为准，别在生产上赌。

## 进程拓扑一图流

把全文的进程关系收进一张图：

```
你的进程(Python/TS)
   │ query() ── 拉起+遥控
   ▼
引擎子进程(Claude Code 二进制)
   │ stdio 上的 JSON 双向流
   │  · 控制段: 配置下发 / init 回执
   │  · 流式段: 事件上行 / 指令下行
   │
   ├──► 工具执行(文件、命令, 引擎亲自做)
   ├──► stdio 型 MCP 子进程(每台一个)
   └──► 网络(模型 API、HTTP 型 MCP、OTel 收集器)
```

三个视图提醒。从你的进程向下看是三层树（你、引擎、MCP 孙进程），资源核算按树全算。从数据看是两条主线（stdio 协议线管控制、网络线管模型与外联），排障先分清哪条线。从故障看是三个隔离边界（进程级崩溃不影响你、网络级故障引擎内处理、协议级故障就是前文说的翻译层怪象），每个边界对应一类恢复行为。

这张图值得画在团队的架构 wiki 第一页。后面所有专题（会话是子进程的本地文件、遥测是子进程直发、托管是这群进程的编排）都是它的局部放大。

## 关键要点

- SDK 的本质是 stdio 上说 JSON 的父子进程对，你拿到的消息类型是管道 JSON 的投影。
- 异常不跨进程：你的回调错误被翻译成中止或静默，排查从 debug 日志开始。
- 版本是双变量：SDK 与引擎各自发版，能力有引擎版本门槛，升级按变更管理走。
- 单发 query() 产出错误结果后还会抛异常，session_id 要在循环里先取走；崩溃的指纹是结果里停止原因为空。
- 并发按进程计资源，部署带二进制，日志两边对齐，这五条是进程模型直接生成的工程清单。
