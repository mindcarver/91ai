# 会话：创建、恢复与分叉

> 更新日期：2026/10

**TL;DR：** 会话是 agent 的全部对话历史，引擎自动写盘，恢复时原样还原上下文。三种回到过去的姿势：continue 接最近一次，resume 接指定 ID，fork 在指定点复制历史开分支。要记住的边界同样清晰：会话保存对话不保存文件系统，fork 分叉的是对话不是代码，跨机器恢复需要专门的存储适配器。

## 会话到底是什么

一次 query 调用结束后，agent 对任务的理解去哪了？答案在磁盘上：引擎把整段对话历史，你的任务、模型的每轮输出、每次工具调用及其结果，自动写成一个 JSONL 文件。这个文件就是会话，文件的标识就是会话 ID。

会话 ID 从两个地方拿：结果消息的 session_id 字段（成功和错误结果都带），或者流开头的 init 系统消息。第一条经验就藏在这里：在你的分发循环里，见到 init 就把会话 ID 存进你的业务数据。等出了问题再去找 ID，等于丢了发票再想报销。

文件落在哪由工作目录决定：用户配置目录下的 projects 子目录里，按编码后的工作目录名分文件夹存放。目录名是工作目录路径的变形（非字母数字字符换成连字符，超长部分截断加哈希）。知道这个布局的用处是排障和备份：会话就是普通文件，能拷贝能归档能删。想改存放位置，有环境变量把整个配置目录重定位。

贯穿案例设成一个渗透测试式的场景：你的 agent 用三十分钟读完了一个大仓库，给出了一份架构分析。现在用户要求"基于这份分析做一次安全审查"。重读仓库要再花三十分钟和同样的 token，恢复会话则一步回到读完的那一刻。

## 三种回到过去的方式

continue 是最省事的：不指定 ID，语义是"接当前目录下最近的一次会话"。适合单人单任务的环境，比如你的个人工具每次启动都接着上次聊。它有一个定义性问题：最近的一次未必是你想要的那次，如果两个任务交替进行，最近一次可能属于另一个任务。

resume 是明确指定：传会话 ID，精确回到那次对话。多会话并行、跨任务恢复、出错后重试，都用它。贯穿案例里安全审查的启动就是 resume 到架构分析那次会话的 ID。

恢复的语义是上下文还原：之前读过的文件、做过的分析、得出的结论都在。但边界必须钉死：**还原的只有对话，文件系统不跟**。会话期间 agent 改过的文件是真实改动，恢复会话不会撤销它们；反过来，会话之后文件被别人改了，恢复的会话记忆里还是旧内容，agent 可能基于过时的文件认知继续干活。对话态和文件态是两条线，会话只管前一条，后一条的回滚归检查点机制管。

fork 是第三种：在 resume 的基础上加分叉标记，引擎复制原会话的历史，生成一个新 ID 的新会话，原会话保持不动。它的用途是"在同一基础上试两条路"：贯穿案例里你可以 fork 架构分析会话两次，一个分支做安全审查，另一个分支做性能审查，两条线互不污染，原始会话永远可以再 fork。

fork 的边界同样重要：**分叉的是对话历史，不是文件**。两个 fork 出的会话如果都去改文件，改的是同一份真实文件，互相看得见对方的改动。想让文件也隔离，配合 worktree 或容器给每个分支一个独立目录，对话分叉加文件隔离才是完整的平行宇宙。

## 恢复之后的选项怎么算

一个高频问题：恢复会话时传的选项（模型、权限、工具集）和原会话不同，听谁的？答案是当次的算数：恢复还原的是历史上下文，配置以你本次传入的为准。这意味着恢复是一次天然的调参机会：上次用默认模型跑的分析，恢复后换高档模型做审查；上次权限开得太大，恢复时收紧。

这个语义也是恢复场景的标准操作模式：出错重试。任务在轮数上限处折戟（error_max_turns），拿到结果里的会话 ID，捕获后异常，resume 回去并把上限调高，任务从断点继续而不是从零再来。预算超限同理，但记得预算是会话累计口径，恢复前要么提高预算要么接受清空重新计，这个口径细节在事件模型里讲过。

## 客户端对象的会话托管

两种语言的会话管理手感不同。Python 的客户端对象会自动跟踪会话：同一个客户端上连续多次 query，会话自动延续，你不用管 ID。TS 没有这套托管，每次调用显式传 continue 或 resume。TS 曾经实验过的第二套会话接口（createSession 那套）已在 0.3.142 移除，现在只有 query 一条路。

TS 的做法多写两行但更显式，Python 的做法省心但有一个隐患：客户端对象活多久会话就延续多久，长驻服务里如果客户端意外重建，延续就断了。做产品时把"当前会话 ID"作为显式状态管理起来，不依赖任何一方的隐式延续，这是更稳的架构选择。一个折中做法是 Python 侧照用自动延续，但每轮结果落地时同步刷新业务库里的 ID，隐式便利和显式状态两头都占。

## 管理 API 与持久化开关

两个 SDK 都带了会话管理的辅助接口：列会话、读某次会话的消息、查会话信息、改名、打标签。做会话管理界面（历史任务列表、恢复入口）时用它们，不必自己解析 JSONL 文件。

持久化本身可以关。TS 的选项把持久会话关掉，会话只存在于内存；Python 走一个环境变量抑制写盘。关持久化的动机通常是性能或隐私（对话不留档），代价是失去恢复能力，且与跨主机存储适配器互斥（下一节的冲突规则会再碰到它）。默认场景让它开着，引擎自己有清理周期，不会无限堆积。

## 会话的完整生命周期

把会话放进时间线看一遍。创建：第一次 query，init 消息分配 ID，你存下它。运行：历史在本地持续落盘。结束：结果消息收尾，文件完整保留。恢复：resume 或 continue 还原上下文，当次选项生效。分叉：fork 复制历史开新支线。归档：管理接口或直接按文件管理。

跨过一台机器怎么办是生产部署的真问题：会话文件在创建它的机器上，自动伸缩的服务里这次请求落在 A 机、下次落在 B 机，本地会话就断了。这个问题的正解是存储适配器，把会话镜像到外部存储，任何机器都能恢复。它是下一篇的主角，也是会话从单机概念升级为生产基础设施的分水岭。

## 权衡与局限

会话恢复的经济学值得算清：恢复省的是上下文重建的 token 和时间，但带着全部历史的会话每轮请求都要为历史付费（缓存缓解但不消除）。超长会话继续跑，边际成本递增；到某个点，把会话里的结论提炼成一段摘要、开一个全新会话携带摘要，反而更便宜。判断的量纲是"历史里有价值的密度"：还要反复引用早期细节的会话值得恢复，只剩结论的会话值得蒸馏。

蒸馏还有一层可靠性收益：全新会话没有历史包袱，不受旧会话里错误推理的污染。恢复会延续错误，旧会话里跑偏的推理会跟着历史一起回来。生产系统的常见设计是短会话加重蒸馏：任务完成即提取结论入业务库，下次从结论出发，而不是无限续命一个巨型会话。

## 会话管理的产品化

会话从机制变成产品功能，中间还有一层设计。四个常见产品形态对应的会话策略。

个人助手型（一个用户一个长期 agent）：显式管理会话 ID，存进用户档案；每次启动 resume 那个 ID；定期（比如每两周）做一次主动蒸馏：让 agent 总结长期记忆要点，开新会话携要点起步，旧会话归档。不蒸馏的长期会话就是慢性病：水位越滚越高、缓存越来越差、历史错误越积越多。

任务队列型（每任务一个 agent）：会话 ID 跟任务 ID 绑定存业务库；任务失败重试 resume 原会话（带上失败上下文）；任务成功即蒸馏产物入库，会话文件进冷归档。这类产品的会话生命周期最清晰：会话寿命等于任务寿命。

协作审查型（多人围绕一次 agent 工作讨论）：会话 ID 即协作对象 ID，分享给参与者的是 ID 而不是会话文件；审查中的会话冻结（不再续跑），要继续就 fork 出工作分支，主会话保持审查时点不被污染。fork 在这里是协作协议：讨论基于一个不可变的共同基础。

批处理型（一夜跑几百个）：会话即产物，跑完即蒸馏即归档，只在失败重试时 resume。存储适配器在这里几乎是必选（几百个会话散在各 worker 本地没法运维），这是适配器篇的典型主场。

四个形态共享一条铁律：**会话 ID 是业务数据**。它出现在数据库、日志、用户支持工单里，命名和索引按业务数据的标准建，别让它停留在进程内存里随重启蒸发。

## 会话进生产后的疑问

**会话能存多久？** 文件不清理就一直在，引擎按清理周期回收本地旧文件（周期可配）。要长期保留的会话，蒸馏成结论存业务库，或把会话文件搬进你的归档存储，别指望 projects 目录是档案馆。

**恢复时提示找不到会话，怎么回事？** 三个常见原因：ID 抄错（最常见）；工作目录变了（老版本 SDK 的查找范围跟目录绑定，跨目录要新版本）；会话文件被清理周期收走了。前两个自己排查，第三个说明该上适配器了。

**并发改同一个会话安全吗？** 一个会话同时被两个进程 resume 属于未定义行为，务必避免。要"多人多入口操作一个 agent"，正确结构是一个常驻会话进程加多路消息入口，而不是多进程抢一个会话。

**fork 出的会话和原会话共享存储吗？** 共享对话历史的复制，不共享后续：fork 之后两边各自演化互不影响。存储适配器里 fork 是重写标识的独立实体（存储篇讲过），删除原会话不影响 fork。

**会话里的敏感数据怎么合规处理？** 三道防线：会话文件所在目录纳入数据保留策略（过期删除）；高敏任务用关闭持久化的选项（不留档模式，注意与适配器互斥）；蒸馏产物入库时过脱敏。会话文件是明文对话记录，它的合规等级等于聊天记录。

## 会话生命周期状态图

把会话在各状态间的迁移画全，工程视角的一张图：

```
        创建(init 分配 ID)
             │
             ▼
   运行中 ◄──resume── 已结束(文件留存)
     │           ▲         │
   fork│      蒸馏后归档    │被清理周期回收
     ▼           │         ▼
  分叉会话     业务库      消亡(不可恢复)
 (新ID独立演化)
```

图上五条边对应五条工程规则。运行到已结束是默认路径，结束时务必收走 ID 和成本数据（闭环动作）。已结束回运行中靠 resume，当次选项生效（调参机会）。运行中直接 fork 出平行支线，原会话不动。已结束的会话蒸馏后归档：结论进业务库，文件进冷存储，业务库才是长期记忆的主体。留存的文件最终被清理周期回收，被回收后 resume 无解，需要长期价值的都要在归档边完成转移。

图里没有画但值得脑补的一条暗边：已结束的会话文件可以手工搬运到别的机器再 resume（前文讲过的迁移手段）。生产系统里这条暗边应该被存储适配器的正规通道替代，手工搬运是救急手段而不是架构方案；判断标准也简单，一旦这种搬运被写进了值班手册，就说明适配器该提上日程了。

再补一条多人协作的经验法则：凡是"会话所有权"不清晰的系统（任何人都能 resume 任何会话），迟早出现两个人同时续跑一个会话互相覆盖理解。会话 ID 的可见范围和操作权限要在产品设计时就定下：客服场景会话属于会话创建者，交接时显式转移；批处理场景会话属于任务，任务锁即会话锁。所有权规则说在前面是三行文档，出事后再补是一场数据考古。

这条法则的另一半属于备份：会话文件纳入备份策略时想清楚 RPO（丢多少会话数据可接受）。个人工具无所谓，生产系统里会话是用户的工作记忆，丢一天就是一天的用户信任。定时打包 projects 目录或依赖存储适配器的后端备份，两条路选一条，别让会话数据活在唯一一份磁盘上。

## 关键要点

- 会话是自动落盘的对话历史，ID 从 init 消息或结果消息取，见到 init 就存业务库。
- 三种回去的方式：continue 接最近、resume 接指定、fork 复制历史开分支；恢复还原对话不还原文件系统，fork 分叉对话不分叉代码。
- 恢复时当次选项生效，出错重试的标准姿势是 resume 加调高上限。
- Python 客户端自动延续会话，TS 每次显式传；产品里把会话 ID 当显式状态管理。
- 恢复救不了所有场景：超长会话的边际成本递增，错误推理也会被延续；短会话加蒸馏是生产的常见替代。
