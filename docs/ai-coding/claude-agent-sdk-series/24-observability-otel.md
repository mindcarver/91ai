# OTel 可观测性：给 agent 装上飞行记录仪

> 更新日期：2026/10

**TL;DR：** 遥测的架构一句话：SDK 自己不产遥测，它把环境变量传给引擎子进程，引擎通过 OTLP 协议直接导出到你的收集器。三类信号（指标、日志事件、链路）按开关启用，默认全部结构化、不含对话内容，内容级记录要逐级显式打开并有脱敏控制。链路信号能把 agent 的每一轮、每次模型调用、每次工具调用放进一张 trace 图，还能和宿主应用的链路自动接续。

## 架构：遥测从哪里来

先定位：SDK 的观测架构继承了进程模型篇的拓扑。SDK 不产生任何遥测，它只做一件事，把你设置的遥测环境变量传给子进程。真正埋点的是引擎（Claude Code 的 CLI 内核），它把数据用 OTLP 协议直接发到你的收集器。数据不过 SDK 的手，不进你的消息流。

这个架构的三个推论。其一，标准协议：OTLP 是 OpenTelemetry 的通用协议，任何兼容的后端（自建收集器、托管平台）都能接，你不需要为 agent 单独建观测体系。其二，配置走环境变量，环境变量又遵循配置篇的规则（TS 替换语义要展开继承，别把遥测配置丢了）。其三，stdout 是 SDK 的消息通道，遥测导出别配成控制台输出，用 OTLP 网络导出。

导出失败默认静默（观测系统自己挂了不能影响业务，这个默认合理），排障遥测本身时打开专门的环境变量让导出错误打到 stderr，从 SDK 的 stderr 回调里读。

## 三类信号与开关

总开关一个，分信号开关三个。指标：token 数、成本、会话数、代码行数、工具决定，按分钟级间隔批量导出，适合接监控大盘和告警。日志事件：用户提示、接口请求与错误、工具结果，按事件粒度导出，适合接日志分析和 SIEM。链路（标记测试版）：带额外开关，按秒级导出，适合接链路追踪系统做性能分析。

三个信号的默认导出间隔不同（指标六十秒、链路和日志五秒），短任务场景要显式调低，否则任务结束了批次还没攒够，遥测迟到或缺席。

## 链路：agent 的解剖图

链路信号的骨架是一棵 span 树，四个层级。交互层：agent 循环的一轮一个 span，任务是几十个轮次的链。模型请求层：每次模型 API 调用一个 span，带模型、延迟、token 数，一轮一次。工具层：每次工具调用一个 span，下面还有两个子形态：被拦下等批准的时间和真正执行的时间，审批等待在链路图里现出原形（审批回调慢不慢、一次任务等了多少次批准，一眼看到）。钩子层：钩子执行也有 span。

子代理的 span 嵌在父会话的工具 span 下，委派结构在 trace 图上就是一棵真实的树。成本篇的归因问题在这里有了可视化答案：打开 trace，哪个子代理在哪次委派里花了最长的模型请求，图自己说话。

更有价值的是**链路接续**：W3C 的链路上下文自动传播。你的应用（Web 服务）处理请求时已经有了一条 trace，SDK 会话在处理中启动，agent 的 trace 自动作为你应用 trace 的子节点接上。用户抱怨"这个功能慢"，你打开这条请求的 trace，从 Web 处理到 agent 的每一轮到每次工具执行，一条链看穿。你给的链路上下文环境变量显式设置会覆盖自动注入，引擎转发给命令执行的上下文也保留，跨进程的因果不断线。

## 打标：让遥测可归因

两个资源属性变量负责身份：服务名（默认引擎名，改成你的应用名）和资源属性（任意键值对）。实践上的关键是给每次会话打业务标：用户标识、租户标识、环境、应用版本。打进资源属性后，指标和事件天然带着这些维度，成本归因、租户配额、按用户的审计轨迹全部免费获得。

会话标识默认不进遥测（有开关控制），多租户场景权衡：带会话标识可精确回溯，不带则聚合分析更干净，按合规要求选。

## 内容级记录：三级显式打开

默认的遥测是纯结构化：有工具名、有 token 数、有延迟，**没有任何对话内容**。这个默认是隐私和安全的及格线，出事故也泄露不了内容。

内容记录分三级显式打开，每级独立开关。第一级：用户提示文本。第二级：工具输入细节（路径、命令、模式）加真实的代理、技能、MCP 服务器名（默认这些名字会被匿名化）。第三级：工具输出内容（文件内容、命令输出、抓取结果），超长截断（上限可调）。

第四级更猛：原始 API 请求响应体，完整 JSON 落日志，内嵌截断或写文件两种模式，思考内容自动脱敏。这是排障的最后手段（系统提示篇提过"看模型实际收到了什么"的暗门，就是它），也是数据暴露面最大的一级。

打开任何一级前过一遍数据分级：提示和输出里有什么敏感内容、落到哪个后端、保留多久。内容级遥测的日志库应当按生产数据处理，权限和保留期与你的对话数据同等级。

## 落地：最小可用到全量

最小可用配置：总开关加指标导出，接一个本地或共用的 OTel 收集器，大盘上先看三张图（会话成本分布、工具决定比例、按服务的 token 趋势）。这一步一小时能做完，收益立竿见影：成本篇的画像数据从 guess 变 measure。

第二档加日志事件，接 SIEM 或日志库，工具调用流水成为安全审计的数据源（配合权限篇的审计模式，钩子记业务语义、遥测记技术事实，两层互补）。

第三档上链路，排障和性能分析升级。短任务记得调导出间隔。

收集器的建议：本地开发跑一个单实例 OTel 收集器（官方明确建议，比控制台导出有用得多），生产复用你现有的观测后端。

## 权衡与局限

遥测的代价三块。性能：导出是后台批量，常态开销小，但原始体级别的内容记录有真实的 IO 和体积成本，别默认开。数据治理：内容级记录把对话数据复制进了观测系统，保留期、访问控制、合规审查范围都要相应扩展。信号本身的成熟度：链路标记为测试版，span 结构可能随版本演化，大盘和告警规则别过度绑定具体 span 名，留一层别名映射。

还有一个观测哲学的提醒：遥测给你的是引擎视角的真相（它跑了多少轮、调了什么工具、花了多少），它不知道你的业务真相（任务完成质量、用户是否满意）。两个视角要拼起来：业务指标记在你的应用里，和遥测按会话标识关联。只有技术遥测的监控，看得见 agent 在跑，看不见 agent 跑得好不好。

## 大盘三张图的具体设计

第一档落地承诺交付三张图，具体设计写下来，照抄可用。

第一张，成本分布图。数据源：指标信号的成本指标，按服务名和你打的业务标聚合。图体是会话成本的直方图加中位数和九五分位参考线。看什么：分布的形状比均值重要。单峰集中在低位是健康；双峰（一堆便宜会话加一小撮天价会话）时，贵的那撮单独拉出来看，通常是特定任务类型或特定用户模式，值得单独优化或定价。告警挂在九五分位的突增上，别挂均值上（均值被大数熨平，尾部失控看不见）。

第二张，工具决定比例图。数据源：工具决定类指标（放行、拒绝、等待各计一次）。图体是堆叠比例的时间序列。看什么：拒绝和等待占比的变化趋势。拒绝率稳步上升说明权限规则和实际任务在漂移（任务在试越来越危险的操作，或规则该更新了）；等待占比高说明审批流是吞吐瓶颈，配合链路信号的审批等待时长定位是流程慢还是该加白名单。

第三张，token 与缓存健康图。数据源：token 类指标，三个科目（普通输入、缓存写入、缓存读取）分列。图体是每会话 token 的构成堆叠加缓存读取占比的折线。看什么：缓存占比折线跌破五成就是优化信号（检查系统提示是否漂移、会话是否过长、前缀结构是否稳定），这张图直接连着成本篇的优化推演。

三张图的共同设计原则：维度用你打的标（用户、租户、环境），时间粒度小时级，告警宁少勿多（观测系统的告警疲劳第一周就会毁掉它）。三张图稳跑一个月后再扩面板，先窄后宽。

## 接入遥测时的疑问

**已有 Prometheus 加 Grafana 的栈，怎么接？** OTel 收集器一路配两个导出器：指标转 Prometheus 格式给现有栈，事件走日志管道，链路给支持的追踪后端。收集器的多导出是设计好的能力，不用改 agent 侧任何东西。

**遥测数据里能看到对话内容吗？** 默认完全看不到，纯结构化。打开了内容级开关才有，且分级独立。给安全团队的说法可以是准确的：默认配置下观测系统不含任何用户数据。

**导出的量级多大，存得起吗？** 纯结构化模式下每会话的量级是几 KB 到几十 KB（轮数乘事件大小），三千会话一天也就百 MB 级。内容级打开后乘十到百倍，原始体级别再乘。容量规划按开关档位分别估。

**trace 接续在生产里可靠吗？** 自动注入要求你的应用本身有链路上下文（你自己得先有 trace）。没有的话 agent 的 trace 是孤儿 trace，依然完整可用，只是接不到请求链上。先给自己应用上链路，再谈接续。

**短任务（几十秒）的遥测会丢吗？** 默认导出间隔（指标六十秒）会迟到但一般不丢（批量攒着）。极端短命进程（函数计算几秒退出）要调低间隔或确认关停前冲刷，这是配置项存在的原因。

## 遥测词汇表：排障时对得上话

接了后端之后，团队要能读懂这些信号名。四组高频词汇，各自回答一个问题。

轮次组：交互层 span（一轮的容器）、模型请求 span（一次模型调用，带延迟和 token）。看"这轮卡在哪"：轮的长短分解到模型请求和工具执行，慢在哪个环节一目了然。

工具组：工具 span（一次调用）、等待子形态（拦下等批准）、执行子形态（真跑）、阻塞事件。看"工具为什么慢"：等待长是审批流问题，执行长是工具本身问题，两个答案通向完全不同的修复。

会话组：会话数指标、会话标识属性（默认不带，开关控制）、镜像错误事件（存储适配器篇的老朋友，遥测里也有它）。看"系统今天干了多少活、有没有丢数据"。

模型组：模型请求里的模型属性、token 指标的科目拆分、成本指标的价目来源标注。看"钱和 token 的结构"，成本篇的四科目解剖在这里有数据源。

词汇表的价值在协作：值班的人看面板说"工具的等待子形态飙了"，团队知道这是审批流的事故不是引擎的事故。观测系统上线后的第一周，值得把这张表贴进值班手册。

## 遥测自身的排障

观测系统自己也会坏，三个高频故障与修法。

面板上什么都没有时，按顺序查：总开关开了吗（环境变量真的传进子进程了吗，TS 替换语义的经典丢法）；收集器收到包了吗（收集器自身的接收指标）；导出错了被吞了吗（开诊断变量看 stderr）。九成停在没有之一。

指标有但事件没有（或反过来），是分信号开关各自独立导致的，检查漏开的那一个。这是配置面碎的正常代价，用配置模板统一管理开关组合，别每次手拼。

短任务的数据迟到或缺席，多半是导出间隔大于任务寿命，批量攒的数据在进程退出时没冲刷。两个修法：调低间隔（有导出开销的代价），或在任务结束点显式等一个导出周期再关进程。函数计算形态的部署必须处理这个，不然你只观测得到长任务。

第四个隐性故障也值得知道：版本升级后 span 结构变了，依赖具体 span 名的告警静默失效。前文说过留别名映射层，这里补一句检测法：告警规则本身加存活监控（一条恒真的测试告警，它不响了说明整条管道断了），观测系统的空白要被观测到。

容器化部署里还有一个更隐蔽的丢法：镜像或编排模板没把遥测那几个环境变量带进去，症状是本地全都有、上了容器全没有。部署清单里把观测变量和业务变量放在一起过，把它当部署配置的一部分管理，而不是排障时才想起来的孤项。CI 里再跑一个最小会话加一条断言（指标确实到达收集器），环境漂移在上线前就会被拦住。

最后一条团队层面的建议：遥测上线时给值班同事一小时导读（词汇表加大盘走读），比让他们自己摸索一周划算。观测系统最大的失败模式不是坏掉，是数据都在、没人会看、出了事还是靠猜。人的那一层和管道那一层同样要接通。

## 关键要点

- 架构：SDK 只传环境变量，引擎经 OTLP 直发你的收集器；stdout 被消息流占用，遥测走网络导出。
- 三信号：指标看大盘、事件看审计与 SIEM、链路看性能；span 四层含审批等待，子代理嵌套，与应用 trace 自动接续。
- 打标是归因的地基：服务名加资源属性带用户租户维度，成本归因和配额免费获得。
- 内容记录三级加原始体第四级，全部显式打开；默认纯结构化零内容；打开前做数据分级。
- 落地三档：指标起步、事件进审计、链路进排障；短任务调导出间隔；业务真相要自己记再关联。
