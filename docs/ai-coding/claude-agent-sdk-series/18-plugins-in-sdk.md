# Plugins 在 SDK 里：把 agent 的扩展打包分发

> 更新日期：2026/10

**TL;DR：** Plugin 是扩展的打包形态：一个目录里同时装技能、子代理、钩子和 MCP 服务器，SDK 会话用一个 plugins 选项整包加载。它解决的是"四件套散落四处无法整体版本化"的问题，把一个 agent 产品需要的全部扩展收进一个可分发单元。SDK 侧只认本地路径加载， marketplace 不直接支持；加载失败静默跳过，验证必须看初始化消息。

## 为什么需要打包形态

前几篇建立的扩展四件套（技能、子代理、钩子、MCP 配置）各自独立存放：技能在技能目录、子代理在 agents 目录、钩子在设置文件、MCP 在各自的配置里。做一个完整的 agent 产品（比如"代码审查助手"），要动四处地方，版本对应关系只存在于你的脑子里：这个技能是 v2 的，那个钩子还是 v1 的，装到客户环境时四处复制，漏一处就是静默残废。

Plugin 把四件套收进一个目录树：技能子目录、子代理子目录、钩子配置、MCP 配置，加上一份可选的清单文件。整包版本化、整包分发、整包启用。从"配置的集合"升级为"产品的组件"，这就是打包形态的价值。

贯穿案例：把前面几篇攒的东西打包。代码审查助手 = 审查技能 + 专属审查员子代理 + 敏感文件防护钩子 + 代码托管 MCP 服务器。四个组件散装要动四处，打包后一个目录加一行选项。

## SDK 侧的加载方式

选项里传插件列表，每个条目带类型和路径。类型只有一种合法值：本地。这是 SDK 侧的关键限制：**不支持从 marketplace 或远程仓库直接加载**，官方的操作指引直白，先下载到本地，给本地目录路径。路径相对时按会话的工作目录解析，指向插件的根目录（各组件目录的父级）。

这个限制的合理性想想就通：SDK 会话是你的程序的一部分，插件来源理应受你的部署管道控制（下载、扫描、签名、版本钉住），而不是运行时从任意远端拉。CLI 用户侧的 marketplace 体验和 SDK 侧的部署纪律，是两种场景的两种正确答案。

CLI 装过的插件可以复用：把安装路径传给 SDK 会话即可，安装目录下找。团队里"CLI 先试用、SDK 产品化"的路径是通的。

## 验证：静默跳过逼出来的纪律

加载失败不抛异常：路径不存在的插件被静默跳过，会话照常起。这个设计对容错友好（一个坏插件不打死整个产品），对排障残忍（少了一半能力你可能很久才发现）。

纪律因此是硬要求：会话启动后检查初始化系统消息。三处要看：plugins 列表里有没有你的插件（名字对不对），skills 和命令列表里有没有带命名空间的条目（形如 插件名：技能名，命名空间防止不同插件的同名组件互撞），plugin_errors 字段有没有内容（加载失败的原因在这里）。

把这段检查写进启动自检：预期加载 N 个插件，实际少于 N 就告警。五行的防御代码，省掉的是"功能怎么时有时无"的幽灵排障。

路径的两个小坑顺手记下：波浪号开头的路径不展开（老习惯踩坑高发区），写绝对路径或相对路径；清单文件是可选的，没有它按目录布局自动发现组件，有它则显式声明，产品化建议带上（显式清单比自动发现可审计）。

## 打包一个插件的实践

目录结构照官方约定摆：组件各归各的子目录，命令目录是旧位置（平面文件），新的技能目录结构（每技能一个目录）是推荐形态。给贯穿案例排目录：审查技能进技能目录，审查员定义进子代理目录，钩子配置进钩子文件，MCP 服务器配置进 MCP 配置文件。

三条实践判断。清单要显式写：声明组件版本和入口，升级和审计都有据可查。命令旧结构别再用：新技能结构是正统，旧的留着兼容。版本策略用整体版本：插件目录打 git 标签或塞进容器镜像标签，不追求内部组件各自版本，用户感知的是"插件 v1.2"，不是"技能 v3 加钩子 v1"。

分发渠道按受众选：内部团队用 git 仓库（克隆即得，升级拉取）；产品化用制品库或镜像（随应用版本走，插件版本和应用版本绑定）；不做运行时远程拉取（前面讲过的部署纪律）。

## 插件与四件套裸配的选择

什么时候打包，什么时候散装？判据是复用与版本边界。单会话一次性配置（临时加个技能试效果），散装快。一个要分发给多个会话、多个环境、多个人用的扩展集合，打包。一个要整体升级回滚的产品组件，打包。组件之间存在强耦合（钩子依赖某个 MCP 服务器存在），打包（散装时漏装依赖组件就是静默残废）。

打包的收益在于把"四处配置的对应关系"从人的记忆转移到目录结构里。凡是这个对应关系开始值钱的地方，就值得打包。

插件也改变扩展的信任模型：评估一个插件 = 评估四类组件的合集。技能注入指令、钩子执行代码、MCP 引入外部调用、子代理定义行为，四类风险打包在一起。装第三方插件前把这四样都过一遍，来源不明的插件按不可信输入处理。SDK 侧"本地路径加载"的限制客观上给了一道闸：所有插件都经过你的部署管道，审查有固定的落点。

## 权衡与局限

插件层是纯组织层，不提供新的运行时能力：插件里的技能和裸放的技能在会话里行为无差别，差别全在工程管理侧（版本、分发、命名空间）。为打包而打包没有意义，判据还是上一节的复用与版本边界。

局限三条。marketplace 不支持意味着版本更新靠你的管道手工（或 CI）完成，没有自动更新通道，这对生产是优点（变更可控）对尝鲜是缺点。插件粒度的启用禁用粒度粗：SDK 选项是整包加载，想"这个会话只要插件里的技能不要钩子"做不到，要么改插件要么裸配那一个组件。跨插件冲突（两个插件同命名空间的同名组件）的处理靠命名空间隔离，但语义冲突（两个技能指导矛盾的操作）没有机制层防御，集成测试里要覆盖。

## 打包实战：从散装到整包的完整迁移

把贯穿案例的迁移过程完整走一遍，每个坑都有真实位置。

第一步，盘点散装资产。现状：审查技能在仓库的技能目录、审查员定义在 agents 目录、防护钩子写在设置文件、代码托管服务器配置在 MCP 配置里。四个位置、三种格式、零个版本标记。盘点的产出是一张资产清单，每行记：组件、位置、被哪些会话用、最近一次改动时间。这张清单本身就是收益，多数团队第一次盘点都会发现"还在被引用的三个月没人改的配置"。

第二步，落目录。建插件根目录，四个组件各归子目录。搬迁不是复制粘贴：钩子从设置文件里抠出来时，注意它原来的作用域（项目级还是用户级），搬进插件后作用域变成"加载了这个插件的会话"，语义等价但有边界，原来全机器生效的用户级钩子，插件化后只有装插件的会话生效，这是收窄不是等价，要在清单里标注。MCP 配置同理，从项目配置挪进插件后，它跟着插件版本走，升级插件等于升级服务器配置，这正是想要的。

第三步，写清单文件。显式列出四个组件和插件元数据。清单的价值在装包校验：加载时初始化消息里回报的组件数和清单对得上，说明搬全了；对不上立刻知道缺了哪个。

第四步，装包验证。SDK 会话加载插件路径，启动自检三查（插件列表、命名空间条目、错误字段）。然后跑一次功能回归：触发审查技能、点名审查员、验证钩子拦截一次敏感写入、调一次 MCP 工具。四件套各验一遍，插件才算迁移完成。

第五步，清旧。散装的原件删除或移出加载路径。这步最容易被拖延，留着的后果是双份定义并存：程序定义和文件定义的优先规则在组件类型上不一致，行为取决于哪份被哪条路径加载，排查起来极其费劲。迁移的最后一公里是清理，不是"先留着以后再删"。

整个过程半天到一天，产出物是一个可版本化、可分发、可整包升级的组件。多数团队做完第一个插件后的反应是相同的：早该打包了。

## 插件加载与升级的疑问

**插件和直接改配置目录，性能有差别吗？** 没有。插件是加载期的组织形式，进会话后组件和散装的行为、开销完全一致。成本全在工程管理侧，不在运行时。

**两个插件都定义了同名技能会怎样？** 命名空间隔离了它们（插件名前缀不同），两份都加载，各自可调用。语义冲突（内容矛盾的技能）没有机制层报错，靠集成测试发现。

**能让用户在运行时自己装插件吗？** SDK 侧没有这个通道（只认本地路径）。产品化做法：你的应用提供插件管理界面，背后是下载到本地目录加重启会话，把 marketplace 的体验自己做在应用层。

**插件里的钩子在所有会话生效吗？** 只在加载了该插件的会话生效。这正是它的价值：按会话装配行为，测试会话加载测试插件，生产会话不装。

**升级插件的正确姿势？** 新版本落到新目录或同目录新提交，会话重启后加载新版。进行中的会话不热更新（组件已进会话）。生产上插件版本和应用版本绑定发布，回滚一起回滚。

## 插件资产的组织策略

插件做多了之后的问题从"怎么打包"变成"怎么管理"。三个组织策略。

命名与编号策略：插件名带领域前缀和稳定语义（review-assistant、deploy-guard），不带版本号（版本靠发布通道表达，名字里带 v2 的插件注定在 v3 时尴尬）。命名空间一旦被用户引用（直发语法里的插件名前缀），就是公开接口，改名是破坏性变更。

发布通道策略：内部插件走两条通道。稳定通道给生产会话用，变更走评审有冷却期（提案到生效至少一周）；快速通道给试验和内部尝鲜，随便改。会话按用途选通道加载，生产永远不直接挂快速通道。这个分法是包管理世界的老纪律，在 agent 插件上同样成立。

所有权策略：每个插件有一个 owner（人或团队），写进清单文件。无主插件的处理规则事先说好：三个月无响应的移出稳定通道，进待认领区。插件会腐化（引擎行为变了、它包的 MCP 服务器改协议了），无主腐化比没有插件更糟。

三条策略指向同一个治理问题：**当插件从"我的方便"变成"大家依赖"，变更的责任怎么落实**。答案和任何共享资产一样：命名稳定、通道分级、责任到人。

## 四类组件的风险分级速查

打包分发前按这张表过一遍组件的风险面。

技能组件：风险是提示注入面（技能内容直接成为模型指令）。审查点：来源可信、内容评审、无敏感信息硬编码。风险等级中，因为技能只影响行为倾向不直接执行。

子代理组件：风险是越权面（它可能带了自己的工具配置）。审查点：工具集最小化、模式继承关系明确。等级中高，子代理配了宽工具就是打包了一个权限漏洞。

钩子组件：风险是执行面（钩子是你进程里的代码，或它声明的 shell 命令）。审查点：钩子代码全文审读、超时与异常处理齐备、无外部数据源拉取。等级高，钩子能改参数能拦截，是组件里的实权部门。

MCP 组件：风险是外联面（引入外部服务器与凭据）。审查点：服务器归属、认证方式、返回体积特征、超时配置。等级高，它把会话的边界扩展到了第三方系统。

全插件的风险等于四类之和，评估时别只看它宣传的功能。一个"很棒的小技能"插件如果顺手带了钩子和 MCP，它的风险面就不是小技能的量级。清单文件把组件显式化，正是为了让这个加法可计算。

这张表的用法也顺便说清：它是给装插件的人看的，不是给插件作者看的。装包前按组件逐行过一遍，等于把"信任这个插件"拆成四个可以分别核实的判断，比整体印象靠谱。粒度的限制同样摆在这里：SDK 选项是整包加载，做不到"只要技能不要钩子"，确实只要其中一件时，要么给插件出裁剪版，要么把那一件拆出来裸配。

给评估流程一个收尾动作：装任何插件前跑一次冒烟会话并留存初始化消息，与装后的对比。插件声明它带来什么和它实际带来什么，两份记录对得上才算过审。这个动作五分钟，拦下的是"插件里夹带私货组件"这类供应链小事故，agent 系统的供应链审查从这个习惯开始建立。

## 关键要点

- Plugin 是四件套的打包单元：技能、子代理、钩子、MCP 服务器收进一个目录，整体版本化分发。
- SDK 只认本地路径加载，marketplace 不直连：插件过你的部署管道，下载扫描钉版本后再给路径。
- 加载失败静默跳过：启动自检查初始化消息的插件列表、命名空间条目和 plugin_errors，少装即告警。
- 路径不展开波浪号；清单建议显式；版本用整体版本，分发渠道 git 或镜像。
- 打包判据是复用与版本边界：多处部署、整体升级、组件强耦合时打包；插件是信任合集，按四类风险一起审。
