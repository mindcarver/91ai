# 外部 MCP：把第三方世界接进会话

> 更新日期：2026/10

**TL;DR：** 外部 MCP 服务器让 agent 获得你不想自己写的能力：GitHub、数据库、内部网关。SDK 里接入有两条路：代码里的服务器配置选项和项目根的 .mcp.json 文件。真正的工程量在接入之后：连接时序决定首轮延迟，认证方式按传输类型分三套，输出超限会悄悄落盘，连接失败不会抛异常而要看状态。这篇按一条连接的完整生命周期讲。

## 两条接入路径

代码路径把服务器配置作为选项传给会话，配置跟着你的程序走，适合产品化部署：服务器列表是代码的一部分，随版本管理。文件路径在项目根放一个 .mcp.json，启用项目配置来源时自动加载，适合团队仓库共享：配置跟着仓库走，clone 即得。

两条路径不互斥，常见组合是文件管团队共享的服务器、代码管产品运行时的服务器。要留意前面继承篇讲过的联动：显式设置了配置来源列表却没包含项目来源时，.mcp.json 根本不会加载，这是"文件明明在那怎么没生效"的标准答案。

传输类型三种。本地进程型（stdio）给一个命令，引擎负责把服务器进程拉起来，适合本机工具。HTTP 型给一个 URL，连远程服务。SSE 型是 HTTP 的旧协议兄弟，老服务器还在用。一个命名细节：代码里类型字段只认 http 这个值，JSON 文件里可以写它的别名，跨两种路径抄配置时这里会咬人，同一份配置换个位置就报类型不认识，是新手接入的高频工单。

## 命名与授权

外部工具进会话后的名字是三段式：mcp__ 服务器名 工具名。这个名字就是它的身份，授权、审计、日志里都用它。

授权的推荐姿势在工具篇讲过原则，这里落到 MCP 语境：允许列表里写完整工具名或服务器级通配符（一整台服务器的工具一次放行），避免用宽权限模式兜底。宽模式对 MCP 工具的覆盖语义不精确，要么盖不住要么盖过头。

通配符也有讲究。整服务器通配省事，但等于把那台服务器上现在和将来的所有工具全部预授权，服务器升级加了个危险工具，你的授权面跟着变大。对不受你控制的服务器，逐工具授权更稳；受控的内部服务器，通配符的效率值得要。

## 认证的三套打法

认证跟着传输类型走。

本地进程型最直接：凭据放在服务器进程的环境变量里传进去。JSON 文件还支持占位符展开，写 ${API_KEY} 运行时替换，避免把密钥写进版本库。

HTTP 型用请求头，放授权令牌。占位符展开同样适用。

OAuth 是最特殊的一套，语义必须记住：**SDK 不会替你跑交互式 OAuth 流程，也不会弹浏览器**。agent 连一台需要 OAuth 的服务器，没有存好的令牌时，会话照常继续，那台服务器的状态标记为 needs-auth，它上面的工具不可用。正确做法是你的应用自己完成 OAuth（你的登录页、你的令牌管理），把拿到的访问令牌放进请求头传给 SDK。轮询服务器状态接口确认从 needs-auth 变成就绪。换句话说，SDK 把"运维认证"的责任划给了宿主应用，agent 只管用。

这个划分在产品里反而是优势：令牌的刷新、多租户隔离、权限范围控制都在你的应用层，用你熟悉的体系，不用学引擎的。

## 连接时序：首轮延迟从哪来

服务器连接是异步的，和会话启动并行。时序规则：没有缓存工具列表的服务器会让首轮任务等待连接完成，默认最多等三十秒（环境变量可调）；有缓存的工具列表的服务器不阻塞，首次真正调用工具时才要求连接就绪。

对产品的影响直接：首次冷启动接三台慢服务器，用户的第一句话可能等十几秒。缓解手段有一组环境变量：调整首轮等待上限、设成零跳过等待、把阻塞点前移到更早的启动阶段（上限五秒）。设计原则是让"连接慢"发生在用户看不见的地方。

状态语义有一组词汇要会读。初始化消息里每台服务器带状态：pending 表示还在连，**不是失败**，新手最常误杀的就是它；failed 表示连不上或重试耗尽；needs-auth 前面讲过。会话中途远程服务器也可能掉回 pending（重连中），重试五次仍失败才判 failed。手动重连有专门接口。诊断口诀：看状态，别看异常，**MCP 连接失败不会从 query 抛出**，静默的服务器只能在状态里发现。

## 输出超限与超时

工具返回的内容有上限：文本结果超过两万五千 token（或五万个字符，除非服务器自己声明了别的上限）时，引擎把内容写进文件，工具结果替换成一条指明文件路径的错误。这个设计是保上下文的：一次五十万 token 的日志查询会把会话直接撑爆，落盘后模型至少还能去读文件的关键部分。上限可通过环境变量调整。

两类超时分开管：连接超时管握手，工具超时管一次调用的执行。慢查询型服务器（大数据、爬虫）两边的值都要按业务重设，默认值是为轻量工具准备的。

## schema 兼容性的暗坑

TS 侧有一个静默失败模式：工具定义的 schema 无法转换成 JSON Schema 时，这个工具被悄悄从列表里剔除，只留一个警告码。也就是说你的服务器声明十个工具，会话里只见九个，没有异常没有报错。老版本 SDK 更狠，一个坏 schema 毁掉整台服务器的工具列表，升级后行为变化（坏一个剔一个）本身就是迁移陷阱。

防御做法：接入新服务器后，第一步检查初始化消息里的工具数量与服务器声明是否一致；对自研服务器，schema 用类型系统生成而不是手写，从源头杜绝不合法 schema。

## 设计一个多服务器工具面

真实系统通常连多台服务器，设计要点三条。

按域分组。每台服务器是一个命名空间，命名时按业务域切（代码托管、数据库、监控），工具名自然带上域前缀，模型的选择准确率受益于清晰的名字空间。

连接分级。启动必须的（核心业务工具）和可选的（增强能力）分开，可选的接受 needs-auth 或 pending 状态继续跑，必须的连不上就快速失败，别让会话带着残废工具面空转。

工具数量克制。每台服务器只暴露 agent 真正需要的工具，服务器自带五十个工具就全接进来是浪费：即使有工具搜索的按需加载，工具发现本身也在消耗轮次。让服务器管理员裁剪，或者你在网关层过滤。

## 权衡与局限

外部 MCP 的代价是控制权的外移。服务器的版本、行为、安全都归服务器管理者，你的 agent 依赖它的稳定性。生产系统接第三方服务器前要过一遍问询：谁维护、变更通知机制、限流策略、返回内容的体积特征。没有答案的第三方服务器，宁可包一层自己控制的网关。

进程模型的开销也要计入：每台 stdio 服务器是一个额外子进程，HTTP 服务器是网络依赖，会话的故障面从"一个引擎进程"扩展成"引擎加 N 个依赖"。监控里把 MCP 连接状态纳入健康检查，别等用户报"agent 说查不到数据"才发现服务器挂了一小时。

## 接入一台新服务器的完整流程

把零散规则串成标准流程，接入新服务器照单走。

第一步，谈判期：向服务器管理员要四样东西。传输类型和端点（本地命令还是 HTTP 地址）；工具清单及每个工具的用途一句话（后面配权限和检查工具数都用）；认证方式（环境变量、静态令牌还是 OAuth）；体积特征（典型返回多大，有没有分页参数）。第四样最常被漏要，接进来当天发现单次返回八万 token 就晚了。

第二步，本地验证：先在最小会话里加载它，工具列表设空（纯隔离环境），看初始化消息。核对三处：状态字段就绪、工具数量与管理员清单一致（TS 的 schema 静默剔除陷阱在这里拦截）、每个工具的名字符合三段式预期。

第三步，授权面设计：按工具用途分级。只读查询类进允许列表（按工具名精确授权），写入类走审批回调或窄作用域，危险类直接禁用列表。第三方服务器不做整服务器通配（前文讲过的升级风险）。

第四步，时序调优：看首轮延迟。冷启动被这台服务器拖慢的话，调首轮等待上限或让它走缓存路径；工具面大就确认工具搜索对它生效。

第五步，监控接入：把这台服务器的连接状态进健康检查，工具调用的成功率和时延进指标（观测篇的打标）。生产上第三方的故障要变成你的告警，而不是用户先发现。

五步流程半天走完，产出是接入档案一份（管理员答复、授权决定、监控面板链接），下次审计或换版有据可查。

## 接入之后的排障疑问

**服务器连不上，第一反应查什么？** 顺序：状态字段是什么（pending 等等看，failed 继续查）；网络可达吗（容器里 curl 端点）；认证过了吗（needs-auth 就是令牌问题）；本地 stdio 型的话命令在容器里存在吗。四步覆盖九成连接工单。

**needs-auth 状态下会话还能用吗？** 能，这台服务器的工具不可用，其余一切正常。产品上把这个状态翻译成"GitHub 连接已过期，请重新授权"并给入口，别让它沉默，用户看得懂的状态才不会变成工单。

**两台服务器有同名工具怎么办？** 不会撞，三段式命名天然隔离。要担心的是语义撞车：两台都有"查工单"，模型可能混用。描述里写清各自边界，或在授权面上只留一台的。

**.mcp.json 和代码配置各放什么？** 文件放团队共享、与仓库版本一致的服务器；代码放产品运行时、按环境变化的服务器。判据是"这个配置的变更该走 git 评审还是走应用发布"。

**怎么测服务器的故障表现？** 接入后在测试环境断网或停服跑一轮任务，看 agent 行为：好的表现是工具报错后换路或如实上报，坏的表现是反复重试烧预算。故障演练是接入流程的隐藏第六步。

## 服务器状态词汇表与会话关系图

状态词汇的完整语义表，值班时对号入座。

就绪：连上了，工具可用。启动慢的服务器从 pending 转过来是正常迁移，无需动作。pending：连接中，不是故障。启动期出现几秒到几十秒都正常，会话中途出现意味着掉线重连中，持续超过重试上限（五次）转 failed。failed：连接失败或重试耗尽，这台服务器的工具不可用，需要人工介入（查网络、查服务端、手动重连）。needs-auth：认证缺失或过期，会话不受影响，但这条能力通道关闭，走你的应用层重新完成认证再传令牌。

四个状态与会话的关系画成一张图（文字版）：

```
会话启动
   │
   ├── 服务器A ──连接成功──→ 就绪 ──────────────→ 工具可用
   ├── 服务器B ──连接中(pending) ──超时/重试──→ 就绪 或 failed
   └── 服务器C ──认证挑战──→ needs-auth ──应用层补令牌──→ 就绪
                                   │
会话运行中：任何就绪服务器 ──掉线──→ pending ──五次重试失败──→ failed
                                                    │
                                        reconnectMcpServer 手动拉回
```

图里三条容易被忽略的边：中途掉线会静默发生（会话照常跑，工具调用时才发现）；手动重连接口是 failed 之后的人工出口；needs-auth 的恢复通道在应用层不在引擎层。监控把 pending 时长和 failed 事件挂上告警，这张图的动态就有仪表可看了。有了告警，pending 挂一小时这种慢性病才能在用户感知之前被值班发现，而不是混在正常会话里静默存在。

最后一个容易低估的维度：MCP 引入的故障面要进你的值班手册。纯 SDK 会话的故障域是一个引擎进程，接了三台服务器后变成四进程加两条网络依赖，任何一个都可能半夜出事。值班手册里每个 MCP 条目三行：它是什么、坏了的现象（哪类工具报什么错）、应急动作（重连、绕过、下线）。接得越多，这三行的价值越高；等故障真的发生再临时翻文档拼凑处置方案，是值班体验里最糟的一种。

## 关键要点

- 两条接入路径：代码配置随程序走、.mcp.json 随仓库走；显式配置来源没含项目时文件不加载。
- 认证三套：stdio 走环境变量、HTTP 走请求头、OAuth 由宿主应用完成再把令牌传入；SDK 不弹浏览器，缺令牌的服务器标 needs-auth 继续。
- 连接时序：无缓存列表的服务器阻塞首轮最多三十秒；pending 不是失败；连接失败不抛异常，看状态字段。
- 输出超两万五千 token 落盘换路径；连接超时与工具超时分开调；慢服务器两边都重设。
- TS 的 schema 转换失败静默剔工具，接入后先数初始化消息里的工具数。
