# 配置加载全解：选项、文件与环境的三国志

> 更新日期：2026/10

**TL;DR：** SDK 会话的最终配置由三个来源合成：你传的选项对象、文件系统上的设置文件、进程环境变量。选项不是孤立参数，每个选项背后都有一条"和文件配置怎么互动"的规则：settings 选项能压过文件配置、环境变量选项在两门语言里语义不同、工作目录不能中途换。理解合成的次序，是"为什么这个配置没生效"类问题的总解法。

## 配置问题为什么难排

SDK 的配置面很宽：模型、权限、工具、系统提示、目录、环境、会话、钩子，每类都有选项、文件、环境变量三种写法。三种写法的关系不是简单的覆盖，各有专属语义。比如想改模型，选项里传模型是本次会话生效；想在文件里配是另一条路；想中途换模型又有专门的运行时方法，三种改法的生效范围完全不同，错用一层就会得到"改了没反应"的假象。

排障时人最常犯的错是只看自己写的那一层。代码里明明传了，没生效，因为另一个来源在更高处压住了它；或者反过来，某行为怪异，查了半天代码，其实是机器上的设置文件在起作用。这篇把合成规则一次讲完。

## 三个来源各自是什么

**选项对象**是显式的代码层配置：传给 query 的那组参数。它的特点是精确、随代码走、每次调用可以不同。工程上的定位：产品的意图声明，理论上你希望它就是全部配置。

**设置文件**是文件层配置：用户目录、项目目录、本地覆盖三处的 settings 文件加 CLAUDE.md 类规则文件。前面继承篇讲过它的加载由配置来源选项控制。它的特点是环境相关、随机器和仓库走。工程定位：环境的差异项（这台机器用代理、这个仓库有特别约定）。

**环境变量**是进程层配置：认证、云平台选择、各类行为开关。它的特点是最底层、影响引擎子进程本身。工程定位：部署基础设施的事（凭据、端点、平台选择）。

三者的重叠地带就是事故地带。同一件事在三层都有写法时，谁赢？逐个看高频案例。

## 高频配置的互动规则

先看模型。选项里传模型，本次会话钉住；不传，用引擎自己的解析链（它有自己的默认模型逻辑，可能被文件和环境变量影响）。还有回退模型的玩法：主模型挂了按列表降级，引擎每个用户轮都会重试主模型，所以故障后无需干预自动回到主力。一个校验细节：TS 里回退列表里写一个和主模型相同的项会直接启动报错，防呆设计。

环境变量选项是两门语言差异最大的地方，必须背下来：**TS 的环境选项是替换语义**，你传了什么，子进程的环境就是什么，连 PATH 和认证变量都不继承，所以要显式展开继承原环境再改；**Python 是合并语义**，你传的覆盖同名项，其余继承。同一个"给子进程加一个变量"的需求，两边的正确写法完全不同。这个差异没注意到，TS 侧最常见的症状是子进程找不到命令或没登录。

工作目录决定一大串东西：项目配置的加载位置、技能发现、会话文件存放。它是创建期属性，没有运行时修改接口，要换目录就开新会话。设计多目录操作时用追加目录选项（给文件访问扩权，不影响配置加载位置），而不是换目录。

设置文件还有一个内嵌替代：settings 选项让你直接以代码传设置内容（路径、内嵌 JSON、TS 还接受对象），它压过所有文件系统来源，只低于企业托管策略。这是"我要文件配置的能力但不要文件配置的不可控"的正解：多租户部署里每租户不同的设置，用这个选项程序化注入，彻底摆脱对宿主机文件系统的依赖。

运行时修改只存在于流式输入模式：换模型、换权限模式有专门方法。有一个狠细节：不带参数调用换模型方法，切到的是"默认模型"而不是"你选项里传的那个"，这个语义坑踩过一次就记住。换模型的代价是提示缓存作废（下一请求按新模型全价重算），频繁换模型就是频繁烧钱。

## 优先级的心智模型

把官方的合成次序翻译成一句人话：**托管策略大于选项里的设置注入，大于代码选项，大于文件配置，大于默认值；环境变量站在旁边各管各的领域**。

其中"托管策略永远第一"是企业安全的基石：组织统一下发的策略，任何层的配置都压不过它，这保证安全底线不被本地配置击穿。

两个具体提醒。文件配置不是死数据：它里面同样能写权限规则、钩子、模型偏好，加载进会话后和你的选项平权参与行为。所以排查"不明行为"时，三处设置文件是必查项，继承篇教过的配置来源清空是隔离实验手段。执行限制类选项（轮数、预算）只在选项层有效，文件里写不了，这两项天然是代码的地盘。

## 一个真实排障案例

把规则串进一个案例。症状：同事的机器上 agent 走的是公司代理，你的机器上直连，两份"完全相同"的代码。排查路径：第一层查环境变量（代理地址在环境里，谁的 shell 注入了什么，立刻分叉）；第二层查设置文件（用户目录的 settings 里有没有网络配置段）；第三层才是代码（两人的选项是否真的一致，git 提交历史）。

这个案例的教训是配置问题的通用解法：从引擎实际拿到的最终配置倒推，而不是从你写的配置正推。看最终配置的手段：初始化系统消息里带着会话生效的模型与配置元数据；会话存储的转录文件里记录着启动参数；debug 日志能看到子进程收到的完整环境。三件工具按"快、中、慢"排序选用，多数时候初始化消息那一件就够用，另外两件留给初始化信息不足以定位的深水区。

## 配置设计的产品化建议

做产品时配置策略要在三种形态里选边。

最紧的形态是"代码加环境"：选项管行为，环境管基础设施，文件层完全清空（配置来源设空）。行为完全确定，适合多租户和对外产品。代价是失去"用户在本机调一下"的灵活性，灵活性由你的产品配置系统接管。

中间形态是"代码加项目文件"：保留项目来源，团队仓库里的 .claude 配置生效，用户和本地来源关掉。内部工具常用，团队约定随仓库分发，个人环境不干扰。

最松的"三层全开"只适合个人工具，机器即配置。

无论哪种形态，把最终生效的配置在会话初始化时打一行摘要日志（模型、权限模式、加载的来源数），上线后"这行为哪来的"类问题的排查时间会砍掉一大半，值班同事也不用再靠猜。

## 权衡与局限

配置的三层结构是历史与生态的产物，不是优雅的设计，它带来的灵活性值得付出的前提是你真的在用这种灵活性。多数产品最终会把配置收敛到代码和环境两层，文件层只在"团队仓库自带约定"这个场景保留。收敛得越早，配置面的心智负担越小。

局限也要说：运行时修改面很窄（模型和权限模式两项），说明官方把"会话中途大改配置"视为反模式。需要频繁改配置的场景，正确架构是短会话加新配置，而不是长会话加运行时改配置。这和会话篇的"短会话加蒸馏"结论殊途同归。

## 会话启动前的配置检查清单

把合成规则压成一份上线前清单，逐项核对能消灭大半配置类工单。

身份类四项：模型显式指定了吗（不指定就接受引擎默认链的不确定性）；回退模型配了吗（长任务高可用的廉价保险）；努力档位选了吗（默认档对多数任务是浪费或不足）；认证走哪个通道（API key 直连还是云平台变量）。

行为类五项：权限模式明确写了吗（不写走默认模式，不同 SDK 版本的默认行为有过变化，显式声明最稳）；工具面是两层分开配的吗（可用性归工具列表，放行归允许列表，别混）；系统提示三形态选了哪个（裸、预设、预设加追加，默认裸常是事故）；配置来源列了吗（产品化场景显式列出要的，别依赖省略值）；追加目录需要吗（工作目录外的访问要逐个授权）。

环境类三项：环境变量选项的语言语义对了吗（TS 替换要展开继承，Python 合并）；遥测环境变量带进去了吗（观测篇的开关全走环境，TS 替换语义下最容易丢）；平台变量（代理、云通道）在目标部署环境里有吗。

每项核对过的产出是"这份会话配置的完整画像"，把它打进启动日志第一行。这份日志在三个月后某个"为什么当时的行为是这样"的考古里价值千金，而且它不依赖任何人的记忆。

## 配置对不上时的排查疑问

**两台机器行为不一样，先查什么？** 顺序固定：环境变量差异（printenv 对比）、三处设置文件差异（配置来源是否都关了）、SDK 版本（npm 或 pip 锁文件）。三步下来九成的行为差异能定位。

**配置来源全关了，为什么还有怪行为？** 四样不受开关管的东西在起作用（托管策略、全局配置文件、自动记忆、沙箱凭据），继承篇的清单逐项关。还不行就是代码选项本身，回到画像日志看实际生效值。

**settings 选项和直接传同名选项（比如模型）冲突吗？** 选项层优先。settings 注入的是"文件语义的配置"，代码选项是显式意图，显式赢。两边都配同一项本身就是配置异味，清掉一处，留下代码层的那份，意图最明确。

**运行时换模型后配置画像日志里的是哪个？** 画像是启动时的，运行时切换要自己补记（切换事件加新模型）。审计需求高的场景，模型切换也打日志，两行代码的事。

**多租户的每租户配置怎么组织？** 模板加差异：一份基础选项对象代码里定义，每租户的差异（工作目录、配置目录、settings 注入、配额）在工厂函数里合并。别把租户配置散在调用点，一个工厂集中管理，租户清单就是配置的唯一真源。

## 配置漂移的检测

配置不是配完就完了，它会漂移：依赖升级改了默认值、有人改了机器上的文件、环境的变量被运维平台"优化"了。漂移的检测三板斧。

第一板斧，配置画像的基线对比。启动日志里的配置画像（前文清单的产出）存进时序库，每次会话启动的画像与基线 diff：模型变了、来源数变了、工具数变了，都在 diff 里现形。漂移检测在会话层面是免费的（数据本来就在打），缺的只是对比这一步。

第二板斧，漂移测试会话。定时（每天一次）起一个标准测试会话，断言配置画像的关键字段与预期完全一致。它抓的是环境侧漂移：机器文件被改、环境变量丢失、托管策略更新。测试会话的断言集就是配置的活文档。

第三板斧，版本升级的配置评审。SDK 升级的 PR 里固定包含一节：这次升级是否改变任何默认行为（changelog 里搜默认、行为、removed）。有变化就更新基线和文档。把"升级必查默认值"写进升级模板，默认值漂移这个最阴险的漂移就被流程管住了。

三板斧的成本合计半小时搭起来，守住的是"三个月后行为和今天一致"这个听起来很低实际很奢侈的保证。

## 三来源对照表

| 想改的事 | 选项层 | 文件层 | 环境层 | 建议 |
| --- | --- | --- | --- | --- |
| 模型 | 本次会话钉住 | 默认模型链 | 平台通道 | 选项层，显式 |
| 权限模式 | 传参或运行时切换 | 规则文件 | 少数开关 | 选项层为主 |
| 工具面 | 两层列表 | 可写规则 | 开关类 | 选项层，产品核心 |
| 系统提示 | 三形态 | CLAUDE.md 并行通道 | 关闭类开关 | 选项层 |
| 认证 | 不在选项 | 不在文件 | 专属地盘 | 环境层 |
| 遥测 | 经环境传 | 少量 | 专属地盘 | 环境层 |
| 会话存储 | 适配器选项 | 无 | 重定位目录 | 选项层 |

表里"建议"列的规律：产品行为归选项层（代码即真相），基础设施归环境层（部署即真相），文件层只保留团队约定场景。三列并存的行（模型、权限、工具）是漂移高发区，这些行的配置方式要在团队里写成明文规范，谁写哪层一锤定音。

规范落地的一个组织技巧：把三层的分工写进代码评审清单（这个 PR 改了配置吗，改在哪层，那层是它的地盘吗）。配置漂移多数是善意的（某人在最顺手的那层解决了问题），评审清单把"顺手"变成"按规矩"，漂移的上游就关掉了。新人的配置 PR 有了可对照的规矩，评审也不再有"凭什么听你的"的争论。

## 关键要点

- 三来源：选项（代码意图）、设置文件（环境差异）、环境变量（基础设施）；重叠地带是事故地带。
- TS 环境选项替换语义要展开继承，Python 合并语义直接加；换模型无参调用切的是默认模型。
- settings 选项程序化注入设置内容，压过文件低于托管策略；工作目录创建期定死，扩权用追加目录。
- 排障从最终配置倒推：初始化消息、转录文件、debug 日志三件工具。
- 产品收敛配置层：对外产品清文件层，内部工具留项目层，个人工具才全开。
