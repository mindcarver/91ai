# 内置工具的控制与裁剪：划定 agent 的能力边界

> 更新日期：2026/10

**TL;DR：** 引擎自带几十个内置工具，从读写文件到联网搜索再到调度子代理。控制它们的心智模型是两层：可用性决定工具在不在 agent 的视野里，权限决定在视野里的工具要不要经过批准。两层各有自己的语法和优先级，混为一谈是配置事故的头号来源。这篇把两层讲清，给出三档裁剪配方和五个常见陷阱。

## 一个工具面设计的场景

贯穿案例：你在做一个面向三个团队的内部 agent 服务。法务团队要它只读代码回答合规问题，平台团队要它能改基础设施配置，安全团队要它能跑扫描命令但不能删任何东西。同一个引擎，三种截然不同的能力面。

这个场景里"给 agent 什么能力"不是玄学提示词，是精确的配置问题。解它需要先建立两层的概念。

## 两层控制：可用性与权限

第一层叫可用性，回答"agent 知不知道这个工具存在"。工具不在这层，模型根本看不到它，谈不上调用。控制手段是工具列表选项（列出要保留的）和禁用列表（列出要剔除的）。把内置工具全清空也做得到：传一个空工具列表，agent 眼里就只剩你的自定义工具和 MCP 工具。

第二层叫权限，回答"视野里的工具，哪些调用免批准"。控制手段是允许列表和权限模式。允许列表里的工具自动放行；没列的工具仍然可用，只是调用时走权限流程（弹审批回调或按模式处理）。

两层的区别用一个例子钉死：Bash 不在工具列表里，agent 想都想不到 shell；Bash 在工具列表但不在允许列表，agent 能发起 shell 调用，每次执行前等你批准。前者是看不见，后者是看得见但伸手要挂号。

优先级关系记三条。禁用列表赢面最大：一个工具同时出现在禁用和允许列表，禁用生效。允许列表只是预授权，不是唯一入口：没被允许的工具依然在视野里走流程。权限模式是全局底色，允许列表是在底色上开的局部通道。

官方文档对 MCP 工具给了一个明确建议值得抄录：用允许列表控制 MCP 工具，别用宽权限模式去覆盖。因为接受编辑类的模式并不自动放行 MCP 工具，而跳过全部权限的模式又宽得危险。精确的工具名授权是唯一既安全又不烦人的中间道路。

## 内置工具的地图

引擎的内置工具可以分成六族，每族对应一类能力。

文件族（读、编辑、写）是代码能力的基础，读是只读的，编辑和写是改状态的。搜索族（文件名匹配、内容搜索）负责在仓库里找东西，纯只读。执行族（shell 命令）是权力最大的一族，能跑任何命令，也就能做任何事，包括坏事故。网络族（网页搜索、网页抓取）给 agent 联网能力，适合资料调研型任务。发现族（工具搜索工具）是管工具的工具，在工具面很大时按需加载工具定义。编排族（子代理调度、技能调用、用户提问、任务清单）是 agent 管理自己工作方式的工具。

六族的风险等级天然分层：搜索族和文件族的读几乎无风险，文件族的写在可控范围，执行族是无上限的风险，网络族引入外部信息，编排族影响的是 agent 自身行为。裁剪工具面时按族思考，比按单个工具思考快得多。

## 作用域规则的语法

允许和禁用列表里可以写比工具名更精细的东西：作用域规则。给工具名挂上参数模式，就只匹配特定参数的调用。删文件命令配一个特定前缀模式，等于只放行删某种文件的调用，其他删操作照旧走审批。MCP 工具的作用域用通配符配整台服务器：某服务器的全部工具一次放行。

这套语法的设计意图是把权限从"按工具"细化到"按用途"。同一个 Bash，读日志的调用和改系统的调用风险不同，作用域规则让你放行前者扣住后者。写规则时的心态要像写防火墙规则：默认拒绝，按需开口，开口尽量窄。

## 执行语义：并发与串行

工具面还隐含一套执行策略，事件模型篇讲过结论，这里补上它对配置的反馈。只读工具的调用并发执行，改状态的工具串行执行，这是引擎内建的保护。对配置的影响在自定义工具上：你不标注，引擎不知道你的工具是否只读，默认按串行对待。想让自定义的查询类工具享受并发，给它标上只读提示，并保证提示诚实。

反过来利用串行也能做事：把有副作用的操作设计成独立工具而不标注只读，引擎的串行保护就成了你的并发安全网，省掉自己加锁。

## 三档裁剪配方

回到贯穿案例，三档配方对应三类信任级别。

情报档：工具列表只留读、搜索、网络三族的只读部分，允许列表就是工具列表本身（全部预授权，因为只读无风险）。法务团队的配置就是它：agent 能看能查能引用，什么都不能改。审批回调几乎不会被触发，因为没有任何调用需要批准。

行动档：在情报档之上加编辑和写，权限模式设为接受编辑类，shell 保持走审批。平台团队的配置：日常改配置流畅无阻，越界动作（跑命令）依然要人点头。

执行档：全工具面加白名单化的作用域规则。安全团队的配置：扫描命令按工具名放行，删除类调用用禁用列表或窄作用域规则扣死，其余走审批。这一档的功夫全在规则设计上，工具面反而是全开的。

三档之外还有一个归零档：空工具列表加纯自定义工具。agent 的全部能力都由你的代码定义，内置一概不用。这是把 agent 当领域专用设备用的配置，产品化程度最高的形态，代价是放弃内置工具的免费战斗力，每个能力都要自己补。

## 五个常见陷阱

陷阱一：显式工具列表吃掉编排工具。你传了工具列表，引擎按你的列表来，没列的都不在。很多写了技能列表或依赖提问能力的配置忘了把对应的编排工具（技能调用、用户提问）列进去，功能静默失效，没有报错，因为工具不在视野里属于正常状态，引擎并不把它当错误。

陷阱二：以为允许列表限制视野。允许列表只预授权，不裁剪。想收紧视野用工具列表，两个选项各干各的，配错方向的例子满地都是：开发者用允许列表想"禁掉"Bash，结果 Bash 还在视野里，每次调用都弹审批，agent 换着花样被拒，体验灾难。

陷阱三：宽权限模式盖住 MCP。接受编辑类模式不自动放行 MCP 工具（前文官方建议的由来），有人因此直接跳到全放行模式救急，等于把前面精心设计的窄作用域规则全部架空。正确解法是给 MCP 工具写允许规则，哪怕是整服务器的通配符，也比全局放权好。

陷阱四：作用域规则写得太宽。删命令的模式写宽了一点，恰好盖住了备份目录，agent 按规则"合法"删掉了备份。规则要窄到具体业务路径，并且放进版本库评审，当成生产配置对待。

陷阱五：忘了并发语义标注。自定义工具没标只读提示，三十个并发查询全被引擎串行排队，延迟翻了几十倍，看起来像性能 bug，其实是工具元数据缺失。上线前把每个自定义工具的读写性质过一遍。

## 权衡与局限

工具面收得越紧，agent 越安全也越笨。过度裁剪的 agent 会陷入"什么都问审批"或"什么都做不了"的泥潭，用户很快弃用。工具面放得越开，agent 越能干也越危险，一次误操作的代价随能力指数上升。三档配方只是起点，真实系统还要按团队、按任务类型动态调整，配合审批回调把"偶尔越界"变成可管理的交互成本。

还有一个局限要说透：工具控制管的是工具调用，不管提示注入后 agent 用合法工具干坏事。恶意网页内容说服 agent 用它被授权的工具删文件，工具层看到的是一次完全合规的调用。这层风险要靠权限模式的审批流和沙箱兜底，工具裁剪是必要不充分的安全层。

## 三档配方的行为推演

把三档配方放进同一个任务里跑一遍脑内推演，看每档的真实行为差异。任务：agent 被要求"清理过期的临时构建产物并汇报释放了多少空间"。

情报档下（只读工具集）：agent 列出目录、统计文件年龄、算出可清理的体积，然后汇报"共可释放约两 GB，涉及三千个文件，我没有删除权限"。任务完成了信息的一半，行动为零。这个档位的语义是：agent 只当分析员，动手执行要交给下一档。用户拿到报告自己执行，或者产品把它升级。

行动档下（加编辑类放行、命令走审批）：agent 尝试删除文件，删除是命令操作，触发审批回调。你的程序看到删除目标路径都在临时目录规则内，自动放行（回调里做范围校验），agent 完成，汇报结果。中间任何一次删除目标越出范围，审批拒绝。这个档位的语义是：行动有闸门，闸门可编程。

执行档下（命令按窄规则预授权）：同样的删除直接执行，无审批往返，速度最快。风险依赖规则质量：规则写成删除某目录下超过三十天的文件，agent 的自由裁量被压到最小；规则写宽了，一次误配就是一次事故。这个档位的语义是：把信任从运行时的审批转移到了配置时的评审。

推演暴露一个常被忽略的事实：档位的选择，选的其实是"错误在哪一层被发现"。情报档的错误在汇报层（没做错事但也没做完事），行动档的错误在审批层（每次交互都有拦截机会），执行档的错误在配置评审层（出事时已无运行时防线）。没有零风险档位，只有风险位置不同的档位，选档时想清楚你的团队哪一层的把关能力最强。

## 工具面预算：一个常被漏算的账

给工具面设预算，是控制它膨胀的实用纪律。预算的两个维度：数量和体积。

数量预算：一个会话的内置加自定义加 MCP 工具总数，给出硬上限（比如四十）。每加一个工具问一句：这个工具的月调用预估是多少？预估低于一个门槛（比如十次）的不配，用的时候让 agent 用更通用的工具凑合或走人工通道。低频工具是工具面的"库存成本"，进出都要讲 ROI。

体积预算：工具定义的 token 总量进观测（底盘水位的第一构成），超过阈值触发两条路之一：上工具搜索（结构化解决），或做工具面裁剪（行政解决）。两条路的分界在工具数量：二十以内裁剪，二十以上搜索。

预算制度的存在还有一个组织学作用：它把"加工具"从顺手的事变成过会的事。工具面失控的团队，几乎都是因为加工具太顺手。

## 工具面的演进节奏

工具面不是一次设计定型的，它随产品成长。健康的演进节奏分三拍。

第一拍，最小起步：上线时只给任务必需的核心工具（往往五件以内），宁可 agent 频繁汇报"我没有做这件事的工具"，也不要预判性地铺一堆"可能有用"。早期的每次工具请求都是需求信号：同一类请求出现三次，说明该添工具了；从来没被请求过的能力，说明任务根本不需要。

第二拍，按证据扩张：每次扩工具面带着使用数据说话（这是哪类任务、缺什么工具、预计调用量），扩张后观察两周实际调用率。数据驱动的扩张让工具面和真实任务分布对齐，而不是和开发者的想象力对齐。

第三拍，定期回收：季度清点，调用率归零的工具进移除评审。工具面的新陈代谢和代码库一样重要，只进不出的工具面半年后就是那个"一百个工具没人敢删"的博物馆。

三拍节奏的实质是把工具面当产品功能管理：有上线标准、有数据验证、有下线机制。多数团队的工具面失控，卡点往往不在配置技术，在意识：没把工具面当成需要管理的东西。

## 误读辨析

两个高频误读收尾。误读一：工具越多 agent 越强。真实关系是倒 U 形：工具超过几十个后，选择精度下降（工具搜索篇的账），误调用上升，agent 实际变弱。决定强弱的是工具面和任务的匹配度，数量本身堆不出强度。误读二：权限配置是安全措施的全部。工具面和权限管的是 agent 的手，管不住它读到的内容（提示注入走的是眼睛不是手）。纵深防御的完整拼图里还有沙箱和网络控制，工具面是其中一层，单独拎出来当全部就是安全错觉。

这两个误读合起来还有个推论值得写进设计文档：工具面的"正确大小"跟着任务分布走，不跟着引擎能力走。同样的引擎，代码审查 agent 十件工具是最优，数据平台 agent 可能三十件才够。跨产品抄工具清单是常见捷径，抄来的往往是对别人任务分布的答案，自己的分布要自己量。

## 关键要点

- 两层心智模型：可用性管视野（工具列表、禁用列表），权限管放行（允许列表、权限模式）；禁用赢过允许，允许只是预授权。
- 内置工具六族：文件、搜索、执行、网络、发现、编排，按族裁剪比按个裁剪快。
- 作用域规则把权限细化到参数级，写法像防火墙：默认拒绝、按需开口、开口要窄。
- 三档配方：情报档全只读、行动档加编辑、执行档全开加窄规则；归零档全自定义。
- 五个陷阱：显式列表漏编排工具、允许列表当裁剪用、宽模式盖 MCP、作用域过宽、缺并发标注。
