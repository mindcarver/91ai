# 托管架构：把 agent 服务跑起来、扩出去

> 更新日期：2026/10

**TL;DR：** 托管 Agent SDK 服务的底层事实就两条：一个会话等于一棵进程树，会话状态默认长在本机磁盘上。因此架构设计围绕两件事：进程资源的容量规划和状态的外置。四种部署拓扑覆盖绝大多数场景，垂直扩容按内存公式算，水平扩容按会话粘性路由，多租户按隔离配方执行。容器本身很便宜，token 才是账单大头，托管优化的重点从来不是省机器。

## 托管问题的本质

把 SDK 服务从笔记本搬进机房，遇到的问题全部源于两个事实。

事实一：一个会话一棵进程树。你的服务进程之下，每个会话拉起一个引擎子进程，stdio 型 MCP 服务器再挂一层孙进程。一百个并发会话就是一百棵树，每棵树有真实的内存、CPU、磁盘占用。这不是线程池模型（线程便宜可以超发），是进程模型（进程昂贵必须实算）。

事实二：状态默认本地。会话转录文件、记忆文件、工作目录的产物，全都写在创建它的那台机器的磁盘上。单机时代这不是问题，进机房后它成了中心问题：自动伸缩把会话杀在 A 机、请求落到 B 机，本地状态就是孤儿。

全部托管设计都是对这两个事实的回应：进程按树核算资源，状态按外置规划归属。

## 四种拓扑

拓扑选型按任务的寿命和到达模式定。

临时型：一个任务一个容器，任务完成容器销毁。适合边界清晰的一次性工作（修一个 bug、翻译一份文档）。优点是隔离最彻底、状态问题最小（产物外传即走）；缺点是冷启动成本每次都付。无服务器形态的 SDK 部署基本属于这类，注意进程模型的限制：函数环境要装得下子进程和二进制（选型篇的老约束）。

长驻型：常驻容器里跑多个 SDK 进程，会话保持温热。适合交互式产品（用户随时回来继续聊）。温热的收益是冷启动消失和缓存命中稳定；代价是资源常驻和容量预留。配套动作是预热：提前拉起会话对象（TS 的预热接口、Python 的客户端常驻），用户消息到达时零启动延迟。

混合型：临时容器加存储适配器水化。会话数据全在外部存储，容器按需拉起、从适配器加载会话、跑完即走、空闲即缩。它兼得弹性和连续性，是生产系统的主流形态。代价是适配器这层基础设施的建设运维（存储篇的全部内容都是为这个形态服务的）。

多代理容器：一个容器里多个引擎进程协作（比如一个协调者带若干执行者）。每个进程必须有自己的工作目录（文件互踩是协作的大敌），容器规格按进程数乘单进程预算上浮。

四类的选择不是终身制：产品早期混合型最稳，规模上来后按任务类型分流到不同拓扑（交互流量长驻、批处理临时）是常见演进。

## 垂直扩容：单机能装多少会话

容量公式：单机会话数等于（机器内存减系统开销）除以单会话内存上限。公式的两个参数都有讲究。

分母要用**峰值常驻内存**（不是平均值）：用有代表性的任务实测会话进程的内存曲线（长任务、大文件、多子代理的最坏组合），取峰值再加安全边际。官方给的起点是单 agent 一 GiB 内存、五 GiB 磁盘、一个 CPU 核，并明确说一 GiB 是下限不是典型值。内存随会话长度和工具活动增长，重任务类型的实测值可能翻几倍。

分子别忘了进程树：一个会话带两台 stdio MCP 服务器，实际占用是三个进程的和。容量测算要用树的合计。

公式之外有三个补充机制。引擎没有内建的会话级超时，长会话会无限活下去，用轮数上限或定期回收进程来封顶内存增长（回收的代价是会话冷重启，与混合型的蒸馏节奏天然契合）。子代理没有墙钟截止时间，只有一个卡死看门狗环境变量兜底，批量任务的外部超时要你的调度层做。大规模并行子代理的扇出会撞接口限流，并发规划时把模型侧限流算进容量，限流触发的排队也要有观测和告警，不然容量数字会在第一次高峰期悄悄失真。

## 水平扩容：多机怎么分担

多机方案的核心决策只有一个：请求与会话的亲和。会话状态（哪怕有适配器）恢复有成本，连续请求落在同一台机器永远最便宜。

标准做法是负载均衡加会话粘性：按会话 ID 做一致性哈希路由，同一会话的请求稳定落到同一节点；节点故障时会话经适配器在别的节点复活（混合型的弹性来源）。没有适配器的部署做不了干净的粘性（本地会话就是死状态），水平扩容前先把状态外置，顺序不能反。

扩容节奏与普通服务不同：SDK 会话是有状态长连接，不是无状态请求。缩容不能粗暴驱逐（正在跑的会话要等任务边界），滚动发布要有连接排空（等存量会话完成或迁移）。把 SDK 服务当成数据库连接池级别的有状态负载对待，而不是 HTTP 服务。

## 多租户隔离的执行清单

多租户是托管安全的最高压场景，配方前面各篇零散给过，这里合成一张执行清单，逐条打勾。

配置隔离：配置来源设空数组（文件态输入全断）；自动记忆显式关闭（它不走配置来源，漏掉就是租户间记忆泄漏）；托管策略照常生效（企业的底线，不许动）。

文件系统隔离：每租户独立的配置目录（环境变量重定位）和独立的工作目录（每次调用显式传）；更进一步用容器或至少独立卷，把文件系统视图彻底分开。可选的项目目录名环境变量让会话存储按租户分键。

网络隔离：每租户的出口规则在代理层做（独立出口 IP、凭据白名单），防止 A 租户的 agent 访问 B 租户的内网资源。

观测隔离：遥测打租户标（观测篇的资源属性），成本、审计、日志全按租户可切分。

隔离的验收不是配置评审，是渗透测试：让 A 租户的会话尝试读 B 租户的文件、记忆、会话，全部失败才算过。这份清单跑一遍半天，漏一条的代价是数据事故。

## 状态外置的完整地图

混合型拓扑里，要外置的状态不止会话，一张地图：

会话转录：存储适配器（唯一有官方通道的），恢复跨机全靠它。记忆文件（自动记忆目录）：默认在本地，要么关闭（多租户必须），要么挂卷同步。工作目录产物：任务产出的文件，对象存储同步或挂持久卷，容器销毁前必须离开容器。依赖缓存（包管理器的缓存目录）：挂卷共享可显著加速重复任务，注意按租户或按项目分键防止缓存投毒。

地图的判据统一：**容器可以被随时杀死而数据不丢**。逐项检查每个状态点，能过这条判词的就是外置到位了。

## 成本结构：别优化错对象

托管成本的两块：容器基础设施和 token。官方给的量级判断值得直接引用：token 成本通常比基础设施成本高一个数量级，一个最小容器每小时大约五美分。

这个结构的推论很实际：把工程精力花在 token 优化（成本篇的全部内容）上，机器侧保持够用就好。一个常见的本末倒置是为了省两台机器把回收周期调得激进，结果会话频繁冷启动、缓存全部失效、token 成本翻倍，省了芝麻烧了西瓜。托管参数（内存上限、回收周期）和 token 参数（会话长度、缓存稳定）要一起调，它们是同一台机器上的联动机。

## 托管部署的疑问

**冷启动到底多慢，能压到多少？** 组成是容器拉起（镜像和平台决定，秒级）、子进程启动（一秒内）、配置加载、MCP 连接（有服务器时是大头）。裸启动一般两三秒，带多台服务器冷连接可到十秒级。压缩手段：预热容器、长驻拓扑、MCP 侧的缓存工具列表（连接篇的时序优化）。

**会话粘性和负载均衡打架怎么办（热点会话把一台机器打满）？** 一致性哈希解决了归属但解决不了热点。单会话的负载上限受它自己的进程资源封顶，真热点（一个会话被高频访问）更像产品问题：考虑把高频内容蒸馏成缓存结果，让会话退出热路径。

**滚动发布怎么做到不中断会话？** 三步：新版本容器上线接新会话；旧容器进入排空模式（存量会话跑完即退，超时的按适配器迁移）；存量清零后下线旧容器。配合会话版本快照（恢复会话用原配置），跨版本的会话恢复也安全。

**预算超限的会话在托管层怎么处理？** 引擎侧预算错误结束查询（执行限制篇），托管层要做的是把预算错误翻译成产品动作（任务标记失败、通知、允许提额重跑），别把它当基础设施故障报警。预算是业务事件，不是 ops 事件。

**监控大盘最少要哪几块？** 会话层数（活跃、排队、错误率）、资源层（每节点进程数、内存水位）、业务层（任务成功率、成本分布）。三块齐了值班就能干活，第四块（链路）在有性能投诉时再上。

## 容量测算的实操步骤

公式有了，落到数字的五步实操。

第一步选代表性任务：从真实负载里挑三个档位（轻：单轮问答型；中：十轮内带工具调用；重：长任务带子代理和大文件）。第二步实测单会话资源：每档任务各跑五次，记录引擎进程的峰值内存、CPU 时间、磁盘写入量，取每档的九五分位。第三步合成画像：按你预估的流量构成加权（轻六成中三成重一成的典型构成），得出加权单会话资源。第四步算单机容量：可用内存（总内存减系统与你的服务进程）除以加权峰值，再乘零八的安全系数。第五步压测验证：按算出的容量实际压一轮，看内存水位和任务时延，偏差超过两成回第三步修正。

五步半天的活，产出的容量数字是水平扩容、预算申请、压测基线的共同地基。跳过测算直接上线的团队，第一个容量事故会替他们补这堂课，学费贵得多。

## 预热的工程细节

长驻拓扑里预热是体验的命门，细节值得展开。

预热的对象分三层。进程层：容器和引擎进程提前拉起（平台层的预热钩子或常驻进程池）。会话层：为即将到来的用户预备半初始化的会话对象（连接建立、配置加载完成、等第一条消息）。上下文层：高频用户的会话提前恢复（把最近会话从适配器水化进来），用户回来时记忆已在。

预热的策略按信号分级。无信号预热（按时段规律盲预，早上九点前预备五十个温热会话）；弱信号预热（登录页活跃度上升时追加）；强信号预热（用户打开 agent 界面的瞬间完成水化，几百毫秒级）。三层信号叠加，冷启动从体验里基本消失。

预热的成本纪律：温热会话占着进程资源，预热池的规模上限按付费用户数和历史活跃率算，闲时收缩（夜里预热池降到最小）。预热是花钱买体验的典型决策，账要明算。

## 扩容与故障场景的追问

**批处理和交互流量混在一个集群，互相干扰怎么办？** 物理或逻辑分组：批处理走独立的节点组（可抢占、可超卖），交互流量走专属组（保护时延）。两组共享适配器和观测，容量各自算。混跑的干扰（批任务把内存打满、交互用户卡顿）是托管投诉的常客，分组是唯一根治。

**节点故障时进行中的会话怎么办？** 分两段：进程没了，会话数据在适配器（混合型的前提），新节点接手恢复；正在写的最后一批可能丢（镜像的异步性），接手逻辑按最后已知状态续跑并向用户说明一次衔接。没有适配器的部署，节点故障等于会话损失，这个数学题在选拓扑时就该算清。

**几百个并发会话时，stdio 型 MCP 服务器怎么算资源？** 每个挂 stdio 服务器的会话都多一层孙进程，容器规格要按进程树的合计算，而不是只算引擎进程。能换成远程形态的服务器就换，换不掉的把每会话的挂载数控制住，容量公式里给孙进程留出内存余量。

**怎么向架构评审委员会论证这套部署的合理性？** 三页材料：一页容量数学（测算步骤的产出：单会话资源、单机容量、所需节点数与成本），一页拓扑图与故障域说明（每类故障的影响面与恢复路径），一页与替代方案对比（无服务器方案为何不适配进程模型、全托管方案的控制力损失）。委员会问的三个问题（多少钱、挂了怎么办、为什么不是别的）各一页正好答完。托管架构的评审要点是让数字代替形容词。

## 关键要点

- 两个底层事实：一会话一进程树、状态默认本地；全部托管设计是对它们的回应。
- 四拓扑：临时隔离最彻底、长驻零冷启动、混合是生产主流（适配器是地基）、多代理容器按进程数配资源。
- 垂直扩容公式按峰值内存算进程树合计；无内建会话超时，用轮数和回收封顶；水平扩容先外置状态再谈粘性。
- 多租户清单：空配置来源、关自动记忆、独立目录、网络分租户、观测打标，验收靠渗透测试不是配置评审。
- 状态外置判据：容器可随时杀死而数据不丢；token 成本比机器高一个数量级，优化别选错对象。
