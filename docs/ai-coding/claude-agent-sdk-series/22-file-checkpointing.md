# 文件检查点：agent 时代的撤销键

> 更新日期：2026/10

**TL;DR：** 开启文件检查点后，引擎在每条用户消息的边界备份即将被修改的文件，消息流里出现检查点标识，你拿标识调用恢复接口就能把文件回滚到那个时刻。它补上会话机制的缺口：会话管对话的时光机，检查点管文件的时光机。但覆盖面有硬边界：只捕获写入类工具的改动，shell 命令改的文件、子代理的编辑、目录操作都不在保护圈内。

## 会话有了时光机，文件呢

会话篇钉死过一条边界：恢复会话还原对话不还原文件，agent 改过的文件是真实改动。这个边界留下一个工程缺口：agent 把代码改坏了，对话可以 rewind，文件回不去，你只能手动收拾或翻 git。

git 是答案的一半：有版本库的地方，diff 加 reset 能救大部分场。但 agent 的很多战场没有这层保护：配置目录、临时工作区、agent 自建的输出目录，或者改动还没提交、用户不想为了回滚把脏提交混进历史。文件检查点机制就是引擎内建的这层保护：改动前自动备份，事后按点恢复，不依赖 git 也不污染 git。

它的工作方式：开启选项后，引擎在每条用户消息处理前，把即将被修改的文件备份。消息流里每条用户消息带一个检查点标识。你的程序存下这些标识，出事时挑一个调恢复接口，文件回到那个时刻。

贯穿案例：agent 分三轮改一个服务：先重构（成功）、再加测试（引入坏改动）、再调格式（正常）。第三轮后你验证发现服务坏了。没有检查点，你要手工区分三轮改动哪些要留哪些要撤。有检查点，每个轮次边界都是恢复点：回滚到第二轮之后，保留重构、撤掉测试和格式化，一个调用完成。

## 开启与使用

开启是两个动作的组合：主选项打开功能，再加一个运行参数让用户消息在流里重放（检查点标识就挂在这些重放的消息上）。配套的权限模式通常选接受编辑（自动批准编辑，否则每个编辑都等审批，检查点的意义减半）。

使用节奏三步。第一步，收标识：分发循环里把每条重放用户消息的标识存起来，按序号排列就是一条时间线。第二步，选点：时间线上每个标识是一个"那时文件世界还好"的候选锚点，选哪个取决于你想保住多少工作（案例里选第二个点保住前两轮）。第三步，恢复：拿标识调恢复接口。

恢复的时机分两种。会话还开着，流式循环内直接调，恢复动作作为一次指令注入当前会话。流已经结束（最常见的事后场景），先恢复会话（空提示触发），在新循环里调恢复，且恢复后的会话要重新开启检查点选项（它跟着会话配置走，不是全局状态）。

## 恢复的确切语义

恢复做什么：把修改过的文件恢复到检查点时刻的内容，agent 新建的文件被删除。不做什么：**对话历史原封不动**。这条语义很重要：回滚后 agent 仍然"记得"自己做过那些改动，它的上下文里改动还在，只是文件系统层面被撤销了。要 agent 干净地重来，恢复文件之后再明确告诉它"改动已回滚，从检查点状态重新开始"，把文件态和对话态的落差向模型说明，否则它可能困惑于"我记得改了但文件里没有"。

另一个方向的误解也要防：恢复只动文件。你想撤销的是对话里的一段错误推理时，用会话的分叉回到更早的会话点；想撤销的是文件改动时，用检查点。两个时光机各管一边，组合使用才能摆出完整的平行宇宙。

## 保护圈的边界

保护圈是这篇最重要的实用知识，圈外的改动不受保护，设计回滚策略前先清点你的风险在不在圈内。

圈内：写入类工具的文件改动（写、编辑、笔记本编辑），这是检查点备份的主体。

圈外五类。shell 命令的文件改动：agent 用命令行重定向、内联编辑改的文件没有备份，命令的行为引擎无法逐文件追踪。子代理的编辑：子代理上下文里的写入不在主会话的检查点内（个别前台技能场景例外）。目录级操作：建目录、移动、删除目录不被撤销。远端与网络文件：备份的是本地文件系统。链接文件：符号链接、硬链接在恢复时跳过（结果里有跳过计数），旧版本引擎甚至穿透链接写入，版本门槛要注意。

边界的实践含义：如果你的 agent 大量用 shell 改文件（很多运维场景如此），检查点的保护接近失效，回滚策略要另建（工作区快照、容器抛弃）。让 agent 优先用写入类工具改文件，不只是习惯问题，是可回滚性问题。这条可以写进系统提示或技能里作为操作规范。

## 会话、存储与检查点的三角

检查点绑定创建它的会话：恢复要回到同一个会话（可以先恢复会话再恢复文件），跨会话用别家的检查点不行。会话恢复的完整姿势在会话篇，这里补检查点专属的两条。

与关闭持久化的选项互斥（和存储适配器同款冲突，一个说不留档一个要留备份，语义矛盾启动即报错）。

与存储适配器的关系：检查点数据在会话转录的体系里，跨机恢复会话时随会话数据走，适配器篇讲的子键机制覆盖这类附属文件。但依赖这条链路前实测一次：跨机恢复后检查点可用性是版本敏感的，把它当能力演进中的部分。

## 典型工作流：确认或回滚

检查点解锁的最大产品模式是确认或回滚：agent 改完，你的程序自动验证（跑测试、起服务探活、对比产物），验证过继续或提交，验证不过自动回滚到检查点并带着失败信息重试或上报。人只在重试失败后介入。

这个模式把 agent 从"改完等人工检查"升级为"自带质量门的循环"，是自治任务安全落地的基础设施。两个工程要点：验证要选真正的判据（测试过不等于没坏，按任务选），重试要有限次（回滚加重试无限循环是烧钱循环，配轮数和预算上限兜底，执行限制篇的老朋友）。

交互式场景同样受益：给用户每个阶段一个"保留或撤销"的选择点，选择点的实现就是检查点标识。agent 的改动从"一锤子买卖"变成"可以反悔的交易"。

## 权衡与局限

检查点不是免费的。备份要写盘：大文件、高频改动的场景，备份的 IO 和空间是实打实的成本，评估工作区的磁盘预算时把备份算进去。恢复也不是万能钥匙：它是文件级粗粒度回滚，恢复点只能选消息边界，想撤"这一轮里的一半改动"做不到，粒度需求细的场景仍然要靠 git 分支或提交粒度的操作规范。

最大的局限还是保护圈：圈外改动的存在意味着"有检查点"不等于"可回滚"，安全声明要以实际操作面为准。审计你的 agent 实际用什么工具改文件，再决定检查点承担多大的信任。

## 确认或回滚的完整实现细节

把杀手级模式的实现拆到可以直接动工的粒度。

流程的五个状态：agent 改动中、验证中、通过、回滚中、重试或上报。状态机由宿主程序驱动，agent 只负责改，验证和决策都在你的代码里。

验证环节的设计是成败手。三个层次按任务选配：快速层（静态检查，秒级，语法和导入可用性）、功能层（跑测试或探活，分钟级）、语义层（人工抽查或另一个只读 agent 复查，小时级）。最低配也要有快速层，裸奔的自动回滚等于把质量门拆了。验证的失败输出要整理成回滚后重试的输入：不是"测试挂了"，是"哪三个用例挂了、断言差异是什么"，重试的提示词里带上这些，agent 才能对症而不是重掷骰子。

回滚环节调用恢复接口，时机选验证判死的当下（会话还在流式循环里，直接调）。回滚完成后给模型发一条说明消息（文件态对话态落差的说明，前文讲过），然后带上失败细节重新下达任务，这是重试轮。重试轮次计到三为止：三轮同类失败说明不是随机坏运气，是任务或验证的设计问题，转人工通道。轮次和预算上限全程兜底，自动循环最忌讳的是它自己变成失控任务。

产物 salvage 是容易被漏的一步：回滚撤掉改动时，改动里可能有值得保留的片段（一半正确的重构、发现的新问题记录）。回滚前让 agent（或你的程序）先把 diff 存档，回滚不删你的存档。人工通道拿到的材料是"三轮失败加每次的 diff 存档"，而不是一句"它不行"。

时序上还有个细节：恢复接口在流结束后不能直接调（进程已关），要么在流式循环内完成整个回滚，要么走恢复会话的路线。设计状态机时把"会话还活着吗"当成回滚路径选择的开关。

## 回滚边界的几个疑问

**检查点和 git 一起用冲突吗？** 不冲突，分层保护：git 管提交历史，检查点管提交之间的过程态。agent 在工作区的每次改动有检查点兜底，验证通过后由你的程序做一次干净的 git 提交，两层各管一段。

**每条消息一个检查点，备份会不会爆盘？** 备份只备份被修改的文件，没改动的消息不产生备份体积。真实压力来自大文件高频改（数据库转储、锁文件这类）：把这类路径从工作区隔离出去（放追加目录外或让 agent 别碰），备份预算就稳了。

**回滚能把"第三个文件的改动"单独撤掉吗？** 不能，恢复粒度是检查点时刻的全量文件态。要细粒度，用多个检查点把改动切成时间片，逐片回放。所以给 agent 的任务节奏最好按阶段分消息下，每阶段边界天然成片。

**子代理改的文件怎么办？** 在保护圈外（前文边界），主会话的检查点不覆盖。涉及子代理改文件的任务，让子代理把改动方案汇报回来由主会话执行写入，或给子代理的任务配自己的 git 工作区。

**用户中途插话会打乱检查点节奏吗？** 不会，插话本身就是新的用户消息，天然开新检查点。反而要注意的是插话后验证逻辑要不要重跑（文件可能又被改了），状态机里验证与改动的触发关系要写明确。

## 保护圈的实测验证

保护圈的边界（前文五类圈外）不该停留在文档认知，部署前花二十分钟实测一遍，你的任务形态实际覆盖多少。

实验一，正打正着：让 agent 用编辑工具改一个文件，回滚到改动前，确认文件复原。这是基线，通不过说明配置没开对（两个开关的组合或版本门槛）。

实验二，shell 侧通道：让 agent 用命令行重定向改另一个文件，回滚同一时刻，观察这个文件没被复原。这是圈外的实感：亲眼看到一次，比读十遍文档记得牢。然后决策：你的任务模式允不允许 shell 改文件？允许，回滚策略必须补 git 或快照；不允许，提示词里立规矩（改文件一律用编辑工具）。

实验三，目录操作：让 agent 建目录再回滚，目录还在。产物目录的清理逻辑要另写（你的程序知道 agent 建了什么目录，从工具结果里收集）。

实验四，混合改动：同一轮里 agent 既用编辑工具又用命令改了文件，回滚后一个复原一个没有。这个实验最有教学价值：它证明"一轮改动"不是原子的，回滚后的状态是部分复原的混合态，验证逻辑必须按文件级核对而不是按轮次宣布成败。

四个实验的结果写进这个 agent 的部署档案：保护圈实测覆盖率多少、圈外风险用什么手段补的。回滚承诺从此有据可查，不是一句"开了检查点"的口头禅。

## 恢复接口的时机速查

恢复调用在什么时机走哪条路，速查表。

会话活跃中（流式循环未关）：直接在循环内调用恢复接口，最快路径。流已结束：先以空提示恢复会话（起一个新流），在新循环里调恢复，且新会话重开检查点选项。跨机场景：会话先经存储适配器到位（存储篇），再走恢复会话加恢复文件两步。恢复后再续任务：先发落差说明（文件已回滚到某点），再下新指令。

表里最关键的分界是第一条：确认或回滚的自动化尽量设计在会话活跃期内完成整个循环（验证加回滚加重试指令都在一个流里），路径最短、状态最连续。流结束后的恢复是给"事后发现要回滚"的场景兜底的，不是主路径。

再补一条与 git 的节奏配合：检查点回滚发生在验证判死时，git 提交发生在验证通过后，两个动作之间不要混入人工改动。人工改过的文件再触发回滚，恢复到的是检查点时刻的内容，人工那部分会一并消失。工作区在自动循环进行期间保持"只属于 agent"，人工干预安排在循环外，这条纪律比任何工具参数都更直接地决定回滚的可信度。

一句与团队的沟通建议收尾：把"这个 agent 的改动可回滚"这句话翻译成精确版本再承诺（写入类工具的改动可回滚到消息边界，命令行改动不在此列），写进产品文档的脚注。模糊的回滚承诺在第一次 shell 改动事故时会反噬信任，精确的承诺哪怕覆盖面小，也是可以兑现的承诺。

## 关键要点

- 开启是选项加运行参数的组合，标识挂在重放的用户消息上；流结束后要先恢复会话再恢复文件，恢复后的会话重开检查点。
- 恢复只动文件不动对话：回滚后要向模型说明落差；对话回滚用会话分叉，文件回滚用检查点。
- 保护圈：写入类工具在圈内；shell 改动、子代理编辑、目录操作、网络文件、链接文件在圈外，圈外改动不被保护。
- 与关闭持久化互斥；确认或回滚是它的杀手级模式，配真判据和有限重试。
- 成本是备份 IO 和空间；粒度是消息边界；"有检查点"不等于"可回滚"，按实际操作面评估。
