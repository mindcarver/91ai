# 消息流与事件模型：读懂 agent 的每一次心跳

> 更新日期：2026/10

**TL;DR：** SDK 的一切高级功能都建立在同一条消息流上：五种消息类型、轮的精确定义、两个执行上限、并行执行的隐藏规则、输入输出的两种模式。读懂这条流，你能从事件序列推出 agent 正在干什么、为什么停、钱花在哪；读不懂，调试就只能靠猜。这篇用一次修 bug 任务把整条流从头走到尾。

## 一次调用的完整生命周期

贯穿案例沿用修 bug 任务：你发一句"找出 utils.py 里的空列表除零问题并修掉它"，agent 读完文件、定位、改写、汇报。这个任务在事件流里展开成五个阶段。

第一阶段，接收任务。SDK 把任务文本、系统提示、工具定义、历史一起交给引擎，流里最先出现的是一个 init 子类型的系统消息，携带会话元数据。这是引擎在自我介绍：会话 ID、初始配置。你的程序通常在这里取走 session_id 存好。

第二阶段，模型响应。模型输出一段"我先读一下这个文件"加一次读文件的工具调用。流里表现为两条模型消息：一条文本块，一条工具调用块。同一次响应里的多个块共享同一个消息 ID，这是你判断"这几条是一个响应"的依据。

第三阶段，执行工具。引擎执行读文件，结果作为用户消息回灌给模型。注意这个名字的误导性：用户消息在这里装的是工具结果，不是人输入的话。

第四阶段，循环。模型看到文件内容，输出定位分析加一次编辑工具调用，引擎执行，结果再回灌。第二、三阶段如此往复，每一整个来回算作一轮。轮数是 SDK 里最重要的计量单位，后面两个上限都以它为尺。

第五阶段，收尾。模型输出最后一条纯文本消息（修复总结，没有工具调用），随后流里出现结果消息，带最终文本、token 用量、花费、轮数、会话 ID。任务结束。

五阶段就是 agent 循环在流上的投影。你写任何分发逻辑，脑子里要有这条时间线：系统消息开路，模型消息和用户消息交替心跳，结果消息收束。

## 五种消息各自的读法

系统消息看子类型。init 开场，压缩边界（compact_boundary）标记一次上下文压缩发生了，还有信息类和进程收尾类。TS 里非 init 的子类型被拆成了独立类型，Python 里统一在系统消息的子类型字段上判断，这是两门语言类型系统最大的不对称处，跨语言移植分发代码时必查。

模型消息看块。一条消息一个块，文本块是它的思考与汇报，工具调用块是它的行动意图。TS 里内容藏在 message.message.content 这层嵌套里，Python 是平的，又一个移植坑。

用户消息看来源。多数是工具结果，流式输入模式下也会混入你中途发的真用户输入，处理时别把两种混为一谈。

流事件只在开了增量选项后出现，装的是模型 API 的原始增量，细节放到本文后半部分。

结果消息看子类型定结局。success 是唯一带最终文本的；error_max_turns 是轮数上限被打穿；error_max_budget_usd 是预算见底；error_during_execution 是执行期异常；结构化输出场景还有专门的校验重试超限子类型。所有子类型都带花费、用量、轮数、会话 ID 四件套，错误结果也不例外，所以错误也能算账。

## "轮"的精确定义与两个上限

轮的定义有一个精确但反直觉的细节：**轮数上限只统计包含工具调用的轮**。最后一轮纯文本收尾不计入。这意味着 max_turns 设 10 时，agent 最多执行 10 轮工具循环，然后还能再说一段总结的话。按"总响应次数"理解上限的人会困惑为什么 10 轮上限的会话有 11 条模型消息。

预算上限的语义同样有两个坑。第一，它是累计值，跨轮累加，不是每轮限额；官方指定的重置手段是等价于 /clear 的清空操作，会话中途不会自动恢复额度。第二，子代理的花费计入主会话的预算，这是防止"主代理省着花、子代理放开烧"的绕过。另外预算的严格执行依赖引擎版本，老引擎上这个选项的强制性打折。

两个上限命中后的表现一致：产出对应错误子类型的结果消息。单发模式下，产出错误结果之后 query() 还会再抛异常，所以循环里要先取字段再等异常，这条规则在会话恢复场景里反复出现。

## 并行执行的隐藏规则

模型一轮里可以发多个工具调用，引擎的执行策略按工具性质分两档：只读工具（读文件、搜索、glob）并发执行；会改状态的工具（编辑、写入、bash）串行执行。这是引擎自带的保护，避免两个写操作互相踩。

自定义工具默认按串行处理，因为引擎不知道它有没有副作用。给工具元数据里标上只读提示后，引擎才会把它并入并发档。这里有一个必须强调的语义：这些提示是元数据不是强制，标错了（把会写的标成只读）不会报错，只会让本该串行的写操作真的并发跑起来，出数据竞争。提示要诚实，这个责任在自定义工具的作者，引擎不替你把关。

## 输入侧：两种模式怎么选

发任务有两个模式。单发模式传一个字符串，一问一答，会话结束；流式输入模式传一个异步生成器，会话常驻，你可以排队发消息、中途打断、跟随回复。能力差异是硬性的：图片输入只支持流式模式；单发模式没有排队和打断。

选择有明确的判据。无状态环境（函数计算、一次性脚本）用单发，一次调用一个结果，最省心。要做对话产品、要在长任务中途改变方向、要传图，用流式。有一个容易低估的坑：流式模式下你的输入生成器抛异常，TS 里表现为引擎收到"用户中止"，Python 里几乎无感（只记 debug 日志），会话停在那里。所以流式模式的责任更多：你的生成器代码质量直接决定会话健康度。

Python 侧还有一个模式切换的细节：客户端对象上的接收循环在第一条结果消息处停下，要多轮对话就一条消息配一对发送加接收调用。把这当成节奏约定记住，能省去"为什么第二条消息没回复"的排查时间。

## 输出侧：整块与增量

默认输出是整块的：每个内容块完整成形后作为一条模型消息到达。这对多数程序够用：你反正只关心结果和工具序列。

开增量选项后，流里混入流事件，粒度到模型的 token 级输出。事件族的命名直白：消息开始与结束夹住一轮，块开始与结束夹住一个内容块，中间是增量，文本块吐文本增量，工具调用块吐一段段拼起来的参数 JSON。一个实用的边界规律：**完整的模型消息在该块的块结束事件之前到达**，也就是说块结束事件不是"这条消息到了"的信号，整条模型消息先到，随后才是它的块收尾。做打字机效果时按这个顺序对表，不会丢块。

增量模式有两个盲区。子代理的 token 增量不转发，主进程的流事件里看不到子代理内部在吐什么字，要归因子代理的输出只能等它的完整消息。结构化输出的 JSON 在增量流里以未校验的参数增量形态出现，拼出来可能是残缺的，校验过的数据只存在于最终结果消息的字段里。做实时渲染时这两处要留占位，不能把增量当权威。

## 读账本：两本账的差别

结果消息里有两个用量字段，口径不同。usage 记主循环自己：主代理的每一轮加总。model_usage 记整棵代理树：主代理加所有子代理加所有子任务。单代理场景两本账相等；用了子代理后差异就是子代理的开销。

这个区分在生产里有两个用处。算成本上限时看哪本账？预算上限按整树口径扣。做归因分析时用哪本账？两个相减就是"委派出去"的成本，评估子代理架构值不值，这一减是第一手数据。

## 停止原因与崩溃指纹

结果消息里的停止原因字段有四个值值得认识。正常收尾是一个值；输出长度触顶是另一个（内容被截断，处理方式是续写或压缩）；拒绝是第三个，模型基于安全判断拒绝执行任务，检测它比解析文本判断"它好像不想干"可靠得多；空值是第四个，前面讲过的崩溃合成指纹，引擎没来得及说话。

把停止原因放进分发逻辑，你的程序就有了对结局的完全分类能力：成功、超限、异常、拒绝、崩溃，五类五条路径。

## 三个常见误解

误解一：结果消息一到流就结束了。实际上结果之后还可能有少量尾部事件（建议类、收尾类），迭代要跑完整条流，否则丢会话收尾信息。

误解二：用户消息等于用户输入。工具结果才是它的大头，把每种消息按"谁在说话"重贴标签（引擎、模型、系统回灌、你的输入）比按官方名字记更不容易错。

误解三：轮数限制等于消息条数限制。轮是工具循环的整来回，纯文本轮不计，同轮多块共享消息 ID。数错单位，上限行为就无法预测。

## 权衡与局限

事件模型给了你完整的可观测性，代价是你的代码要承担分发责任。整块模式省心但拿不到过程细节；增量模式细节全但边界处理繁琐。工程上常见的中庸做法：默认整块跑通，把需要实时感的部分（进度展示、状态栏）局部升级到增量，两套渲染共存。事件流的稳定性也有前提：SDK 在快速演进，新增事件类型会以新子类型出现，分发代码要留默认分支兜住没见过的类型，别让一个新事件类型打崩整个处理循环。

## 一条真实流的逐段解读

把分发逻辑落到一条真实输出上。任务："修复 utils.py 里的除零问题并验证"。下面是流的骨架，括号里是该处理什么。

系统消息（init 子类型）：取走会话 ID 存档，记下模型与配置画像。（你的处理：入库一行。）

模型消息一（文本块）："我先看看这个文件的实现。"（纯推理，界面渲染成思考气泡，逻辑上可忽略。）

模型消息二（工具调用块，读文件）：注意它和消息一共享消息 ID，属同一轮响应。（渲染成"正在读取文件"。）

用户消息一（读文件的结果回灌）：确认即可，一般不渲染。（日志可记体积。）

模型消息三（文本加工具调用，编辑文件）：一轮响应多块的真实例子，文本解释改动，调用块是动作。（两个块一起处理，别丢任何一个。）

用户消息二（编辑结果）。

模型消息四（工具调用，跑测试）。

用户消息三（测试输出，这次体积大，注意它是上下文压力的主要来源）。

系统消息（压缩边界，如果任务够长）：上下文被摘要过一次的信号，记审计。（健康指标加一。）

模型消息五（纯文本，最终汇报）：这是停止前的最后发言。

结果消息（success 子类型）：取最终文本、总成本、分模型用量、轮数、会话 ID、停止原因。（入库，任务闭环。）

尾部事件若干（建议类）：跑完循环别提前 break 的原因。

一条流读完，五种消息各就各位。把这段骨架做成团队的分发逻辑参考实现，新人的事件处理代码从抄它开始，能少踩一半的类型判断坑。

## 读流时的常见疑惑

**同一轮的多个块，处理顺序有保证吗？** 有，流本身有序，按到达顺序处理即可。并行工具调用的执行结果可能乱序完成，但消息流的顺序是引擎整理过的。

**怎么区分模型消息里"给我的信息"和"给模型的推理"？** 不需要区分，所有模型消息都是模型写给外界看的。真正私有的思考过程不出现在流里（要看得开原始体级遥测）。渲染层面按内容判断（含工具调用的是行动，纯文本是叙述）。

**子代理的消息会出现在主流里吗？** 会以委派工具调用的形式出现（工具名是代理调度工具），子代理内部的完整对话不进主流。想看子代理内部，去它的会话文件（挂在主会话键的子路径下，存储篇讲过）。

**压缩边界之后，之前存的消息引用还一致吗？** 你的程序里已提取的数据不受影响（你已经拿到了）。但别持着"稍后再去流里找某条早期消息"的懒惰引用，压缩后流的历史就是摘要化的，该存的数据实时存。

**结果消息的轮数和数出来的轮数对不上？** 对齐口径：轮数只计工具轮（纯文本收尾不计），并发调用的多个块算一轮。差一通常是数了收尾轮，差好几通常是并发块被当成多轮。

## 关键要点

- 五阶段生命周期：init 系统消息、模型与用户消息交替心跳、结果消息收束；结果后还有尾部事件。
- 轮只计工具轮，纯文本收尾轮不计；预算是整树累计，子代理花费计入。
- 执行策略按工具性质分档：只读并发，改状态串行；自定义工具靠只读提示进并发档，提示标错不报错但会出竞争。
- 图片输入与中途打断只在流式输入模式；增量模式看不到子代理 token、结构化输出增量未校验。
- 两本账：usage 主循环，model_usage 整树，相减即委派成本；停止原因空值等于崩溃指纹。
