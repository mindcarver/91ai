# 成本追踪与预算：从 token 到美元的账本

> 更新日期：2026/10

**TL;DR：** 账本有三级：每条模型消息带 token 计数，结果消息带调用总成本和分模型明细，预算选项给你一个硬止损线。三个口径必须分清：主循环口径不含子代理，总成本和分模型口径含全部代理树。所有美元数都是客户端估算不是账单，别拿它给用户计费。预算只算本次调用自己的开销，恢复会话不背历史账。

## 三级账本

第一级在每条模型消息上：本次请求的输入输出 token 计数。它的用途是过程观测：看着输入数涨，你就看着上下文水位涨（上下文篇的观测手段就是它）。一个技术细节先记下：这级里的输出数是占位值（请求开始时的预估），真实输出总数要以结果消息为准，按消息累加会算错。

第二级在结果消息上：本次调用的总成本（美元）、累计用量、分模型明细。分模型明细把整棵代理树按模型拆开，每个模型一行 token 数和成本，还标注价目来源（官方牌价、托管价目表、未知）。这级是账本主力，你的成本分析基本围着它转。

第三级是预算选项：一个美元数字，会话花费逼近它就终止，结果以预算错误子类型收场。它是止损线不是账单：防的是失控任务烧穿钱包，不是精确计费。

## 三个口径，一次分清

主循环用量：只算主代理自己的请求。总成本：含子代理的全部请求。分模型明细：含子代理且按模型拆分。三者的关系在子代理篇出现过（两本账），成本场景的用法更具体：总成本减主循环折算就是委派开销，评估"子代理架构值不值"直接算这个差。

并行调用的一个计账细节：同轮并行工具调用的多条消息共享消息标识且用量相同（该用量属于整轮请求而非单条），按消息累加要把同标识去重，否则重复计账。

缓存 token 单列两个科目：缓存写入（单价高）和缓存读取（单价低），它们和普通输入 token 是三个价。算成本模型时把三个科目分开，长会话的缓存读取占比是成本结构里最重要的健康指标（缓存命中好的会话便宜一个量级）。

## 预算的精确语义

预算只算本次调用自己的开销。三条推论。恢复会话时，历史会话的花费**不计入**本次预算（你恢复一个已经花了两美元的会话，预算从零重新计，但结果消息的成本字段会带上历史累计，两件事分开：预算看本次、账本看累计）。清空操作（等价 /clear）把预算重新归零。子代理花费计入预算（整树口径，防绕过，执行限制篇讲过）。

预算耗尽的现场要认得：整个查询以预算错误结束，后台子代理停，新委派被拒。错误结果里的用量字段不含触发超限的那次响应（它没完成），但总成本和分模型明细含（它实际发生了）。从账本角度以后者为准，这是"错误结果也算账"的精确版。

预算值本身有校验：零会被启动拒绝（防呆，零预算等于不跑，配错了不如早失败）。

## 估算的边界

所有美元数字都是客户端估算：SDK 内置一份构建时的牌价表，拿 token 数乘出来。它和真实账单的偏差来源：牌价调整后表没跟上（SDK 版本滞后）、模型不在表里（明细里标未知的那些）、计费规则的边角（批量折扣、区域加价）。有一个已建模的规则值得知道：数据驻留场景（推理地理标记为美国之外的某配置）token 单价上浮一成，SDK 会算进去。

结论写死：**这些字段用于监控、归因、预算控制，不用于计费**。要给用户出账单，走官方的用量与成本接口或控制台，那是账单口径。

## 汇总的坑：恢复、多轮与崩溃

做全局成本汇总时三个坑。

恢复会话的重复计算：恢复后的调用，其总成本字段含历史累计。你把每次调用的总成本加起来，历史部分被加了多遍。正确做法：只读最新一次结果的总成本（它总是全量的），或者每段调用记增量（结束减开始）。

流式多轮的节奏：流式输入模式下每轮发一条结果，轮内用量只算本轮主循环，但总成本字段是累计的。汇总逻辑跟着"只读最后一条"的纪律走。清空类操作会重置累计，跨清空汇总要把重置前最后一条单独存下再加总。

崩溃的账：崩溃现场的结果可能字段残缺甚至归零。兜底方案：退回按消息累加（输入和缓存 token 可从消息级恢复），但子代理用量和输出 token 这条路救不回来。监控上给"最后一条健康结果的成本"也留个位置，作为崩溃场景的最近真值。

## 成本工程的三层实践

第一层，观测：每会话结束打一行结构化账（总成本、分模型、缓存占比、轮数、压缩次数），进时序库。跑两周你就有画像：哪类任务贵、贵在哪个模型、缓存健康度如何。没有画像的成本优化都是猜。

第二层，归因：把成本挂到业务维度上。观测篇会讲 OTel 的打标（用户、租户、仓库），成本数据 join 这些维度，你才能回答"这个客户这个月花了多少""哪类任务单位价值成本最高"。分模型明细在这里立功：子代理用高档模型的配置，成本明细里一眼看出。

第三层，控制：预算硬止损（每次调用配额）、并发限制（子代理篇的三个上限）、缓存优化（稳定的系统提示和前缀结构、一小时的缓存时长开关权衡写价）、模型分档（默认低档、关键裁决高档的子代理设计）。四件套按画像出牌。

## 权衡与局限

成本可见性本身有成本：结构化打标和账本落库是基础设施投入，小规模内部工具可以只做第一层观测。预算线是钝器：设紧了误杀长任务（预算错误后 resume 提额重跑的路径要留），设松了失去意义，没有画像就设不准，所以顺序永远是先观测再控制。

局限的诚实清单：估算不等于账单（重申）；消息级输出数是占位（重申）；崩溃丢账（重申）；以及牌价表随 SDK 版本走，升级 SDK 后成本曲线的跳变可能只是换表不是真省钱，做前后对比时把 SDK 版本当控制变量。

## 一个成本优化的真实推演

把账本知识放进一个完整推演。起点：一个仓库分析类 agent，月跑三千次任务，账单显示平均每任务一美元二，团队觉得贵。第一步拉画像：分模型明细显示七成成本在一个高档模型上，消息级数据显示每个任务平均二十五轮、上下文中位水位十二万 token，缓存读取占比只有两成（健康线应该在六成以上）。三个信号指向同一个诊断：上下文常年高位运行，缓存没吃上，每轮都在为大体量输入付钱。

第二步动刀。第一刀砍上下文底盘：工具定义四十多个常驻（tool search 未生效因为走了自建代理回退到全装），改直连后按需装载，底盘从一万八降到三千。第二刀改任务拆分：二十五轮的长任务拆成两段短会话接力（上下文篇的架构），每段水位不超过五万，缓存命中率天然上升。第三刀模型分档：主循环降到中档，仅最终裁决环节保留高档子代理。三刀之后复测：平均每任务四毛一，降了六成五，其中缓存占比升到七成贡献最大。

推演里有三个可复用的判断。缓存的杠杆效应最大且最容易被忽略：水位降一半不省一半的钱（输出价不变），但缓存占比翻倍省的是输入价的大头，优化顺序永远是先缓存后模型后拆分。分模型明细是诊断入口：不知道钱在哪个模型上，后面全是盲调。画像先行再动手：没有基线的优化无法证明有效，"感觉快了"不算数。

## 账本口径与预算的疑问

**预算设多少合适？** 从画像来：平均成本的三到五倍做单任务上限，长尾任务单独评估。设成平均值附近会把正常波动当故障，一次一次手动 resume 提额比预算本身还贵。

**子代理显示的成本能单独出账吗？** 分模型明细只有模型维度，代理维度的拆分要靠遥测打标：观测篇讲的真实代理名记录（内容记录第二级）打开后，成本指标带代理名，按代理聚合就有了。

**同一任务两次跑成本差很多，正常吗？** 正常。轮数受模型当次发挥影响（一次走对路八轮，一次绕路二十轮），缓存受前缀一致性影响。看分布别看单点，成本监控用中位数和九分位。

**恢复会话后预算怎么算？** 预算从零重计（只算本次调用），但成本字段带历史累计。给用户做配额时要想清楚口径：按"新工作"计费看本次增量，按"会话总消耗"展示看累计字段，两个数都要给，标清楚哪个是哪个。

**价格表过时了怎么办？** 看分模型明细里的价目来源标注：标未知的模型成本是按兜底价算的，误差最大。升级 SDK 换新表，升级前后做成本对比时把版本变化记进注脚。

## 一次任务的成本构成解剖

把一个典型任务的账单拆到科目级，建立"钱花在哪"的直觉。任务：修复一个中等复杂度的 bug，跑了十四轮，总成本四毛二。

科目一，输入 token（本次会话非缓存部分）：约三成。这部分是每轮真正新进上下文的内容（新的工具结果、新的用户输入）。它的健康信号：随轮数线性但不指数增长。指数化就是出了问题（比如某工具每轮返回全量数据）。

科目二，缓存写入：约一成。新内容第一次进上下文时按写入价（贵）计一次，之后走缓存读。优化空间小，金额也小。

科目三，缓存读取：约四成。每一轮把命中的历史重发一遍，按读取价（便宜）计。它是占比最大的科目，也是杠杆最大的科目：前缀稳定它就大，配置漂移它就掉。这个科目占比低于五成的会话，先查缓存健康再谈别的。

科目四，输出 token（含思考）：约两成。模型生成的内容和推理。它的优化手段是努力档位（低档少思考）和任务拆分（短任务的收尾总结短）。

解剖的价值在诊断映射：成本异常的会话，先看科目结构再看总额。输入科目畸高是工具返回体积问题（工具篇的落盘分页），缓存读取畸低是前缀漂移问题（提示词或配置不稳定），输出畸高是轮数或思考过度问题（档位或任务定义）。四个科目各对应一类病，总额只是症状。

## 预算的产品化：配额、告警与止损三层

预算选项是引擎给的止损开关，产品化要再包三层。

配额层：业务侧的额度体系（用户每月十美元额度），由你的应用管理，判定在会话启动前（余额不足不发任务）。它比引擎预算细，可充值可结转，是商业规则不是技术规则。

告警层：任务进行中的成本观测。每轮结束从累计成本判断：过半时记一笔日志，触顶前九成告警一次。长任务的烧钱意外多数能在中途被拦下，拦不下至少留了案发记录。

止损层：引擎预算选项兜底（配额的最后一道防线，设为配额余额加少量余量）。它防的是失控场景（agent 陷入循环、子代理失控展开），正常任务永远不该触到它，触到就是事故要复盘。

三层分工：配额管商业，告警管过程，止损管事故。只配止损不做前两层的系统，用户看到的是突兀的预算错误；三层齐备的系统，用户在触底前就收到了提醒。成本体验的差距全在这层包装上。

## 预算产品化的追问

**止损线和配额层的数字要维持什么关系？** 止损层是配额的最后一道防线，值设为配额余额加少量余量，并且要跟着余额变。定死一个不动的止损线，要么在余额充足时提前误杀，要么在余额耗尽后仍然放行，两层数字要一起维护。

**预算触顶后的自动恢复怎么做才稳？** 预算错误的现场捕获会话 ID，判断是否值得续（任务完成度过半且失败原因可修才续），续的方式是 resume 加高预算，同时把已花费额记进任务的累计账（防止反复 resume 绕过配额）。全自动续跑最多一次，第二次触顶说明任务本身有问题，升级人工。

**怎么向非技术的管理层汇报成本？** 用三个数：总账（月成本）、单位（每任务中位成本）、趋势（环比变化）。技术细节（缓存、科目、口径）放附录。管理层的成本焦虑多数来自"不知道钱去哪了"，三个数加一句解释就能覆盖九成疑问，剩下的留给成本归因的明细报表。

**成本数据能用来做容量规划吗？** 能，而且是少数靠谱用法：任务量乘单位成本给出线性外推，缓存健康度给出优化空间上限，两数相减就是"不优化的话下季度多少钱"。把这条外推曲线挂进成本大盘，预算会议上的争论会从立场之争变成参数之争。

**省钱的第一刀砍哪里，如果只能砍一刀？** 砍缓存不健康，不是砍模型。缓存读取占比低于五成的系统，先把前缀稳定下来（提示词版本化、配置不漂移、会话别无谓重启），这一刀通常省两到四成且不损失任何质量。模型降档是第二刀，它省钱但也降智，永远排在缓存之后。这个顺序说穿了很简单：先消灭浪费，再谈节衣缩食。

## 关键要点

- 三级账本：消息级 token（输出数是占位）、结果级总成本与分模型明细、预算止损线。
- 三口径：主循环不含子代理，总成本和明细含整树；并行消息同标识去重；缓存写入读取单列。
- 预算只算本次：恢复不背历史账，清空归零，子代理计入；错误结果的明细含触发超限的那次。
- 美元数是估算不是账单，计费走官方接口；汇总防三个坑：恢复重复计、多轮只读最后、崩溃丢账。
- 三层实践：先观测画像，再业务归因，后预算与缓存与分档控制。
