# Managed Agents：把 harness 也交出去

> 更新日期：2026/10

**TL;DR：** Managed Agents 是 Anthropic 托管的 agent 运行时：agent 循环跑在它的编排层上，每个会话配一个容器当工作区，你的客户端只负责收事件流和发消息。它和 Agent SDK 的分工是托管与嵌入：SDK 你管进程，Managed Agents 它管进程。核心模型是 agent 与 session 两级抽象（agent 定义版本化，session 只带指针）、按结果定义任务（定义交付物与评分标准，循环迭代到达成为止）、凭据放金库在出口代换（沙箱里永远看不到密钥）。目前是测试版能力。

## 一个架构选择题

先回到定位篇的四问，第三问在这里兑现：过程归你还是结果归你。

用 Agent SDK，过程归你：引擎进程在你的基础设施上跑，每一步都在你的掌控和你的运维范围里。前面所有篇幅（托管、存储、安全、观测）都是为这个选择付的工程账。

用 Managed Agents，结果归你：agent 循环交给 Anthropic 的编排层，每个会话在它的基础设施上配一个容器作为工作区（工具执行都发生在容器里），你的客户端退化为两个动作：收事件流、发用户消息。托管篇那笔工程账（进程容量、状态外置、拓扑设计）大部分不用付了，换来的是过程控制力的让渡。

这不是优劣题是匹配题。判断标准在文末的决策框架，先把机制讲清。

## 脑手分离：官方的架构哲学

理解 Managed Agents 最快的路径是它自己的架构叙述：把 agent 系统拆成三个独立接口。脑（模型加 harness）、手（沙箱加工具）、会话（持久的事件日志）。三者之间只有最小假设，任何一个可以独立失败、独立替换。

这个拆法解决的真实问题很具体。早期的全合一容器设计是宠物式运维：容器挂了会话就丢，调试要钻进装着用户数据的容器，企业客户还得拉专线打通网络。拆成三个接口后：容器死掉只是一次工具调用错误，agent 可以重新申请资源重试；harness 崩溃可以从会话日志的最后事件处恢复（日志活在 harness 之外）；上下文管理的策略（压缩、裁剪、缓存优化）留在可替换的 harness 里，会话只保证持久存储。

一个值得玩味的细节是官方承认 harness 会过时：新一代模型不需要上一代 harness 里的补丁（他们举的例子是某代模型的"上下文焦虑"补丁在下一代成了死重）。所以架构上把 harness 做成可替换件，模型进步时换 harness 不动会话。这个"为模型进步留余地"的思路，在长线 agent 系统的设计里相当值钱。

拆分的收益有官方数字背书：容器按工具调用惰性供给（会话不再预付启动成本），首 token 延迟的中位数降了约六成，九五分位降了九成以上。

## 两级抽象：agent 与 session

API 的形状值得单独讲，它是个好设计。

第一级是 agent：创建一次，持有模型、系统提示、工具、MCP 服务器、技能这些定义。对它的每次更新生成一个新的不可变版本。第二级是 session：每次运行创建，body 里只带一个指针（agent ID 加版本号），定义本体绝不上 session。

这个形状的收益：定义与运行解耦，同一个 agent 版本可以被无数 session 复用；版本钉住意味着可回滚、可对比（两个版本各跑一批 session 就是 A/B 测试）；定义的变更不影响进行中的 session（它们钉在旧版本上，跑完自然过渡）。做产品的读者会认出来，这就是镜像与容器、类与实例的关系，被正确地用在了 agent 上。

定义的维护有两种通道：走 API 或 SDK 的配置对象，或者走版本控制的文件（一个专门命令把文件定义同步上去，锁文件记录 ID 映射）。文件通道的意味是定义可以进 git、走评审、随应用发布，把 agent 定义纳入普通软件工程。

## 按结果定义任务

Managed Agents 的任务定义方式与 SDK 有质的不同：不描述过程（先做什么再做什么），而描述结果（交付物长什么样、怎样算达成）。机制上，任务的完成标准通过一个定义结果的事件给出，运行时按评分标准迭代循环，直到结果达标或预算耗尽。

这个模式的适用面有明确边界。适合的形态：交付物可描述可评分的长任务（一份报告、一个修复并通过测试的分支、一次数据清洗），你关心结果不关心路径。不适合的形态：过程即产品的任务（交互式助手、需要人在环审批的流程）、交付物说不清标准的探索（评分标准写不出来，循环就没有收敛方向）。

评分标准（rubric）的写作是这种模式下的核心技能：标准要可机械判定或可一致判定，模糊的标准换来的是循环空转烧预算。这和测试篇的判据写作是同一种手艺，一个用在评估一个用在运行时。

## 内建的控制面

托管运行时把散落在 SDK 各篇的能力收进了统一控制面，挑四个对部署决策影响最大的。

预算是会话级的美元硬上限，触顶时会话进入明确的暂停状态（不是静默死亡），webhook 通知你，续不续是你的决定。这与 SDK 侧预算选项语义对齐，但执行在托管层，更难绕过。

推理地理位置可以钉住（数据驻留合规），这对受监管行业是把 agent 放出去的前置条件。

记忆库是跨会话的持久记忆（独立的能力头），带版本化和脱敏控制。它对应 SDK 侧自动记忆的托管版，但边界更清晰（显式的库而不是散落的目录）。

多 agent 协作是内建的：协调者、会话线程、顾问这些角色有原生支持，不用自己拿 SDK 拼编排。大规模委派（子代理篇说超过几个就该上工作流）在这里是平台能力而不是自建工程。

## 凭据与沙箱：安全模型的两块基石

凭据模型值得专门讲，它是整个安全设计的招牌：**密钥永远不出现在沙箱里**。MCP 认证和其他秘密放在金库里，金库按会话挂载；实际使用时代理在出口处做凭据代换，沙箱内的代码看到的只是"有个代理帮我完成了认证"。git 令牌只在沙箱初始化（克隆、配置远端）时用一次，之后不再可见。

对照安全部署篇看这个设计的分量：SDK 侧要靠你自己搭代理注入（凭据出信任边界那一层），Managed Agents 把这层做成了平台默认。代价是你要信任它的边界实现，收益是你不用自己养这层工程。

沙箱两型：云型跑在 Anthropic 基础设施上，自托管型跑在你自己的基础设施或 VPC 里（一个 worker 进程轮询接入）。自托管型的意义是折中：编排和数据面在墙内，托管的是控制面。数据不能出墙但想要托管运维的团队，这是目前唯一的两全路径。

## 决策框架与现状

SDK 与 Managed Agents 的选择，四条判据。控制粒度：要每步可控（审批回调、钩子、事件流全在手上）选 SDK，按结果验收就够选 Managed。运维预算：愿意养托管篇那套工程选 SDK，不想养选 Managed。数据边界：数据必须全程在墙内的，SDK 自建或 Managed 的自托管沙箱；完全出不去的只能 SDK。任务形态：交互式、人在环的，SDK（托管版的事件流以任务为中心）；长线可评分交付物的，Managed 天生契合。

现状要诚实交代：这是测试版能力（按版本头灰度），已知限制里有一条对客户端工程质量影响很大：事件流没有重放，连接掉线时的现场恢复要客户端自己做（重取事件、按标识去重），挂在待确认工具调用上的掉线甚至可能卡死会话，客户端的重连逻辑要按官方指引写扎实。归档是不可逆的（只读、不能复活），归档的 agent、环境、记忆库不能被新会话使用。选型时把测试版三个字和这些限制摆在一起权衡。

我的判断：对多数团队，两者不是二选一而是分工演进。交互产品和需要深度过程控制的自动化用 SDK（它给你全部旋钮），长线批处理和结果导向任务逐批迁到 Managed（它替你付运维账）。等它出了测试版、事件流补上重放，再重估分界线。

## 选型与迁移的疑问

**已有的 SDK 代码能迁过去吗？** 定义类的资产（系统提示、工具、MCP 配置、技能）迁移是搬运加适配；代码类的资产（自定义工具函数、钩子逻辑）要重新安置：自定义工具改为它支持的定义形态，钩子语义看它控制面的对应物，逐条对照。迁移成本主要在钩子和深度依赖事件流的逻辑上。

**自托管沙箱和 Agent SDK 自建，不都算"跑在自己基础设施上"吗？** 层级不同：自托管沙箱是你的机器当工作区，但 agent 循环（harness）仍在它的编排层，你托管的是手不是脑；SDK 自建是脑和手都在你这边。要的是数据不出墙，自托管沙箱够；要的是连编排逻辑都不出墙，只能 SDK。

**结果导向的循环烧钱怎么办？** 两道闸：会话预算硬上限（触顶暂停）加评分标准的质量（标准清晰循环短）。前者是保险，后者是根治，评分标准写得含糊，多少预算都填得进去。

**多 agent 协作和 SDK 的子代理怎么对应？** SDK 子代理是会话内委派（一棵树），Managed 的协作是会话间编排（协调者带多个 session 线程）。前者轻、在上下文里；后者重、跨会话持久。跨天的多阶段协作在 SDK 里要自己拼会话接力，在 Managed 里是原生形态。

**测试版期间上生产的风险怎么控？** 灰度接入（非核心任务先跑）、双通道备份（同任务保留 SDK 通道可回退）、对它的限制做显式验收（重连逻辑演练、归档不可逆流程确认）。把它当新依赖的常规引入流程对待，测试版标签本身就该触发这套流程。

## 能力映射：SDK 概念在托管侧的对应物

从 SDK 篇幅过来的读者，一张映射表建立坐标系。

工具与 MCP：SDK 的自定义工具和外部 MCP，对应 agent 定义里的工具与 MCP 服务器配置（定义在 agent 级，全会话共享）。技能：同样挂在 agent 定义上，还能从仓库的技能目录发现（文件态资产的延续）。权限与审批：SDK 的回调式人工介入，对应它控制面里的工具确认流（掉线时的会话卡死风险前文点过，客户端要写稳）。会话与恢复：SDK 的会话加适配器，对应它的会话级抽象加平台托管的事件日志（恢复是平台能力不是你建的）。预算：语义对齐（会话级美元上限加暂停态），执行层从你的进程移到平台。记忆：SDK 的自动记忆（文件态、默认开）对应它的记忆库（显式资源、版本化、可控性更强）。

映射表的读法：概念的对应性高，实现的 ownership 全部反转（你建的变成平台的）。迁移评估时按表逐行问一个问题：这个我自建的组件，换成平台版我失去什么控制、省掉什么运维。答案一行一行累计，就是迁移决策的全部材料。

表里没有对应物的也要看清：SDK 的钩子体系（生命周期回调）在托管侧没有等价物，深度依赖钩子的逻辑（审计、消毒、动态注入）是迁移的最大改造点；同样的，托管的内建多 agent 协作在 SDK 侧要自建。两边的最深能力恰好错位，这是"分工演进"判断的依据。

## 观测集成的追问

**它的观测和 SDK 的 OTel 打通吗？** 控制面有自己的状态与事件体系（webhook、状态查询），与 OTel 管道是两套源。接进你的大盘要做一层汇合（两边都按会话标识关联），工程量不大但要计划进去。别假设"上了托管观测免费"，观测的集成永远要自己接线，只是要接的源少了一半（进程层的那些不用你管了）。

## 关键要点

- 分工一句话：Agent SDK 嵌入式（你管进程与过程），Managed Agents 托管式（它管循环，你收结果）；两者是匹配题不是优劣题。
- 架构哲学是脑手分离：harness 可替换、容器可重试、会话日志在 harness 外支撑崩溃恢复；惰性供给容器把首 token 延迟中位数降约六成。
- API 两级抽象：agent 定义版本化不可变，session 只带指针；定义可走文件通道进 git 走评审。
- 任务按结果定义：交付物加评分标准加迭代循环；评分标准的写作质量决定成本，说不清标准的任务不适用。
- 凭据在金库、出口代换、沙箱零密钥；沙箱有云与自托管两型；测试版现状（无事件重放、归档不可逆）要摆进选型权衡。
