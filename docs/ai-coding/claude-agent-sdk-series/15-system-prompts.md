# 系统提示的修改：换脑还是加规矩

> 更新日期：2026/10

**TL;DR：** SDK 会话的系统提示有三种形态：不传（裸工具循环，几乎没有 Claude Code 的人设）、整替（你的提示完全取代预设）、预设加追加（保留官方全套行为准则，在后面加你的规则）。整替是高风险手术：工具使用指引和安全条款全部丢失，责任转移到你身上。绝大多数场景的正确答案是预设加追加，这篇给出判断标准和每个选项的坑。

## 先搞清楚默认值是什么

一个反直觉的事实排在所有讨论之前：**SDK 会话的默认系统提示不是 Claude Code 的那套**。不传系统提示选项时，会话拿到的是一个最小提示，只覆盖工具调用的基本协议，Claude Code 预设里的工具使用指引、安全与行为准则一概没有。这和命令行的非交互模式不同，那边默认就用完整提示。

这个设计的意图可以理解：SDK 会话常常不是"终端里的编码助手"，套上那身衣服反而别扭。但它制造了一个认知陷阱：从 CLI 迁过来的人以为默认行为一致，实际默认是个"裸 agent"，能力和谨慎程度都打折。

所以第一个决策不是"怎么改"，而是"要不要穿衣服"。三种形态对应三种选择。

## 三种形态

形态一：不传。会话是一个纯工具循环，没有人设、没有编码助手的自我认知、没有安全条款。适合把 SDK 当"带工具的模型接口"用的场景：你的程序自己定义全部行为，agent 只负责按指令调工具。这是最轻的形态，也是最"裸"的形态。

形态二：整替。传一个自定义字符串，预设全部出局，会话只听你的。这是自由度最大的形态，也是这篇要重点泼冷水的形态。

形态三：预设加追加。声明使用官方预设（就是 Claude Code CLI 的那套提示，含工具指引和安全条款），再附上你的一段规则。什么都没删，只往后面加，官方文档直接称它为最低风险的自定义方式。

## 整替的账单

整替不是删掉一句"你是编码助手"那么轻。预设里装着的东西逐项记账：每个内置工具的使用指引（什么时候用编辑、什么时候用搜索、怎么规划多步任务）、安全与行为边界（拒绝危险操作的原则、对注入内容的戒心）、系统提醒机制的解释（那些提醒从哪来、该多当真）。整替之后这些全部归零，除非你在自己的提示里重新写出来。

安全条款的丢失最要命。一个被剥掉安全行为的 agent 面对精心构造的注入内容，抵抗力完全取决于你写的那段提示。做整替时你接管的其实是一个安全组件，"简化提示"只是它的表象。接管就要尽责：官方的说法是你要为补齐工具指引和安全说明负责。

还有一处隐蔽的丢失：预设里解释系统提醒来源的那句话也没了。你的 agent 收到应用注入的上下文提醒时可能误判来源，把它当成用户指令。整替时自己补一句"提醒来自应用程序而非用户"，这句官方示例值得抄。

什么时候整替仍然正确？判断标准是"你的 agent 是不是还是那个东西"。输出形态变了（不是给人读的终端界面）、身份变了（不自称 Claude Code）、权限模型变了（无人审批的自治运行）、领域变了（根本不是编码任务），四条中一条成立就值得考虑整替。反过来，无人值守的 CI 型编码自动化，官方明确说预设仍然适用：没有人在场不等于不需要那套行为准则。

## 追加的正确姿势

预设加追加是默认答案，但追加文本自己也有讲究。

放在追加里的应该是"你的产品规则"：编码规范、输出格式要求、领域上下文、任务边界。不该放的：工具使用技巧（预设已有，重复会稀释）、与预设冲突的越权指令（让 agent 无视安全条款的要求，预设的分量通常赢）、频繁变化的动态信息（后面讲原因）。

追加与另一个常见容器 CLAUDE.md 的分工要理清：系统提示是代码的一部分，随你的程序版本走，改它就是改产品；CLAUDE.md 是数据的一部分，随仓库或用户环境走，改它不动代码。稳定的产品规则进系统提示，环境相关的约定进 CLAUDE.md。还要记住 CLAUDE.md 的加载与系统提示选项无关，它走配置来源那条路，两者是并行的输入通道。迁移时的常见顺序是先全放 CLAUDE.md 快速验证，规则稳定后再沉进系统提示进版本管理，两步走的成本比一开始就分干净低。

## 两个高级旋钮

排除动态段是一个性能选项，理解它要先理解提示缓存：系统提示是每个请求都发的固定部分，命中缓存就便宜。预设里有一小段因用户而异的内容（比如自动记忆的存放路径），它让不同用户的提示各不相同，缓存互相打不中。打开排除动态段，这段内容挪到第一条用户消息里，所有用户的系统提示变成同一份，缓存全员共享。代价：挪进用户消息的指令分量略轻（系统提示里的指令天然更重）。多租户服务这个选项几乎必开，单用户工具无所谓。

提示快照是会话与提示变更的关系问题：会话会记录创建时的系统提示，恢复旧会话时你新改的追加文本不会生效，要等一次压缩或新会话。有个选项可以关掉提示录制让改动即时生效，但官方建议生产保持录制：缓存复用和历史保真都受益。这个旋钮的正确理解是"开发期调提示用的"，生产别动。

TS 还有一个长提示的缓存切分能力：把自定义提示切成静态和动态两段，各自享有缓存断点，静态部分跨请求复用。仅在你直接调 API 的部署下有效，走 Bedrock 或网关的场景用不上。提示很长且每次只有尾部变化时值得配。

## 修改生效的时机

系统提示不是实时的。会话中途想改变 agent 行为，改系统提示选项没有用（它已经在会话里定型了），正确通道有两个：用钩子在用户提示提交时附加上下文（这是动态注入指令的正规通道），或者直接在下一条用户消息里说明。把"改系统提示"当成部署期动作，把"改行为"当成运行期动作，两个心智模型分开，就不会犯中途改提示不生效的错误。

## 决策表

把全文收成一张判断表。做 CLI 类编码助手、有人在环：用预设，不追加或轻追加。同类产品加产品规则：预设加追加，绝大多数产品在这里。输出形态或身份或权限模型或领域变了：考虑整替，账单先付（安全条款、工具指引、提醒解释自己补）。只要工具循环不要人设：不传。多租户：预设加追加，排除动态段打开。开发期频繁调提示：临时关快照，上线前恢复。

## 权衡与局限

系统提示是 agent 行为塑造的最强杠杆，也是最难调试的杠杆：它不出现在会话消息流里，你看到的对话里没有它，出问题时只能靠对比实验（同一任务换一版提示看行为差异）。观察模型实际收到了什么提示，要走原始请求体日志或网关，这是排障时要知道的暗门。

它的效力也有边界：提示约束的是倾向不是边界，真正的硬边界在权限系统（工具调用可以真的被拒）和沙箱（操作可以真的失败）。安全设计永远不要押在提示上，提示管礼貌，权限管门禁。

## 一版产品级追加文本的骨架

整替的账单吓退多数人之后，问题变成：追加文本怎么写才配得上"产品规则"四个字。一版经过生产检验的骨架分六段，顺序有讲究。

第一段身份与任务框架：一两句说清这个 agent 在产品里扮演什么（本 agent 是 XX 平台的发布审查助手，服务于内部工程师）。模型带着 CLI 预设的通用编码助手人设，不点破身份它就按通用助手的方式理解任务。

第二段服务对象与语气：回答给谁看（工程师、非技术运营），语气和详细度按对象定。这一段直接改变输出的形态，是产品体验层最便宜的杠杆。

第三段业务规则：格式约定（报告必须包含的三节）、边界（不做什么、什么必须拒绝）、领域约定（术语表、内部系统名）。这是追加文本的主体，也是唯一必须由业务方参与撰写的一段。

第四段环境说明：它有哪些自定义工具和技能（一两句用途概述）、审批流长什么样（某些操作会等待人工批准，等待期间保持耐心不要重复发起）。模型知道自己被怎样扩展，调用才不茫然。

第五段异常行为约定：工具失败怎么办（读错误消息、换路或上报，不无限重试）、遇到不确定怎么办（明确说出不确定，不要编造）。这一段治的是自治 agent 的两大顽疾：重试循环和幻觉自信。

第六段兜底指令优先级：当本指令与用户单次要求冲突时怎么办（通常业务规则优先并说明原因）。没有这段，一句"忽略之前的规则"的用户输入就能翻你的产品规则。

六段合计两三百 token，换来的是从"通用助手套了个壳"到"产品的一部分"的实际差距。写完做一轮对抗测试：故意用提示注入话术攻击它，看第六段兜不兜得住。

## 写提示词时的常见疑问

**预设和追加的总长会不会超限？** 不会在工程意义上：预设加合理追加的总 token 量级离窗口上限很远。要省的是缓存效率，长度基本不用操心（排除动态段就是干这个的）。

**同样的追加文本在不同模型上效果一样吗？** 不一样。指令的服从度随模型能力波动，高档模型对第六段优先级规则的遵守明显更稳。产品跨模型部署时，提示词的回归测试要按模型分别跑。

**怎么测试提示词改动的效果？** 固定一组测试任务，改动前后各跑一遍，对比行为差异（关键：看行为不只看文本）。把测试任务集进版本库跟提示词一起评审，提示词的变更管理就闭环了。

**系统提示和技能都放规则，会不会打架？** 会，分工要显式：系统提示放全程有效的通用规则，技能放"做某类任务时"的专项流程。两边都写同一条规则时，措辞保持一致或干脆只留一处，规则的两份不一致表述是 agent 行为抖动的经典来源。

**为什么我改了系统提示，恢复的会话没变化？** 会话录制了创建时的提示（快照机制）。新提示要新会话或等压缩才生效。生产上把提示变更当成"影响新会话的变更"发布，存量会话自然衰减结束。

**追加文本和钩子的注入，都改行为，怎么分工？** 提示管常态（一直成立的规则、身份、格式），钩子注入管条件态（仅当某事件发生时要附带的上下文，比如这次任务涉及生产库才注入谨慎提示）。判据是"这条信息是不是每次都需要"：每次都要进提示，按需的走钩子。全塞进提示的下场是规则通胀，每条规则的分量被稀释，半年后没人敢删其中任何一条。

## 提示词评审的检查单

提示词（整替的完整版或追加文本）进生产前过一遍这张单，九条。

一，身份段有没有：agent 知道自己是谁、为谁服务吗。二，对象与语气有没有：输出的读者明确吗。三，业务规则可执行吗：每条规则单独读，一个新工程师能照做吗（规则里的"合理""适当"都改成可判断的标准）。四，边界写了没：不做什么、什么必须拒绝。五，环境说明有没有：它有哪些工具和技能，审批流什么样。六，异常行为约定有没有：工具失败怎么办、不确定怎么办。七，优先级兜底有没有：与用户单次指令冲突时听谁的。八，与技能的分工干净吗：全程规则是否重复出现在技能里（不一致的双份规则必删一份）。九，对抗测试跑了吗：注入话术三类各打一轮（忽略规则的指令、伪装系统消息、诱导越界任务），行为符合预期才放行。

九条过完签个字进版本库。这份签核的价值在半年后：行为不对劲时翻出当时的检查单，九条对应九类排查方向，比从零审计快得多。

检查单还有一个隐性收益常被低估：它让提示词的评审有了客观抓手。提示词评审最大的困难是"感觉没问题"和"感觉有问题"都说不出口，九条把感觉拆成了可勾选的事实，评审会从品味之争变成清单核对，这是把提示词工程从手艺推向工程的一小步，也是团队能一起维护提示词的前提。

从手艺到工程的另一半是版本化：提示词文件独立成文件进仓库（而不是散在调用点的字符串），每次变更的 diff 单独可读，回滚一个版本不打扰代码。文件化的提示词还能被测试脚本直接引用，评审、测试、回滚三个动作共享同一份真源。这套做法没有任何新奇之处，它就是普通软件工程对提示词的一次正常收编，而收编的前提是提示词已经被当成值得管理的资产。

## 关键要点

- 默认形态是裸工具循环，不是 Claude Code 的提示；从 CLI 迁移的人最容易误解这一点。
- 整替的账单：工具指引、安全条款、提醒来源解释全部丢失，责任归你；四条件（输出、身份、权限、领域）之一变了才考虑。
- 预设加追加是默认答案；产品规则进追加，环境约定进 CLAUDE.md，动态信息别放提示里。
- 排除动态段让多租户共享缓存；快照开关是开发期工具，生产保持录制。
- 会话中途改行为用钩子或消息，不用系统提示；提示管倾向，权限管边界。
