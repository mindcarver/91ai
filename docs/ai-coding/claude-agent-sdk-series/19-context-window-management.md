# 上下文窗口管理：长跑 agent 的生存术

> 更新日期：2026/10

**TL;DR：** 上下文是 agent 最宝贵的不可再生资源：任务历史、工具结果、文件内容、规则文件全在里面挤。窗口逼近上限时引擎自动压缩（旧历史摘要化、近期保留），压缩有边界信号、有丢失风险、有前置钩子。SDK 程序员的手里牌包括：子代理隔离脏上下文、技能与工具搜索的按需装载、努力档位、还有"把蒸馏做成架构"的短会话模式。这篇把增长、压缩、节流、架构四层讲全。

## 上下文是怎么涨起来的

一次会话的上下文从四个来源增长。系统提示和工具定义是固定底盘，会话开始就占掉一块，工具越多底盘越大（工具搜索篇的那笔账）。任务对话随轮数线性涨。工具结果是最大变量：读一个大文件、查一次大表，几千 token 一口吞进历史。规则文件（CLAUDE.md 们）按配置加载，常驻不走。

增长的结构性问题在于它是累积的：上下文不随任务推进自动瘦身，第三轮读的文件到第三十轮还躺在历史里，哪怕它早就无关了。窗口的消耗像一条只涨不跌的水位线，长任务的死法几乎全是水位触顶。

触顶会怎样？引擎的自动压缩机制接管：把较早的历史摘要成一段总结，近期交流保留原文，压缩边界以系统消息的形式出现在流里。会话继续，但历史"变质"了：从逐字记录变成了概要。这是官方设计的生存机制，不是故障，但它的副作用必须当成设计约束来管理。

## 压缩的语义与代价

压缩的语义一句话：**旧消息被摘要替换，细节不可逆地丢失**。摘要保留了任务主线和关键结论，丢掉的是过程细节：某次搜索的完整结果列表、某段代码的精确内容、某个中间推理。压缩后 agent 对早期工作的"记忆"是概要级的，你问它"第三步那个报错的完整堆栈"，它可能只能复述"有个堆栈错误"。

由此推出第一条设计纪律：**持久重要的信息不能只存在于对话历史里**。早期的关键决策、重要的中间产出，要么实时落到文件（让 agent 写下来，文件在需要时可重读），要么由你的程序从事件流里捕获存库。历史是工作内存不是硬盘，压缩随时可能清内存。

第二条纪律关乎规则的位置：要在全程生效的规则，必须放在每次请求都会重新注入的地方，也就是 CLAUDE.md 或系统提示，因为它们在压缩后依然完整在场；放在早期对话消息里的指令，压缩后只剩摘要里的一缕残影。官方文档明确建议把持久规则写进 CLAUDE.md 让压缩器在摘要时参考，同一个道理。

压缩的定制面有三个。摘要的倾向可以用指令引导：在规则文件里写压缩时要保留什么（关键决策、错误教训、格式约定），压缩器会读它。压缩前有钩子可以介入（区分手动与自动触发），做归档、审计、快照都行。手动压缩也存在，你的程序可以在任务阶段间隙主动触发，把压缩点选在语义干净的位置（一个子任务刚完成），而不是让自动机制在任务中途硬切。

## 节流：让水位涨得慢

压缩是最后手段，节流是日常功课。按性价比排序。

子代理隔离是最大的一张牌（子代理篇的视角换到上下文）：把高消耗的调研型子任务委派出去，子代理内部读的一百个文件全部留在它自己的上下文里，主会话只收摘要。脏上下文隔离在子代理，主上下文保持干净低水位。会话篇讲的"两本账"在这里有了第三个维度：子代理不光分摊成本，还保护主上下文的生命周期。

按需装载是第二张：技能正文调用时才进上下文，工具定义经工具搜索按需装载，两条机制前面各自成篇。共同原理：把"可能需要"和"现在需要"分开，只付现在的钱。

输出控制是第三张：工具结果的体积直接可控。自定义工具返回摘要加文件路径（大结果落盘），外部 MCP 的超限自动落盘机制，配置查询类任务让工具分页返回。每省一千 token 的工具输出，就是历史里少一千 token 的常驻负债。

模型与档位是第四张：努力档位影响思考深度（也影响某些场景的 token 消耗），模型的选择决定窗口大小本身。长任务的模型选型里，窗口容量是和智能并列的硬指标。

## 架构：短会话与蒸馏

节流和压缩都在"单会话尽量活长"的框架里。更激进的架构反过来：接受会话是短的，把连续性建在会话之外。

短会话模式的运转方式：一个任务或一个任务阶段一个会话，完成即提取产物（结论、产物文件、给下一阶段的交接摘要），下一阶段新会话带交接摘要起步。会话历史从"几十万 token 的连续体"变成"每段几万 token 的接力棒"。

它的收益是复合的：每段会话都在低水位高质量区运行（无压缩损失），提示缓存命中率高（短且稳定的上下文），出错隔离（一段坏了不影响下一段），成本可按段归因。代价是交接摘要的设计要花心思（漏了什么下一段就缺什么）和会话管理复杂度上升。

两种架构不是信仰之争，判据是任务的连续性密度：强连续（全程反复引用同一批早期细节）用长会话加压缩管理；弱连续（阶段间只需结论传递）用短会话接力。真实系统常是混合：主干短会话接力，个别强连续段内部允许长会话。

## 观测：知道水位在哪

管理的前提是观测。三处水位信息可用：每条消息的用量字段告诉你本次请求的输入输出规模（输入规模就是当前水位的近似），压缩边界消息标记每次压缩事件（一次会话压缩了几次是最重要的健康指标），初始化消息里能拿到窗口的基准信息。把"压缩次数"和"会话结束时的输入规模"打进日志，跑一周就有你自己的任务画像：哪类任务水位涨得快、压缩集中在哪个阶段、该给哪类任务上子代理隔离。

这套观测也是成本观测（成本篇详谈），一鱼两吃。

## 权衡与局限

上下文管理没有银弹，每张牌都有反面。子代理隔离引入信息损耗与协调成本；按需装载增加调用延迟与不确定性；输出落盘把检索负担转嫁给后续轮次；短会话接力把复杂度转移到交接设计。工程的做法是组合拳按任务画像出牌，而不是把一张牌当信仰。

局限里最重要的一条：压缩机制本身不可完全关闭也不可完全控制（可以引导不可指定），摘要质量依赖模型当时的发挥。把"压缩后细节丢失"当成概率性必然事件来设计（重要信息出历史、进文件），比指望压缩器聪明可靠得多。

## 一个长任务的上下文账本

用贯穿案例把机制变成数字。任务：发布前全量回归审查，涉及读四十个文件、跑测试、核对依赖变更、写审查报告。窗口按二十万 token 算，先看不管不顾的跑法。

底盘先扣掉：系统提示加工具定义（三十个工具全装）两万，项目规则文件八千，起步水位两万八。第一步读文件：四十个文件平均每个两千 token，八万进历史，水位十万八。第二步跑测试：五轮测试的输出每轮三千，一万五，水位十二万三。第三步核对依赖：又读一批配置文件，三万，水位十五万三。第四步写报告时水位已过十七万，自动压缩触发，前两步的细节摘要化，agent 写报告时对那四十个文件的记忆只剩概要，报告里的"逐文件结论"开始编（它不记得细节但不承认不记得）。

再看过管理的跑法。底盘砍掉：工具搜索生效，底盘降到六千。第一步改成子代理委派：一个审查子代理读四十个文件产出结构化结论清单，主会话只收五千 token 的清单，子代理的八万留它自己的上下文里。第二步照旧。第三步的依赖核对再委派一个子代理，主会话再收三千。第四步写报告时主会话水位六万出头，无压缩，四十个文件的结论在清单里逐条可查，报告有据可依。同样的任务，一个触发压缩靠摘要写报告，一个全程原文水位运行，质量差异就出在账本管理上。

这个账本的可迁移结论有三条。委派的本质是上下文外包：把"过程很重、结论很轻"的步骤整体搬走。产物即记忆：让子代理的产出落成文件或结构化清单，主会话需要细节时重读文件而不是依赖历史。底盘是最容易砍的：工具和规则的常驻成本每轮都在付，一次优化长期受益。

## 水位与压缩的疑问

**怎么知道我的会话离压缩还有多远？** 消息级输入 token 数就是当前水位的近似读数，除以窗口容量得占比。做成面板常驻展示，团队对水位的感觉会从玄学变成数感。

**压缩后 agent 变笨了是我的错觉吗？** 不是错觉，是摘要化损失。判断标准：压缩后追问早期细节，它的回答是概括性的、缺少具体数字和名字的，就是丢了。解法不是问它，是让它重读当时的产物文件。

**子代理的结论清单怎么设计才不丢关键信息？** 清单的粒度按"主会话后续还要不要用"设计：后续要引用的（文件、行号、结论、置信度）显式成列，过程推理一概不要。清单本身就是一次蒸馏，蒸馏的纯度决定主会话的质量。

**短会话接力的交接摘要写什么？** 三样：已完成什么（结论与产物路径）、未完成什么（卡在哪、为什么）、下一阶段的输入与注意事项。写给自己不写给用户，格式服务于下一段会话的第一轮就能上手。

**窗口大的模型还需要这些吗？** 需要，换算比例而已。窗口大十倍，任务复杂度也会涨上来（更大的仓库、更多的并行子任务），水位管理的纪律从十万窗口到百万窗口是同一套。区别只在触发线远了两档，多出来的侥幸空间，恰恰是最容易出事的地方。

## 压缩现场的处理手册

自动压缩发生时（压缩边界消息出现），宿主程序和用户各有一套动作要做。

宿主程序的四步。第一步记账：压缩计数加一、压缩时的水位记下。这是健康指标，超过两三次的会话该考虑拆分。第二步校验关键锚点：压缩后立即让 agent 复述一次关键约束（当前任务目标、不可违反的规则），复述漂移说明压缩摘要丢了重点，要么把规则挪进 CLAUDE.md（每次请求重注入），要么蒸馏重启。第三步检查产物依赖：压缩后 agent 若要引用早期读过的文件，指示它重读文件而不是回忆。第四步评估拆分时机：压缩是拆分的天然信号，任务有阶段边界就现在拆。

用户侧（如果产品有对话界面）的一段话要透明：长任务的上下文已自动整理，较早的细节以摘要形式保留。用户对"它忘了前面说过什么"的愤怒，一半来自没有预期，给了预期就变成可理解的行为。

手册之外有两条预防。压缩前钩子里把关键状态快照（当前任务清单、已确认的决策）写进文件，压缩后 agent 重读快照接续，等于给摘要加了一份保险。规则文件里写好压缩指引（保留哪些），让压缩器摘要有据可依。预防做得好，压缩现场的处理就从抢救变成例行。

## 常用组合的速查

几个经过验证的组合配方，按场景取用。

长文档分析型：委派加落盘。子代理读全文产出结构化笔记落盘，主会话持笔记工作，细节需要时按笔记的行号引用重读原文片段。主上下文全程只有笔记体积。

多轮迭代型（改代码跑测试循环）：产物即锚点。每轮的代码状态在文件里（本来就在），历史里只留结论性的轮次摘要，工具输出大的（测试日志）落盘给路径。水位随轮数增长得极慢。

探索调研型：阶段蒸馏。每个探索方向一个子会话，产出一段结论，主会话只汇总结论。方向之间的独立性天然适合这种结构，主上下文约等于一份综述的体积。

持续服务型（常驻 agent）：定期蒸馏重启。每天低峰期把会话蒸馏成接续摘要，新会话携摘要接班。常驻会话的水位曲线从锯齿状攀升变成平稳波动。

四类配方覆盖了多数长任务形态，共同的底层动作只有两个：让重内容留在会话外（文件、子代理），让会话内只留轻结论。所有上下文管理的花样，都是这两个动作的组合。

配方之间也可以叠着用：长文档分析打底、多轮迭代做主干、探索调研派分支、持续服务定节奏，一个产品 agent 往往四样全占。起步时按主导形态选一个跑起来，等观测数据（压缩次数、结束水位）说话了再叠加下一个，比一开始就上全套稳当。

最后补一条与人协作的纪律：上下文管理对用户要透明。蒸馏重启了、子代理代劳了、历史被摘要了，这些动作用户无感知时，"它怎么忘了昨天说的事"的工单就会来。产品文案里一句话的成本（长任务的细节会定期整理归档，关键结论始终保留），省掉一轮客服。技术问题解决了，预期问题还得靠沟通解决，这步没有工具能代劳。

## 关键要点

- 上下文四来源只涨不跌：固定底盘、对话、工具结果、规则文件；长任务的死法是水位触顶。
- 压缩语义：旧历史摘要化不可逆；重要信息实时出历史进文件，持久规则放 CLAUDE.md 或系统提示。
- 节流四张牌按性价比：子代理隔离脏上下文、按需装载、输出落盘分页、模型与档位。
- 架构分两路：强连续任务长会话加压缩管理，弱连续任务短会话加蒸馏接力；真实系统混合用。
- 观测看两处：压缩次数和结束水位，跑出任务画像再决定给谁上什么牌。
