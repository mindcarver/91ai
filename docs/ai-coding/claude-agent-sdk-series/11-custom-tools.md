# 自定义工具：把你的系统能力交到 agent 手里

> 更新日期：2026/10

**TL;DR：** 自定义工具是 SDK 最核心的扩展点：在你自己的进程里定义工具函数，包成一个进程内服务器传给会话，agent 就能像调内置工具一样调用你的数据库、你的内部 API、你的业务逻辑。定义由名字、描述、输入 schema、处理函数四件套构成；返回内容支持文本、图片、结构化数据；错误处理有一套"报错给模型看"的专门语义。写好它的关键是把描述当提示词写、把 schema 当接口设计。

## 为什么这是最核心的扩展点

内置工具解决的是通用问题：读文件、跑命令、搜网页。你的 agent 要解决的是你的问题：查你们的订单系统、调你们的发布接口、走你们的审批流。这些能力模型一无所知，工具定义是你向模型描述这些能力的唯一渠道。

其他扩展方式各有短板。让 agent 用 Bash 调你们的命令行工具，能力上可行，但每次调用都要 agent 现学命令语法，出错率高，权限也没法按业务语义收窄。架一个外部 MCP 服务器，功能完整但要独立进程、独立部署。自定义工具走中间路线：函数写在你自己的代码里，进程内直接调用，没有序列化到外部进程的开销，没有额外部署物，同时保持了 MCP 的工具定义标准，模型看到的就是规范的工具接口。

贯穿案例：给一个客服 agent 配一个查订单工具。输入是订单号，处理函数调内部订单 API，返回订单状态、物流、退款记录。agent 拿到用户"我的包裹到哪了"的提问，自己决定调这个工具，拿结构化结果组织回答。这个十行函数就是自定义工具的全部形态。

## 四件套：定义的解剖

名字要当唯一标识起。完整形态是三段式：服务器名加工具名（形如 mcp__订单__查询订单），因为工具都挂在一个进程内服务器下，服务器名是你传给会话时的命名空间。想免审批就在允许列表里写完整名，整服务器的通配符也行。

描述要当提示词写。模型完全靠描述决定什么时候用这个工具、期望它返回什么。描述写"查询订单"和写"根据订单号查询订单的当前状态、物流轨迹和退款记录，用户询问包裹进度、退款进展时使用"，调用的准确率差一个量级。写描述的时间是整个工具开发里回报率最高的投入。

输入 schema 是模型填表的表格。两门语言的写法不同但产物一样。TS 用 schema 库链式定义，字段可以逐个加说明，可选字段标出来。Python 有两档：简单类型标注（字典里名字对类型）够用于基础场景，但表达不了枚举和可选，要这些就得手写完整 JSON Schema。一个 Python 特有的坑：类型标注字典里每个字段都是必填语义，想要默认值就在处理函数里自己补。

处理函数是真正干活的地方。拿到模型填好的参数，执行你的逻辑，返回结果。异步没问题，长任务没问题，你的函数能干什么，这个工具就能干什么。

## 返回内容的形态

返回的第一选择是文本块，给模型读的描述性内容。但返回能力远不止文本，四类内容可以混搭。

图片可以内联返回：字节数据加类型字段。可用的格式是四种常见图片格式，其他格式引擎不会当视觉输入，而是存到磁盘把路径当文本回给模型，模型只能引用不能看。这条规则影响设计：给模型看截图必须转成受支持的格式，给它看超长报表反而可以存盘给路径省上下文。

资源块适合返回"一块有标识的数据"，文本或二进制内联携带。注意它的标识字段只是标签，引擎不会按它去读东西，取数逻辑在你自己的函数里。

结构化字段返回机器可读的 JSON。这给了你一种两段式设计：结构化字段给宿主程序消费（你的代码在工具层拦截或后处理），文本块给模型消费（组织回答）。有一个机制细节要记：设置了结构化字段时，文本块会被引擎丢弃（默认它们是重复内容），只有图片和资源照常转发。这个默认对，但你要知道它存在，别写了半天文本奇怪为什么不出现。

Python 和 TS 在返回支持上有一处不对称：音频块 Python 侧直接丢弃（带警告），TS 侧存盘给路径；二进制资源 Python 侧不转发。用富媒体返回前先查你这门语言的支持面。

## 错误的专门语义

工具报错有两档，语义完全不同，这是自定义工具最容易写错的地方。

第一档：函数抛异常，你不接。引擎接住它，把原始异常信息包装成错误结果回给模型。能用，但原始异常信息往往是堆栈和内部细节，模型读不懂也用不好，更糟的是可能把内部路径、连接串带进对话。这一档永远不该出现在生产代码里。

第二档：函数接住异常，返回"这是一个错误"的标记加你自己写的错误消息。你的消息是写给模型的提示词："订单号格式不对，应为 10 位数字"或"订单服务当前不可用，建议告知用户稍后再试，不要重试超过两次"。模型读得懂的错误让它能合理决策：换个参数重试、放弃并解释、或者问用户。错误处理的核心认知：工具错误是写给模型的指令。你的程序该接的异常已经接完了，这条消息的读者是模型。

错误永远不终止 agent 循环，这是有意的设计。工具失败是 agent 的常态工作条件，它要能在部分工具失效的世界里继续完成任务。

## 并发标注与上下文经济

标注里最重要的一个是只读提示。标了，引擎才敢把你的工具和其他只读调用并发执行；不标，一律串行。标注是元数据不是强制，标错了引擎不报错，但并发安全就破了。纪律：函数只读才标只读，有一丝写操作就不标。

工具定义要吃上下文，几十个工具的 schema 是可观的 token 开销。引擎的工具搜索机制默认把工具定义按需加载（发现篇细讲），你的自定义工具自动受益。个别必须随叫随到的关键工具，可以标记为始终加载，代价是常驻上下文。这个标记的判断标准是"延迟敏感度"：查订单这种对话中间环节的工具值得常驻，周报生成那种低频工具让它按需。

参数的流式输入是个进阶能力：工具参数还没在模型那边生成完，你的函数就能开始收到已生成的部分。对参数巨长的工具（生成大文件、长文本）这能把等待时间藏进生成时间。这个开关默认关闭，按工具打开。

## 自定义工具还是外部 MCP

同一个能力两条实现路线，判断标准有三条。

进程归属：能力属于你的应用本身（查你的内存状态、调你的内部函数），自定义工具天然合适，函数就在你进程里。能力是独立服务（公司统一的数据库网关），外部 MCP 更合理，谁都能连它，不必经你的应用转发。

生命周期：工具随你的应用起停，用自定义；工具需要独立部署、独立升级、被多个应用共享，外部服务器。

凭据边界：你的应用已持有的凭据，函数内直接用，自定义工具省事；需要独立凭据轮换和授权流转的，外部服务器的认证体系更完整。

两条路线不是二选一，成熟系统通常混合：业务核心能力自定义（近、快、私有），通用能力外部（共享、标准）。好在两者对模型来说都是 MCP 工具，模型侧无差别，切换实现不影响 agent 行为，路线选择因此保持可逆，前期选错也不必推倒重来。

## 权衡与局限

自定义工具把你的代码放进了 agent 的决策路径，可靠性要求随之而来。工具函数的挂起会挂起 agent（引擎在等结果），无限循环的工具函数就是无限挂起的会话，耗时任务要么设内部超时要么设计成提交后轮询的模式。工具的吞吐也成了系统的吞吐：并发二十个会话每个都在调你的数据库函数，你的连接池规划要跟上。

另一个局限是描述的维护成本。接口演进时 schema 和描述要同步更新，过时的描述比没有描述更糟：模型按旧描述调用，参数对不上，错误信息又没写好，agent 陷入重试循环。把工具的描述和 schema 当公开 API 文档对待，变更走评审。

## 一个工具从需求到上线的全程

用查订单工具的增强版走完全程，看每一步的判断点。

需求确认：客服场景要查订单。追问一句：还要改订单吗？答案决定工具的读写性质（改单是写工具，并发语义、权限设计全不同）。本例只读。

设计参数：订单号是必填参数。要不要加个可选的"包含退款明细"开关？判断标准：两段数据总是被一起用就别拆参数（模型少一次决策），经常分开用才拆。描述里写清参数格式（十位数字），模型填表的错误率降一档。

设计返回：订单主体（状态、物流轨迹、时间戳）加退款记录数组。数据可能缺失的（无退款记录）怎么表达：空数组还是字段缺省？定空数组（调用方逻辑简单），写进描述让模型稳定产出空数组。

错误设计：订单号格式错、订单不存在、服务不可用三种错误，各自写一句给模型的提示词。第三种特别写了"不要立即重试"（服务抖动时的重试风暴是客服场景的常见事故）。

权限与并发：只读工具标只读提示进并发档；允许列表加上它的全名，客服场景免审批。

观测与迭代：上线后从事件流统计调用成功率、参数错误分布、平均返回体积。参数错误集中在同一字段说明描述不够清楚，改描述（描述就是提示词，迭代成本低）。返回体积大就考虑落盘改路径。

六步全程的关键认知：工具是产品，有需求、有迭代、有退役（调用率归零的工具从允许列表和服务器里下掉，工具面只进不出是另一种膨胀）。

## 工具作者的实际疑问

**工具函数里能再调别的 agent 吗？** 能（函数里什么都能做），但想清楚再这么做：工具阻塞期间 agent 在等，嵌套 agent 的时延全算进这一轮。慢操作的正确模式是提交加轮询：工具立刻返回受理号，agent 后续用查询工具取结果。

**同一个工具想给不同租户返回不同数据怎么办？** 工具函数运行在你的进程里，天然拿到会话上下文（你调用 SDK 时自己传的关联信息）。租户路由在函数内部做，对模型完全透明：一个查订单工具，内部按租户查不同的库。

**模型总在错误的时机调这个工具，怎么改？** 三层排查：描述是否清晰（最常见，把"什么时候用、什么时候别用"都写上）；参数是否太模糊（模型猜不准所以乱试）；是不是该配技能（复杂流程里工具的正确用法靠技能教，不靠描述硬扛）。

**返回的图片模型真的会看吗？** 会，四种受支持格式的内联图片作为视觉输入进模型。但注意成本：图片按视觉 token 计费，高频返回截图的工具账单会说话。给模型看图用在必须视觉判断的场景（UI 截图对比），文字能表达的用文字。

**工具超时了 agent 会怎样？** 工具函数一直不返回，agent 一直等。函数内部必须有超时（外部调超即返回错误结果），引擎不会替你掐断自己的函数。这是自定义工具与外部 MCP 的一个差异：外部调用有工具超时环境变量兜底，进程内函数的超时纪律靠自己。

## 工具命名与组织的章法

工具上量后，命名从偏好变成工程问题。三条章法。

命名的一致性模板：动词加对象（查订单、取库存、建工单），团队内一个模板贯彻。模型对命名模式的泛化能力很强：三个"动词加对象"的新工具，它没读过描述也能猜个八成用途。反过来，混杂的命名风格（getOrder、fetch_inventory、拿数据）各自消耗模型的猜测预算。

服务器名当领域名用：自定义工具都挂在进程内服务器下，服务器名是命名空间，把它命名为业务域（订单服务、库存服务）而不是技术层（api-server）。工具全名 mcp__订单__查询订单 里两段都在教模型这是什么。

一族工具一起设计：发现要查订单时，顺带问改订单、退订单要不要也做。一族工具共享参数词汇（都用订单号字段名）和返回风格（都用同样的状态枚举），模型学一族比学三个孤立工具快。孤立设计的工具凑到一起，词汇表打架（order_id 和 orderId 和 单号），误调用率悄悄上升。

章法的检验方法：把你的工具全名列表打印出来遮住描述，让同事猜用途。猜得准的命名体系是给模型的礼物，猜不准的先修名字再修描述；这一步花十分钟，比上线后翻误调用日志便宜得多。

工具家族的最后一条军规写给下线：工具退役要像 API 下线一样走流程（公告、观察期、移除）。直接删工具的现场是 agent 在调用一个不存在的工具，错误消息里它一脸无辜。观察期里先从描述里标注弃用（模型会自然少用它），流量归零再删，对模型优雅、对你无损。

## 关键要点

- 四件套：名字是标识、描述是提示词、schema 是表格、函数是引擎；描述质量决定调用准确率。
- 返回四类内容可混搭；设了结构化字段文本块会被丢弃；图片限四种格式，其他存盘给路径。
- 错误两档：未接的异常把内部细节漏给模型，正确做法是接住后写给模型看的错误消息；错误不终止循环。
- 只读标注决定能否并发，标错不报错但破坏安全；关键工具标始终加载，长参数工具开流式输入。
- 路线判断三条：进程归属、生命周期、凭据边界；两者对模型无差别，可混用。
