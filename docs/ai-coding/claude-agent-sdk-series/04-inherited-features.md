# 白得的功能：SDK 从 Claude Code 继承了什么

> 更新日期：2026/10

**TL;DR：** 用 Agent SDK 起一个会话，引擎默认会把 CLI 的整套文件态配置一起加载进来：CLAUDE.md、自定义命令、Skills、hooks、子代理、MCP 服务器、自动记忆。总开关是 settingSources，默认全开，设成空数组才隔离。还有四样东西不归这个开关管，包括自动记忆和托管策略。继承面是 SDK 最大的红利，也是多租户服务最大的暗坑，这篇把清单和边界一次盘清。

## 从一次诡异的行为排查说起

设想这样一个排查场景：你在 SDK 里起的 agent 总是先输出一段中文项目说明再干活，你从没在代码里写过这段话。查了系统提示选项，是空的；查了任务描述，没有它。折腾半天才发现，是你机器上 ~/.claude/CLAUDE.md 里一个月前随手写的一段规则，被这个会话默认加载了。

这类问题不会发生在你新写的代码里，会发生在你看不见的继承面上。SDK 的会话不是从零开始的裸 agent，它默认穿着 CLI 的全套衣服。衣服里有些是你想要的（Skills、hooks），有些是历史遗留（你个人的配置文件），有些是安全要求（企业托管策略）。把它们盘清楚，是 SDK 工程化的第一步。

## 总开关：settingSources

继承的大门只有一个选项：settingSources（Python 写作 setting_sources）。它决定会话从文件系统的哪些位置读配置。不传它时，行为等价于列出全部三个来源：user、project、local。

三个来源分别是：project 读当前工作目录下的 .claude 及其父目录（适合放项目级规则和团队共享配置），user 读用户主目录的 ~/.claude（你个人的全局偏好），local 读 CLAUDE.local.md 和 settings.local.json（不进版本库的个人本地覆盖）。CLI 用户对这三层应该眼熟，SDK 会话读的就是同一批文件，连层级叠加的行为都一致。

把 settingSources 设为空数组，三处全部断开，会话只剩你在代码里传的选项。这就是嵌入式部署的"干净模式"：agent 的全部行为都来自你的程序，宿主机器上有什么配置一概不认。

一个关键认识：这个开关管的是"读不读文件"，不是"有没有这些功能"。Skills、hooks、子代理这些机制本身始终存在，开关只控制文件态的配置来源。你的程序完全可以不用任何文件，纯用代码选项把 Skills 列表、hooks 回调、子代理定义传进去。

## 逐项过一遍继承清单

第一项是 CLAUDE.md 与规则文件。相关来源启用时，会话启动即加载对应层级的 CLAUDE.md，子目录的在访问到时按需加载。多层叠加是相加关系，没有严格的覆盖优先级，两份文件冲突时靠模型自己理解，官方因此建议在文件里显式写清规则之间的次序。在 SDK 里，这类文件仍是给 agent 立规矩的第一工具；当你需要更强的确定性时，改用系统提示选项注入，那是代码可控的通道。

第二项是自定义 slash 命令。.claude/commands 目录下的命令文件会被会话发现并可用，发现机制同样挂在 settingSources 上。给 CLI 写过的团队命令库，SDK 会话直接受益。

第三项是 Skills，它值得展开多讲几句。同样经由 settingSources 发现，启动时只加载简短描述，正文在被调用时才进上下文，这个设计让装几十个 Skills 的成本很低。控制项是 skills 选项：省略时全部发现的 Skills 可用（和 CLI 一致），传列表只启用指定名字，传空数组全禁。有一个容易漏掉的配套：设置了 skills 选项时 Skill 工具会自动加入允许列表，但如果你显式传了工具数组，就得自己把 Skill 写进去，否则工具面里没有它，Skills 调不动。另有一条硬边界：Skills 必须以文件形态存在，SDK 没有编程注册 Skill 的接口，动态内容走自定义工具那条路。

第四项是 Hooks，它有文件态和代码态两支。SDK 会话里两类 hooks 并存：文件态的（settings.json 里定义的 shell 命令、HTTP 调用等）经由 settingSources 加载，代码态的作为回调传给 query()。两类都会在子代理里触发。SDK 比 CLI 多出几个事件类型，TS 侧支持会话开始、会话结束这类 CLI 不暴露的生命周期事件，等于给了宿主程序更细的观测面。

第五项是子代理，走文件和代码两条路。.claude/agents 目录下的定义文件会被继承，代码里也能用 agents 选项直接传定义。启用子代理要在允许列表里加 Agent 工具，和 Skills 的配套陷阱同构。

第六项是 MCP 服务器。文件态的 MCP 配置随 settingSources 加载，代码态用 mcpServers 选项传。这里有一个企业部署必知的坑：claude.ai 的 connectors 是跟着 claude.ai 登录走的，你的 mcpServers 传个空对象并不能关掉它们，要显式设 strictMcpConfig，或单独禁用 connectors，或用环境变量关掉，三条路任选。空配置不等于无外部服务器，这个反直觉行为值得写进部署检查单。

第七项是自动记忆，放在最后是因为它两面性最强。引擎会把跨会话的记忆存在 ~/.claude/projects/ 项目对应的 memory 目录里，agent 用文件写入工具保存记忆。这是"越用越懂你"的来源，也是租户间信息泄漏的潜在通道，下一节细说。

## 不归总开关管的四样东西

settingSources 的权力有边界，下面这些无论开关怎么设都会生效，做隔离设计时必须单独处理。

企业托管策略和服务器侧管理的设置永远加载。这是企业的安全底线，SDK 无权关闭，也不应该能关闭。

~/.claude.json 这个全局配置文件始终被读。它不属于三个来源里的任何一个，是引擎自身状态的存放处。

自动记忆默认在 settingSources 之外运作。要关它得用专门的开关：选项里关自动记忆，或设对应的环境变量。多租户场景里这一条最容易被漏掉，因为人们直觉上以为断开配置来源就断开了所有文件读写。

用户设置里的沙箱凭据规则（拒绝和掩码条目）也会被读取。这同样是安全语义的一部分。

把"settingSources 管不到"的四样和"settingSources 能管"的清单放在一起看，结论很清晰：配置隔离不等于行为隔离。前者砍掉了配置输入，后者还需要逐项处理记忆、策略、全局文件这些旁路。

## SDK 与 CLI 的行为差异

继承不是复制，几处差异值得记住。hooks 的事件面 SDK 更宽，TS 侧多出的生命周期事件让宿主能做 CLI 做不到的观测。Agent teams 是 CLI 独占的能力，SDK 的选项面里没有它的配置入口，一个 SDK 会话顶多以普通会话身份当个组长。connectors 的认证跟着 claude.ai 走，在第三方产品里本来就用不了 claude.ai 登录，所以那条路在合规场景里自然消失。

还有一类差异是"CLI 有、SDK 转译"。CLI 的交互式命令（各种斜杠命令的界面形态）在 SDK 里不存在，SDK 拿到的是等价的程序接口：CLI 里手敲 /compact，SDK 里是压缩相关的选项和钩子；CLI 里看进度条，SDK 里是事件流。用 CLI 的心智找 SDK 的接口，映射基本都在。

## 多租户：官方警告与配方

官方文档对默认配置给了一句罕见的重话：默认值对多租户隔离不安全。展开成场景就是：同一台机器上给两个租户起会话，A 租户的 CLAUDE.md 会被 B 租户的会话读到（如果没断开 user 来源），A 的对话记忆可能被自动记忆机制存进共享目录再被 B 的会话翻到。

隔离配方由三条组成，缺一不可。每租户独立的文件系统视图（容器或至少独立的工作目录与配置目录，配合环境变量重定位配置路径）；settingSources 设为空数组断开文件态输入；显式关闭自动记忆。三条做完，会话才算是"只携带你代码里写的行为"。

单租户的内部工具不必如此紧张，但方向相同：你能说出这个会话的行为来自哪些文件，就算合格；说不出来，继承面就是暗物质。

## 什么时候保留，什么时候清空

保留继承面的理由是复用：团队已有的 CLAUDE.md 约定、命令库、Skills 直接生效，SDK 会话像团队里一个新成员入职就带全套手册；个人工具也受益，你的个人偏好无缝延续。凡是"这个 agent 代表某个人或某个团队干活"的场景，继承面是红利。

清空继承面的理由是确定性：产品化的 agent 对外代表你的产品，它带着哪台机器上的私人配置跑，行为就随机器漂移，这在任何对外服务里都不可接受。凡是"这个 agent 代表一个产品干活"的场景，继承面是负债。

决策可以压成一句：代表个人或团队干活的 agent，保留继承面；代表产品干活的 agent，清空继承面再上线。

## 权衡与局限

继承面的存在让 SDK 的学习曲线有个诡异的形状：前两天觉得一切顺利（默认能跑），第三天开始困惑（行为与代码不符），排查后才明白默认加载的存在。这篇的目的就是把第三天的困惑提前到第一天。

局限也说一句：清单是活的。引擎持续把 CLI 的新能力接入继承面，今天的边界明天可能移动，多租户部署的隔离配方要随版本回归测试，把它当持续工程而不是一次性设置。

## 上线前的继承面清点

把继承知识落成一份清点流程，产品化会话上线前跑一遍，五步。

第一步，声明意图：这个 agent 是"给人用的"还是"给产品用的"（前文的决策）。写在设计文档第一行，后面的每步都对照它。

第二步，来源清点：三处配置来源逐处列出实际存在的文件（用户目录的 CLAUDE.md 和设置、工作目录链上的 .claude、本地覆盖）。产品化场景的清点结果应该是空（清空配置来源），内部工具的清点结果应该是白名单（明确列出加载哪几份）。

第三步，旁路核查：四样不受开关管的东西逐项确认（托管策略知道内容吗、全局配置文件存在吗、自动记忆关了吗、沙箱凭据条目谁维护）。产品化场景自动记忆必须显式关，这条单独打勾。

第四步，行为验证：起一个冒烟会话，看初始化消息的技能、命令、代理列表，与第二步的声明比对。多出来的每一项都要能说出处，说不出的就是暗物质。

第五步，文档化：清点结果写成这个 agent 的配置基线（加载什么、不加载什么、为什么），进版本库。半年后有人问"这个 agent 为什么会 X"，基线就是答案。

五步半小时，产出的是"这个会话的行为全部可解释"的保证。继承面出的事故，多数能追溯到没做这半小时。

## 继承面的实操疑问

**清空配置来源后，Skills 和子代理还能用吗？** 能，但只能走代码通道（选项传入）。文件态的技能目录、代理目录不再被发现。产品化 agent 想用技能，把技能目录打进部署产物、用配置注入的方式引入，控制权在你手里。

**团队成员想给内部 agent 加条规则，走哪里？** 项目级的 CLAUDE.md 或设置文件，走 git 评审。继承面的好处在这里体现：规则的变更像代码一样有 review 和历史。前提是这个 agent 的配置来源包含项目，也就是它是"给人用的"那一类。

**同一台机器上 CLI 和 SDK 会话互相影响吗？** 读同一批文件（用户目录的配置），写各自独立的会话数据。CLI 里改的用户设置，SDK 会话下次启动会读到（来源启用时）。想让 SDK 会话完全不受 CLI 使用影响，还是那句话：清空来源。

**自动记忆关了，agent 还能"记住"用户偏好吗？** 能，两条正路：会话机制（短期，对话内记忆天然存在）和你的应用层记忆（长期，你存偏好、你注入系统提示）。引擎的自动记忆是便利不是必需，产品化场景用应用层记忆更可控也更可审计。

**怎么发现"这个会话加载了多少东西"？** 初始化消息是权威：技能数组、命令列表、代理名单、配置画像都在里面。把它 dump 成一行日志是所有清点工作的起点，前面几篇反复提初始化消息，原因就在这：它是会话出生证明兼配置审计报告。

## 关键要点

- settingSources 是继承面总开关，默认加载 user、project、local 三处，空数组全断。
- 继承清单：CLAUDE.md、自定义命令、Skills、hooks、子代理、MCP、自动记忆；Skills 和子代理有"显式工具列表要自己加对应工具"的陷阱。
- 四样东西不受开关管：托管策略、~/.claude.json、自动记忆、沙箱凭据规则；配置隔离不等于行为隔离。
- 多租户配方三条：独立文件系统视图、settingSources 空数组、关自动记忆。
- 给人用的 agent 保留继承面，给产品用的 agent 清空它。
