# 从 CLI 与旧 SDK 迁移到 Agent SDK

> 更新日期：2026/10

**TL;DR：** 三种出身的人走三条迁移路：CLI 脚本用户的资产是任务模式（提示词和流程经验，直接平移）；非交互命令行用户的资产是脚本（逐步替换解析逻辑为类型化事件流）；旧 Claude Code SDK 用户的迁移是包改名加两个破坏性变更（默认系统提示变了、选项类改名）。三条路共同的关键动作是迁移前建立行为基线，否则"迁完不一样了"说不清是谁的锅。

## 先认路：你是哪种移民

迁移失败的第一大原因是不认路就走。三种出身，行李完全不同。

CLI 交互用户：你在终端里天天用，攒下的资产是任务经验（哪类任务怎么提示有效、哪类任务它会搞砸）。你没有代码要迁，你要迁的是判断力，这最值钱也最容易迁。

CLI 自动化用户：你有一堆脚本，cron 里跑非交互命令，grep 解析输出。你有真实的迁移对象，也有真实的迁移收益（解析层是脆弱的）。

旧 SDK 用户：你用的包叫 Claude Code SDK（那个旧名字），它改名成了 Claude Agent SDK，API 面有小改。你的迁移是半天的事，但有两个坑必须知道。

## CLI 用户的迁移：经验的平移

交互用户的"迁移"其实是新技能习得，两个认知转换最重要。

第一个转换：从会话到调用。CLI 里你的心智单位是会话（一个终端窗口聊到底），SDK 里是调用（一次 query 一个任务单位，会话是显式机制）。对应关系：你在终端里做的每一件事，SDK 里都有一个程序化等价物。你敲的任务描述就是 prompt 参数；你按的每次批准，是审批回调的一次调用；你中途插的话，是流式输入的一条消息；你想回退的冲动，是检查点机制。把这个映射表建起来，CLI 经验完整兑现。

第二个转换：从眼看到程序看。CLI 里输出你肉眼扫，SDK 里输出给程序分发。你肉眼能忽略的噪音（系统消息、内部状态）程序会认真处理，所以事件分发的类型分支要从第一天写对。反过来，你肉眼会注意的信号（它开始绕路了、它在重复同一个动作）程序原来注意不到，这些信号要显式编码（重试计数、轮数监控），这是迁移中最容易丢的能力。

平移验证法：挑三个你最熟的 CLI 任务（一个顺利的、一个要纠偏的、一个经常翻车的），在 SDK 里重建，对比行为。三个都对上，经验迁移完成；对不上的是机制差异点，逐个学。

## 脚本用户的迁移：解析层的安乐死

非交互脚本的结构千篇一律：命令行起进程、参数传任务、输出捕获、grep 或正则解析、按解析结果走分支。迁移的实质是把解析层换成事件流。

分步替换法，不动业务逻辑。第一步，包一层：脚本保持原样，把"起命令行进程"换成"SDK 发任务"，输出先全部落盘不解析。第二步，换观察：写事件分发把落盘内容结构化（结果消息的字段就是你要的答案），和旧的 grep 结果并行对比。第三步，换分支：业务逻辑的判断条件从"grep 到什么"换成"结果子类型和字段值"，一类一类换。第四步，删旧层：对比期结束删掉 grep 代码。

这个走法的价值在风险控制：每步都可回退，解析层退役前新旧并行足够久，"迁移把脚本搞坏"的事故面被压缩到单类判断的粒度。

迁移中顺手收获的三个升级：错误的分类不再靠字符串匹配（结果子类型是官方枚举）、会话可恢复（脚本失败重跑从头来，SDK 恢复从断点续）、预算可控制（脚本烧钱无上限，SDK 有硬顶）。很多团队迁完才意识到旧脚本的这几块一直是裸奔。

## 旧 SDK 用户的迁移：改名加两个坑

官方迁移指南对应的正是这条路，路径明确。

包名替换：TS 从旧包名换到新包名（卸旧装新改 import 三步），Python 同理（模块名跟着改）。锁文件和依赖清单同步更新。

坑一，默认系统提示变了。旧版本的 SDK 默认带 Claude Code 的系统提示；改版后默认是最小提示（一个裸工具循环），这是产品立场的转变（SDK 不再假设你是编码助手）。升级后行为突然变笨变裸，九成是这个。修复：显式声明用预设（保留旧默认行为），或借机评估是否本就该配自定义提示。这个变更影响深远，值得在迁移 PR 里单独一个提交并跑对比评估。

坑二，选项类改名：Python 的选项类从旧名换成新名，字段基本不变。全局替换即可，但顺手检查一遍动态构造选项的代码（反射或字符串拼选项名的地方，替换工具不一定覆盖）。

历史遗留的第三个坑要提防：极老版本的 Python SDK 曾把空配置来源列表当省略处理（等于没隔离），如果你的多租户隔离依赖空列表，先升级再迁移，顺序反了隔离是假的。

## 迁移工程学：基线先行

三条路共用一个工程纪律：迁移前建行为基线。

基线的内容：一组代表性任务（覆盖你的主要场景）在旧方案下的行为记录（输出、耗时、成本、失败模式）。迁移后同组任务重跑对比。没有基线的迁移，一切"感觉不一样了"都无法归因（是 SDK 行为变了、你的翻译错了、还是本来就有波动）；有基线的迁移，每个差异都能定位到具体机制。

基线的规模按系统重要性定：个人脚本三五个任务够，生产服务要覆盖到能对账的程度。建立成本一次付，之后每次升级 SDK 都复用（它就是机制回归测试的雏形）。

## 切换与回退

切换策略按容错度选。激进切换（旧路径直接下线）适合个人工具和低危脚本，快但出错就回不去。双写并行（新旧同时跑，结果对比，人不掉线）适合生产服务，成本是双份运行费用跑一个对比期。灰度分流（按任务类型或流量比例切）适合大规模系统，风险释放最平滑。

无论哪种，回退预案写清楚：旧路径保留多久、回退的触发条件（哪些指标恶化到什么程度）、回退动作谁执行。回退预案不是不信新方案，是让切换决策可以大胆做。

## 迁移路上的常见疑问

**CLI 的配置文件（CLAUDE.md、设置）迁到 SDK 还有效吗？** 有效，SDK 会话默认加载同一批文件（配置来源机制）。你的项目级配置零迁移成本生效，个人级配置在产品化场景反而要显式清掉。配置的迁移问题不是"怎么迁"是"要不要留"。

**headless 直连协议的集成（没用 SDK，直接说协议的）算哪种移民？** 算第四种：轻集成用户。你的迁移量取决于集成厚度，几百行的解析层建议直接换 SDK（解析层是维护大头）；几十行的薄封装可以先留，SDK 版本对齐后再换。判据是解析代码的行数和它出 bug 的频率。

**迁移要不要顺便重构？** 不要。迁移和重构混在一个 PR 是事故配方：行为差异无法归因。先纯迁移对齐行为，再单独重构。实在手痒，重构 PR 里引用迁移基线做前后对比，至少归因链不断。

**团队里 CLI 和 SDK 并存，配置和技能怎么共享？** 共享天然成立（同一批文件两边都读）。管理上把共享资产（项目 CLAUDE.md、技能库）当公共产品维护，变更通知同时发两个使用方。冲突几乎不存在，因为文件就一份。

**迁移后成本变了，正常吗？** 两个方向都可能：变贵（事件流全量处理比你的 grep 费一点、缓存冷启动期）或变便宜（会话复用省了重复上下文、结构化输出省了重试）。给两周的缓存预热期再下结论，用成本画像对比（同任务分布的每任务中位数），别拿单日数字吓自己。

## 迁移检查清单

三条路通用的收尾清单，迁移 PR 合并前逐项过。

包与版本：新包名装对、旧包卸干净（残留的旧包在依赖树里作祟是幽灵 bug 的来源）、锁文件更新、引擎与 SDK 版本组合记录在案。行为基线：迁移前的基线跑过、迁移后对比过、差异都有归因（机制变化、翻译误差、正常波动三选一）。系统提示：默认提示变更处理了吗（显式预设还是借机重设计，二选一明确）。配置来源：空列表语义确认过（老版本 Python 的坑）、产品化场景该清的清了。错误处理：单发的错误后异常语义接住了、stderr 回调在位（不然下一次故障又盲人）。回退预案：触发条件、保留期、执行人三项写明。

清单的价值在迁移完成后：它就是这次迁移的验收记录，半年后行为疑云翻出来看，当时确认过的项不用重查。

## 三类用户的迁移节奏参考

三类出身的典型节奏与里程碑，给排期做锚。

CLI 交互用户（学习型迁移）：第一周跑通最小程序加读懂数据类型；第二三周重建自己的三个典型任务（经验平移验证）；第四周起把日常工作中适合自动化的部分逐步固化成产品。里程碑：三个任务的 CLI 与 SDK 行为对齐。

脚本用户（替换型迁移）：每脚本四步替换法，简单脚本（百行内）两三天一个，复杂脚本（有状态管理和多轮交互）一两周一个。并行期建议两到四周（新旧对比跑）。里程碑：解析层全部删除，那个旧脚本目录清空。

旧 SDK 用户（升级型迁移）：包替换半天，默认提示变更的影响评估与适配两三天（含对比评估），总量一周内。里程碑：迁移 PR 合并且评估对比无回归。

三类节奏的共同瓶颈不是技术是验证：机制可以一天迁完，行为验证（基线跑通、对比清楚）占掉三分之二的时间，而且不能压缩。想快的正确姿势是把验证自动化（基线脚本化），不是跳过验证。

## 迁移收尾的追问

**迁移期间新旧并行跑，成本翻倍怎么办？** 并行跑的是基线验证任务集（几十个任务），不是全量生产流量双跑。全量双跑只在灰度分流策略里按比例出现（比如新通道先接一成）。控制并行面的粒度，成本增量可以压在个位数百分比。

**旧脚本的历史包袱（没人敢动的祖传脚本）要迁吗？** 分级处理：还在被调用的按正常流程迁；调用率趋零的趁迁移做一次退役评审（多数祖传脚本的正确归宿是删除）；说不清有没有人用的，加调用日志观察一个月再定。迁移是清理的天然契机，别把技术债原样搬进新家。

**多租户产品从旧 SDK 迁移，有什么特别要注意的？** 两件事前置：确认空配置来源语义（老版本 Python 的坑直接影响租户隔离的正确性）；迁移顺序上先升级隔离相关的配置到显式声明，再换包。租户隔离的正确性在迁移前后各做一次渗透验证（安全篇的演练），确认迁移没有引入隔离回归。

**迁移期间要不要冻结共享配置的变更？** 建议 freeze。并行对比期内 CLAUDE.md 或技能库变了，行为差异就没法归因到迁移本身（到底是包换了还是配置变了说不清）。共享配置的变更窗口安排在对比期之外；实在要改，改完把基线重跑一轮再继续对比，归因链别断。

**迁移完的团队最容易犯的下一个错误是什么？** 观察下来排第一的是"迁移后不继续用 CLI"。团队把 SDK 当正式渠道后，日常探索还在 CLI 里做（顺手），两边的行为基线慢慢分叉（CLI 的配置漂移、SDK 的提示词演进），某天 CLI 里验证过的模式搬进产品失效，排查半天才发现两边早就不是同一个配置世界。防法：产品的配置基线同样在 CLI 环境里复现一份（脚本化），月度对齐一次，或者干脆约定探索也在 SDK 的最小 harness 里做。迁移的终点是工作流的统一，不是多一个渠道。

**一个人的 side project 值得走完这套流程吗？** 按投入产出裁剪：基线可以缩到三个任务的手工记录，双写并行可以砍成直接切换（个人项目回退成本低），回退预案两行字（旧脚本还在）。但两样不要省：迁移前的行为基线（个人项目返工最贵的是时间）和默认提示变更的适配（它影响每一个任务，最不该漏）。流程的意义在大团队是协作对齐，在个人项目是少走弯路，形态不同核心动作相同。

**迁移到哪里算完？** 给一个可验收的终点定义：旧依赖从锁文件消失、行为基线对比通过且归档、错误处理与新语义全部对齐（错误后异常、状态字段）、回退预案归档备查、团队的新人文档指向新路径。五项全绿，迁移关闭。多数团队的迁移烂尾不是技术卡住，是"差不多就算完了"的模糊标准让最后一成永远悬着，终点定义本身就是防烂尾机制。

## 关键要点

- 三条路：CLI 交互用户迁判断力（会话到调用、眼看到程序看两个转换），脚本用户迁解析层（四步替换法并行对比），旧 SDK 用户是改名加两个坑。
- 最大的坑是默认系统提示变更：旧默认带完整提示，新默认是裸循环，升级后变笨先查这里。
- 基线先行：迁移前记录行为基线，差异可归因，基线复用为机制回归测试。
- 切换按容错度选（激进、双写、灰度），回退预案先写好；迁移与重构绝不混在一个变更里。
