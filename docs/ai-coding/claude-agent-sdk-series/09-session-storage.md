# 会话存储：让会话跟着你的基础设施走

> 更新日期：2026/10

**TL;DR：** 默认情况下会话是创建它的机器上的本地文件，自动伸缩、无服务器、多机部署里这个假设直接破产。存储适配器把每批会话写入镜像到你的后端（对象存储、Redis、Postgres 都行），任何机器都能恢复任何会话。但它是镜像不是替代：本地先写、镜像跟随，镜像失败不打断 agent 但会丢数据。这篇讲适配器的接口契约、双写的语义、三类后端的设计和一致性验收。

## 问题的形状

设想一个部署：三台 worker 跑同一个 agent 服务，负载均衡随机分发请求。用户上午的任务跑了一半挂在 A 机，下午的续跑请求落在 B 机。B 机去自己的 projects 目录找会话文件，没有。会话断在 A 机的磁盘上，用户看到的是 agent 失忆。

再设想无服务器：容器用完即弃，会话文件随容器蒸发。还有合规场景：企业要求所有对话留存三年、按租户隔离、随时可审计，散落在各机器本地目录里的 JSONL 文件满足不了任何一条。

三类问题（多机可达、持久存活、受控留存）指向同一个解：把会话从"引擎顺手的本地文件"升级为"你基础设施里的一等公民"。存储适配器就是这个升级的接口。

## 适配器的接口契约

适配器不是简单的存取两个方法，它模拟的是本地会话文件的完整生命周期。核心动作两个：追加（每批会话条目落盘后转发给你的后端）和加载（恢复会话前从你的后端取回全部条目）。围绕核心还有一组可选能力：列会话（continue 语义要用它找最近会话）、会话摘要（管理界面一次拿到元数据列表）、删除（要级联到子键）、列子键（恢复时发现子代理的会话文件）。

三个契约细节决定实现质量。键的结构是工作目录加会话 ID（可选子路径，子代理的会话文件用它寻址），你的后端按这个键组织数据。条目是不透明的 JSON 对象，加载时必须按追加顺序原样返回，深度相等即可，不要求字节相等，这给了后端序列化格式的自由。摘要必须在追加时顺带维护，而不是列表时现算，否则每次列会话都要全量回放，代价不可接受。

还有两条工程约束写在官方契约里：时间戳要用共享时钟（多机时间不一致会搞乱"最近会话"的判断）；摘要的读改写要防并发（两个会话同时追加，摘要合并会丢更新）。这两条是多机部署最先坏的地方，值得在实现里显式处理。

## 双写语义：镜子的物理学

适配器最常见的误解是把它当成会话的"唯一真相源"。不是。引擎的写入路径固定：每批条目先写本地磁盘，成功后转发给适配器镜像。本地是第一写，镜像跟随。

由此推出三种运行形态。新会话和镜像未命中的恢复：本地文件是主副本，跑完还在。镜像命中的恢复：SDK 把会话从你的后端加载进一个临时目录运行，跑完删掉临时副本，此后你的后端持有唯一持久副本。这条规则决定了一件要紧事：**一旦依赖镜像恢复，镜像就是孤本**，镜像后端的可靠性等级必须按主存储设计，不能按缓存设计。

失败语义是这套设计的精髓。镜像写入是尽力而为：失败重试三次带退避，超时类失败不重试（调用可能实际已到达）。三次用尽，SDK 记日志、发一条 mirror_error 系统消息、丢弃这批、继续跑。**agent 永远不会因为镜像故障而中断**。这个选择的代价要理解透：镜像后端挂十分钟，期间的数据批次就没了；如果是镜像恢复型会话，跑完本地临时副本一删，这批数据就永久丢了。所以 mirror_error 系统消息要进你的监控告警，它就是数据丢失的现场信号。

重试还带来重复投递：同一批可能收到两次。适配器必须按条目的去重键幂等处理，这是分布式写入的常规课。

## 镜像之外的三件事

持久化选项的冲突。关闭会话持久化的选项与存储适配器互斥，组合使用直接在启动时报错。这个互斥是合理的：一个说不留档，一个说留到外部，语义矛盾，早失败好过静默选边。

本地残留。镜像命中的恢复用临时目录跑，跑完删掉，但如果进程中途被杀，临时目录可能残留。要彻底不留本地痕迹，把配置目录环境变量指向临时位置；TS 里注意环境变量选项是整体替换语义，记得展开继承原环境，再把凭据带上，否则恢复会话时遇到的是没登录。

保留策略。SDK 从不删你后端里的数据，保留期、归档、合规删除全是你的责任。本地的旧文件另由引擎的清理周期处理，两边节奏不同，别指望它们对齐。

## 三类后端的设计

官方仓库的示例里给了三套参考实现，各代表一类存储的典型设计。

对象存储（S3 型）按追加粒度落对象：每次追加写一个分片文件，加载时列表、排序、拼接。实现最直白，吞吐好，代价是加载要多次请求、列表操作有配额压力。适合写入密集、恢复不频繁的场景。

键值存储（Redis 型）给每个会话维护一个列表结构，外加一个按序的会话索引。加载单次搞定，延迟低，适合恢复频繁的场景。代价是内存成本和持久化配置：Redis 当主存储要打开持久化并想清楚恢复演练，否则重启丢数据的正是你唯一的副本。

关系型或文档库（Postgres 型）每条目一行或一个文档，插入序号排序。最强的是查询能力：审计、按租户检索、时间范围统计都是 SQL 一句的事。代价是高频小写入对连接池的压力，追加批次里做好批量插入。

选型判据归结为三个问题：恢复频率多高（高选低延迟存储）、审计查询需求多重（重选关系型）、镜像后端的持久性等级（按孤本标准选）。不存在万能答案，三套参考实现都该读一遍再动手，它们处理了幂等、排序、摘要维护这些容易漏的细节。

## 一致性验收

适配器是基础设施代码，靠肉眼检查不可靠。两个 SDK 仓库都带了适配器的一致性测试套件：TS 把合规测试文件拷进项目跑，Python 用一个工厂函数传入 pytest 驱动。套件会验证追加加载的顺序一致、去重、摘要维护、子键级联这些契约点。

把合规测试纳入持续集成，每次改适配器实现自动跑。再配一个内存实现的适配器做开发测试用（官方就带了），本地迭代不依赖真实后端。这两件套是适配器工程化的最低配置。

上线前还要做一次故障演练：故意让镜像后端不可用，确认 mirror_error 告警触发、agent 不中断、恢复后数据缺口可量化。没演练过的失败语义只是文档上的承诺。

## 会话树的恢复细节

两个容易忽略的恢复盲区。其一，子代理的会话文件挂在主会话键的子路径下，恢复主会话时要能发现它们（可选的列子键接口干这个），丢失子代理文件的主会话恢复后，历史里子代理那段就是残缺的。其二，fork 的实现是重写会话 ID 和内部标识，不是文件字节拷贝，你的后端里 fork 出的会话是独立实体，删除原会话不影响它，反之亦然。

还有一条与读取 API 的分工：管理接口里读会话消息，返回的是压缩后的链；要拿原始全history，用适配器的加载接口。做审计界面时用前者，做精确回放时用后者。

## 权衡与局限

适配器解的是"会话跟着基础设施走"，它不解"会话应该多大"。镜像让超长会话的恢复变得方便，反而可能诱导你无限续命会话，把事件模型篇讲的蒸馏纪律丢掉。好的架构是适配器加短会话：每台机器随时能恢复任何会话的能力给你兜底，日常运营仍然以"任务完成即蒸馏"为主旋律。

适配器也增加了写入路径的复杂度：每批落盘后多一次网络调用，失败要监控，重试要幂等。单机个人工具上这些全是纯开销，不要为了架构正确性给单机部署上适配器。判据回到问题形状：你的部署里是否存在"会话的创建者和使用者可能不是同一台机器"，是，上适配器；否，本地文件已经够用。

## 实现一个适配器的施工顺序

参考实现读过之后，自己动手的正确施工顺序，每步都有验收点。

第一步，选型与表设计。按前文三问选后端，把键结构（项目键、会话 ID、子路径）翻译成你的存储模型：对象存储是键前缀约定，键值是键命名规则，关系型是三列索引加插入序号。表设计的验收：手工插入两条假数据，按加载语义拼回来，顺序和内容一致。

第二步，实现追加与加载。先不做摘要和列表，只做最小闭环：追加落一批、加载拼全程。幂等在这步做（按条目标识去重），重试语义靠它成立。验收：一致性测试套件跑到追加加载的部分通过。

第三步，接双写观察。适配器接进会话跑真实任务，观察镜像消息流和 mirror_error 事件。故意停掉后端验证失败路径：agent 不中断、告警触发、恢复后缺口可查。这步的产出是故障演练记录，也是上线评审的材料。

第四步，补摘要与列表。continue 语义和管理界面需要它们。摘要的读改写加锁（并发会话同时追加），时间戳统一用一处时钟源。验收：并发压一轮（两个会话同时写），摘要无丢更新。

第五步，保留与删除策略。业务定义保留期，定时清理任务按保留期删数据，删除接口的级联（子键、摘要）在清理任务里同样生效。验收：过期数据真的删得掉（很多"保留策略"只写不删）。

五步全部走完再上生产，一致性测试套件全程挂在 CI 里。施工周期视后端熟悉度两到五天，其中第三步最容易被压缩，也最不能被压缩。

## 适配器上量之后的问题

**会话量大了加载慢怎么办？** 加载要拼全程历史，超长会话的加载是真实的性能点。三个手段：对象存储并行拉分片；键值型用管道批量读；加载加缓存（同一会话连续恢复第二次就近取）。极端长会话的根治还是蒸馏拆段，别让单会话无限长到适配器背不住。

**两个 worker 同时恢复同一个会话怎么办？** 适配器管存储不管锁，并发恢复同一会话是未定义行为（和本地会话一样）。要互斥就在业务层加分布式锁：会话 ID 做锁键，恢复前拿锁。存储适配器不解决这个问题，别指望它。

**镜像延迟有多大？** 每批写入后转发，正常网络下秒级。但要意识到它是异步跟随：会话进行中另一台机器恢复它，可能拿到少最后一批的状态。对"实时接管"要求高的场景，接管的协议里带版本号（当前批次序号），缺口显式处理。

**能不能只镜像部分租户？** 能，适配器是你的代码，按会话键路由：高保留要求租户进镜像，低敏租户留本地。成本与合规的折中常用这招。

**换后端怎么迁移？** 双写过渡：新适配器和旧适配器并挂（包一层双写适配器），读旧写新，跑一个对齐周期（两边数据条数与内容抽样一致），切读新、观察、下旧。会话数据的迁移和任何存储迁移同工程，别信"直接导过去"。

## 双写路径的时序图

把双写的完整时序画出来，设计后端和排查数据缺口时按图索骥：

```
引擎子进程          SDK(你的进程)         你的后端
   │ 每批条目先落盘      │                   │
   │──────────►│ 本地写完成            │
   │          │──append(条目)────────►│ 镜像写入
   │          │◄─(成功/失败)──────────│
   │          │ 失败:重试3次带退避      │
   │          │ 仍失败→丢弃+mirror_error│
   │ 继续任务(永不中断)  │                   │
```

恢复路径是另一条：

```
你的程序 ──resume(ID)──► SDK ──load(键)──► 后端
   命中:历史进临时目录 ──► 运行 ──► 结束删本地副本(后端成孤本)
   未命中:回退本地文件(老路径)
```

两张图叠起来的三个设计推论。图一说明镜像链路是尽力而为层：它挂在主路径旁边而非当中，任何它的问题表现为数据缺口而非业务故障，监控点就是那一个错误事件。图二说明恢复命中的会话改变了所有权：本地副本被删，后端从备份升级为孤本，这条路径上的后端可用性要求高于图一路径。两张图合起来定后端的 SLA：按图二的口径定（恢复路径不可用等于会话不可恢复），图一自动被覆盖。

## 关键要点

- 适配器接口的两大核心：追加（每批镜像）与加载（恢复前取回）；摘要要在追加时维护，时间戳用共享时钟，读改写防并发。
- 双写语义：本地先写镜像跟随；镜像恢复型会话跑完删本地副本，后端是孤本，按主存储等级设计。
- 镜像失败不打断 agent：重试三次后丢弃并发 mirror_error 系统消息，这条消息就是数据丢失告警；重试带来重复投递，按条目键幂等。
- 三类后端各有取舍：对象存储写入友好、键值加载快、关系型可审计；用官方一致性测试套件验收，上线前演练故障。
- 关闭持久化选项与适配器互斥；SDK 不删你的数据，保留策略自理；单机部署不需要适配器。
