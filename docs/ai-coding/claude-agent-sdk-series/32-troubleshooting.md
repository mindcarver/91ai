# 排错手册：高频故障的症状、根因与修法

> 更新日期：2026/10

**TL;DR：** SDK 故障集中三类：起不来（二进制和认证问题）、跑不动（挂起与卡死）、结果怪（成功表象下的失败）。这篇按症状组织，每条给根因和修法。通用心法一条：先分层（你的代码、引擎进程、外部依赖），再对齐事实（版本、会话 ID、日志时间线），最后才动假设。排错的混乱九成来自顺序颠倒。

## 第一类：起不来

**引擎找不到。** Python 侧的典型报错是"在某路径找不到 Claude Code"。根因三选一：没装引擎；选项里配了路径但路径不对；运行环境（服务、IDE 启动的进程）的 PATH 和你终端里的不一样。修法顺序：先在应用的真实运行环境里跑一次版本查询命令确认可见，再查配置的路径，最后考虑原生安装。

**平台二进制缺失。** TS 侧报"某平台架构的原生二进制找不到"，根因九成是安装时跳过了可选依赖（npm 的省略开关把二进制包跳了）。重装不省略，或指到原生安装的路径。

**Windows 的批处理拒绝执行。** 引擎进程是 npm 的批处理垫片时，Python SDK 会拒绝启动。这是刻意加固（批处理垫片会被参数注入），修法是给真正的可执行文件路径，或原生安装。注意配置了显式路径会关闭自动发现，只装原生版却留着旧路径配置，等于没修。

**启动即失败但报错含糊。** "启动失败"类错误常见于路径指向了不可执行的东西（文本文件、目录、无执行权限），或容器里的二进制与平台不匹配。去掉自定义路径让 SDK 用自带的副本，容器场景在镜像构建期重装。

**没连上就调用。** Python 客户端的方法在连接建立前（或断开后）被调，修法是用上下文管理器形态管理客户端生命周期，连接的生命周期交给语法结构而不是手动调用。

## 第二类：跑不动

**静默卡死。** 没有报错、没有输出、永远等待。三个高频根因：你的回调没返回（审批回调在等一个永远不来的批准，或输入生成器异常被吞）、引擎在等外部资源（MCP 连接、网络）、单发模式下的错误后异常语义被误解（结果已产出、异常随后抛，你以为在等实际该收尾了）。修法：开 debug 落盘看引擎侧最后在等什么，九成卡死一屏日志内现形。

**进程退出码一。** 引擎非零退出且没有错误结果。TS 侧表现为循环被一个普通异常拒绝，Python 侧是进程错误类异常。两个必做动作：配 stderr 回调拿到真实的错误输出（不带回调时错误提示是固定占位文本，不是真的 stderr）；区分异常类型，引擎报告了错误结果的场景有专门的异常子类携带完整结果数据，先接它。

**MCP 服务器连接问题。** 前文的原则在排错场景复述：连接失败不从查询抛异常，看初始化消息的状态字段。pending 等待不是失败；failed 查网络与进程；needs-auth 查令牌。会话中途工具突然不可用，先查服务器是不是中途掉线重连中。

**流式输入的生成器问题。** 你的输入生成器抛异常，TS 侧表现为引擎收到"用户中止"（报错词不达意），Python 侧几乎无感（debug 日志才可见）。会话莫名停止且涉及流式输入时，第一检查点永远是生成器代码。

## 第三类：结果怪

**成功但没有结构化输出。** 结果子类型明明是成功，结构化字段却是空。两个原因方向：产出侧没有可校验的输出（schema 自相矛盾等不可满足情形，模型怎么填都不过）；或踩中了成功子类型不保证字段存在的边缘。修法：当失败处理走兜底；反复出现则检查 schema 可满足性（把约束一条条减到能过，再加回定位矛盾约束）。

**会话恢复失败。** 恢复时报找不到会话。三个根因按概率排：ID 不对（抄错、存错）；工作目录变了（老版本查找范围与目录绑定）；会话文件被清理周期收走。修法对应：核对 ID、确认目录或在正确目录恢复、接受损失并考虑存储适配器。

**预算触顶的现场。** 预算错误出现时要区分引擎侧（任务真的烧到顶了，正常止损）和迁移侧（恢复的会话历史累计把预算吃穿，口径问题）。处理套路：捕获后取会话 ID 和成本字段（异常抛出前先拿到数据），判断值不值得提额续跑，续跑要走业务确认不是自动循环。

**压缩后的行为退化。** 会话中后期 agent 开始忘事、重复问已答的问题。这不是 bug 是压缩的摘要损耗。确认方法：流里数压缩边界消息。处理：关键信息核实走产物文件不走记忆；判定退化严重的会话蒸馏重启。

**行为随机器漂移。** 同代码不同机器行为不同。三步定位：环境变量对比、配置文件三处对比（配置来源是否真的关了）、SDK 与引擎版本对比。多数漂移在第一步现形。

## 分诊流程：一屏版

把通用心法落成流程。第一步分层：症状在启动期（第一类）、运行期（第二类）、结果期（第三类），三类对应三组根因族。第二步对齐事实四件套：引擎版本（能力门槛的排查前提）、会话 ID（贯穿日志的主键）、配置画像（初始化消息那份）、双边日志时间线。第三步最小复现：把问题压到最小任务（一个工具调用、一条消息），能稳定复现再深入，不能复现的记录环境等下次。第四步才动假设和改代码。

顺序颠倒的代价示例：跳过对齐直接改代码，改完"好了"，其实是环境变量在那次重启时被平台恢复了，问题下个月原样回来。排错的最大浪费不是查错方向，是修好了不知道为什么好。

## 预防：把高频故障做成自检

排错的最高形态是不排。三类自检把这篇的大半内容前置。

部署自检（每次发布跑）：引擎可执行且版本正确（起不来的三连）、认证变量在真实运行环境可见、MCP 服务器状态全就绪、stderr 回调在位（不然下次故障又是盲人）。

冒烟会话（每小时或每天）：跑一个最小任务断言结果子类型，捕获配置画像与基线对比。它同时看守着引擎健康、配置不漂移、行为不变形三件事。

演练清单（季度）：依赖故障、认证过期、存储故障、注入攻击四项（测试篇的清单），每项的结果是"出事时的行为已知"。

三道自检的建设成本一两天，之后这篇手册的使用频率会显著下降。故障手册的正确命运是被自检体系逐渐淘汰。

## 排障现场的几个疑问

**debug 日志具体怎么开？** 选项里的调试开关（两语言都有，等级越高越全）把引擎侧输出落盘，配合 stderr 回调覆盖标准错误流。排障时两个都开，事后记得关（调试日志的体积不小）。

**怎么区分是 SDK 的 bug 还是我的用法错？** 三问：官方文档有没有支持这个用法的明文；最小复现里去掉你的全部定制（钩子、自定义工具、特殊配置）还在吗；官方仓库的已知问题里有没有同症状。三问下来基本能定侧。确定是 bug 就带着最小复现提工单，别在生产环境绕着改。

**生产环境出了这篇没覆盖的故障，现场怎么办？** 保现场三动作：留存会话文件和双边日志、记录引擎与 SDK 版本、必要时候用恢复会话把故障会话拉起来重放（只观察不改动）。然后按分诊流程走。事后把新故障补进你自己的手册，这篇的结构（症状加根因加修法）可以照搬。

**升级后一片红，怎么快速判断该回滚还是适配？** 看红的集中度：集中在一个机制（事件类型变了、选项改名了）是适配型，改代码半天内搞定；分散且行为性（提示变了、默认值变了）先查迁移指南的破坏性变更清单，有明文按官方路径迁，没有明文的行为变化先回滚再提工单确认。

## 错误信息解读词典

引擎和 SDK 的报错措辞有固定套路，读懂措辞能直接跳到根因。这本词典收高频条目。

**"在某路径找不到"类**：启动器找不到引擎可执行文件。信息里的路径是它找过的位置，先核对这个路径本身（拼错、不存在、无权限），再查为什么找到它（配置的显式路径还是自动发现）。

**"进程以退出码一结束"类**：引擎非零退出。退出码本身几乎无信息量，价值在于触发你去看 stderr（配回调）和区分有没有伴随的错误结果（有则异常类型不同、数据在手）。

**"被用户中止"类**：字面意思是用户中止，实际来源三选一：真的中止（流式输入的中断指令）、你的输入生成器异常（被翻译成了中止）、生命周期误用（连接已关还在写）。涉及流式输入时优先查第二个。

**"提示过长"类**：上下文超限。老版本上它会以卡死形态出现（压缩救不回来），新版本已修复为正常触发压缩。还看到它先升级，升级后仍现则检查是否有单条超长输入（一条消息塞爆窗口，压缩无能为力）。

**"结构化输出为空"类**：成功表象下的失败，词典第一类里讲过。反复出现走 schema 可满足性排查（逐条减约束定位矛盾）。

**"回放文件相关"类**：检查点恢复的专属报错。没开过检查点的会话要恢复、会话未正常结束、流已关还想直接调恢复，三种情形三种修法（对照检查点篇的时机表）。

词典的用法：新报错先来这里对暗号，对上了直接跳根因；对不上再走分诊流程。团队的私有报错（自定义工具的、网关的）应该往这本词典里补，它才会越长越有用。

## 一个完整排障案例

词典和流程放进一个真实形状的案例。某日告警：工单 agent 的任务成功率从九成二跌到七成，无部署无变更。

第一步分层：结果期故障（任务都跑完了但结果变差），第三类。第二步对齐事实：冒烟会话的配置画像与基线一致（排除配置漂移）；引擎版本未变（排除版本门槛）；抽取失败任务的事件流对比历史，发现失败任务集中在"带监控链接的工单"。

第三步最小复现：构造带监控链接的工单十连发，七次失败，复现率吻合。事件流细看：失败任务在点击监控链接的动作上工具报错。深挖工具（自定义的网页抓取封装）：目标监控平台一周前换了域名，旧域名的错误被封装层吞掉后返回了误导性的错误消息（"页面无内容"），模型按"页面为空"理解，反复重试后放弃并给了降级结论。

第四步修复三件：封装层放行真实错误（域名失效，查工单工具的关联配置更新域名）、错误消息写给模型（"监控平台不可达，转人工核实监控数据"）、监控类工具加健康探测进部署自检。

案例的教训浓缩成一句：**成功率下跌但没有部署变更时，先查环境里的第三方（域名、接口、凭据的有效期），它们变更不需要通知你**。这也是为什么部署自检清单里永远该有外部依赖的探测项。

## 日志与线索的追问

**日志里会话 ID 是空的，怎么回事？** 单发的错误后异常路径里，异常对象可能不带会话信息（数据在已产出的结果消息里）。修法就是全书反复讲的那条：循环内见到初始化消息就取 ID 存业务库，别指望异常处理里还有。

**同一个错误间歇性出现，怎么定位？** 间歇性的来源基本三类：限流类（按时间分布，高峰重现低谷消失）、外部依赖类（依赖方的抖动窗口）、并发类（只在并发超阈值时现）。给报错加时间戳和并发数两个维度做散点，聚集形状直接指向类别。

**生产排障能不能开原始体日志？** 能但限定窗口：确认需要看模型实际收发的内容时，临时开（注意它记录全部请求响应，含敏感内容），看完立刻关，日志文件按敏感数据处理。常态化开着是合规事故预备役。

**排障时要不要先升级到最新版试试？** 不要无差别升级：升级同时改变版本和问题，就算修好了也说不清是哪个的功劳，还可能引入新变量。顺序是先在当前版本上做最小复现和日志定位，确认是已知且新版已修复的问题（查官方仓库的已知问题列表），再带着理由升级。排障期和环境变更期错开，归因链才保得住。

**排障时最容易被忽略的信息源是什么？** 会话转录文件。它比日志完整（每一轮的原始收发都在），比复现快（历史现场直接翻）。排障流程里"拉出故障会话的转录通读一遍"应该排在改任何代码之前，多数谜团在转录里早有伏笔，只是没人看。给它配一个只读的查看工具（按会话 ID 拉取加渲染），是排障基础设施里回报率最高的一件。

## 关键要点

- 三类故障：起不来查二进制与认证、跑不动查等待与异常语义、结果怪先查成功表象下的失败。
- 高频五连：静默卡死开 debug、非零退出接 stderr、结构化空字段当失败、恢复失败查三因、漂移查环境。
- 心法一条：先分层再对齐事实最后动假设；修好了不知道为什么好是最大浪费。
- 三道自检（部署、冒烟、演练）把手册淘汰掉，是排错的终极形态。
