# 结构化输出：把 agent 变成一个 API

> 更新日期：2026/10

**TL;DR：** 在选项里传一份 JSON Schema，agent 的最终回复就被约束成可校验的结构化数据，出现在结果消息的专门字段里。校验失败时 SDK 会带着错误重新提示模型，重试超限则以错误子类型收场。这是把 agent 从"能聊天"变成"能对接系统"的关键一步，但 schema 的写法、版本门槛和两个成功假象决定了它好不好用。

## 为什么需要它

没有结构化约束时，agent 的最终回复是一段自由文本。你的程序要从中提取信息，就得解析自然语言：正则、关键词、碰运气的 JSON 提取。这条路在 demo 里能跑，在生产里是慢性病，模型这次把结论放在最后一段，下次放在第一段，偶尔还补一句"希望对你有帮助"，你的解析器跟着模型的心情抖动。

结构化输出把这个关系倒过来。你在任务开始前声明"我要的数据长什么样"，SDK 在任务结束时拿着声明验收模型的输出：合格就解析成数据交给你，不合格就告诉模型哪里不合格让它重交。你的下游代码从此面对的是稳定的字段，不是自由的散文。

贯穿案例：一个代码审查 agent，输入是仓库路径，输出需要三个字段：问题列表（每条含文件、行号、严重级别、描述）、总体评分、是否建议合并。用结构化输出定义这个形状，你的 CI 系统就能直接消费审查结果，评审仪表盘、阻断规则、统计报表全都接得上。

## 声明形状，验收结果

用法在概念上只有两步。选项里传入一份 JSON Schema（TS 用 outputFormat，Python 用 output_format，内容是一份类型为 json_schema 的声明加 schema 本体）；任务跑完后，在成功结果消息的 structured_output 字段里拿数据。

schema 的书写有一条硬规矩：校验只认 draft-07 这一个版本，声明了更新版本的 schema 会被直接拒绝。用 Zod 生成 schema 时要显式指定 draft-7 目标，因为 Zod 默认产出的版本声明更新；用 Pydantic 的 model_json_schema 则开箱即合。支持的特性集是 JSON Schema 的基础面：基本类型、枚举、常量、必填、嵌套对象、引用。format 关键字（比如标 email 的格式）只是注解，不会被校验，别指望它帮你拦格式错误的值。

给贯穿案例写的 schema 核心就是三层：顶层三个字段，问题数组里每个元素四个字段，严重级别用枚举列出可选值。枚举在这里价值极大，它把"严重级别"从自由文本变成有限集合，下游的统计逻辑才写得出来。

## 校验失败时发生什么

验收不是形式检查，是真的拿 schema 去验模型的输出。不通过时 SDK 会把校验错误回灌给模型，要求重新生成。这个过程对你是隐式的，你看到的只是任务耗时略长。重试有上限，超限后结果消息以 error_max_structured_output_retries 子类型结束，这时没有结构化数据可拿，错误列表里能区分是校验始终不过，还是模型中途出别的问题。

这个机制意味着写 schema 是在写两种东西的混合体：给校验器的规则和给模型的提示。字段名本身、描述的清晰度，都会影响模型一次过的概率。官方的建议值得照做：schema 保持简单、避免又深又必填的嵌套、数据可能缺失的字段设成可选、字段语义在描述里写清楚。

## 两个成功假象

第一个假象：子类型是 success 就有数据。实际上存在成功结果里没有 structured_output 字段的情形（模型路径上的边缘情况），把它当失败处理，走你的兜底逻辑。判定标准用两段：先看子类型，再看字段存在与否。

第二个假象：增量流里的 JSON 拼出来就是结果。开了 token 级增量输出的会话里，结构化数据会以参数增量的形式在流里出现，那是未校验的碎片，可能残缺。校验过的权威数据只在最终结果消息里。实时渲染可以做占位展示，落库和决策必须等最终结果。

## 版本门槛与历史行为

这个功能有一条清晰的版本线。当前版本：schema 不合法直接在启动时失败，报具名错误，早失败早发现。2.1.205 之前的行为是两副面孔：不合法的 schema 被静默忽略，agent 照常跑，返回自由文本；带 format 关键字的 schema 被拒绝。如果你的团队有从旧版本迁来的代码，"以前能跑现在报错"多半是撞上了这条从宽容到严格的分界线，把 schema 修合法就是修复。

## 设计 schema 的工程判断

三条实战判断，出发点都一样：schema 也是写给模型看的提示词。

枚举优于自由文本。能枚举就枚举，严重级别、状态码、动作类型，枚举既约束模型又方便下游。但要评估枚举的完备性：漏了一个真实存在的级别，模型会被迫把不属于任何枚举值的东西硬塞进最近的桶里，数据悄悄失真。枚举宁可宽不可缺。

数组与可选的博弈。必填数组强迫模型至少给一条，审查没发现问题时它会编一条低价值的凑数。把数组设可选，空结果用缺省表达，下游逻辑处理"没有问题列表"比处理"一条凑数的问题"干净。反过来，业务上必须有值的字段（比如总体评分）就必填，别给模型留空窗。

嵌套深度换 token。深嵌套对模型是负担，重试率随之上升。贯穿案例里问题数组只嵌一层对象，评分和结论平铺在顶层，刻意压平。schema 越浅，一次通过率越高，这是用表达力换可靠性，划算。

## 它解决不了什么

结构化输出约束的是最终回复的形状，不是内容的真伪。审查 agent 给你一份完美符合 schema 的结果，文件和行号仍然是模型声称的，可能指错地方。把 schema 当接口契约用没问题，把字段值当事实用要另外校验：行号回到文件里验存在性，评分规则在下游复核。接口的严谨和内容的可信是两层，混了会出事故。

它也不约束中间过程。agent 干了十轮工具调用，中间输出不受 schema 影响，只有最后的总结性回复被验收。想在中间环节拿结构化数据，用自定义工具的参数本身就是结构化输入，让模型在行动中产出数据，那是另一条更可靠的通道，两套机制配合的设计后面工具篇会讲。

## 权衡与局限

代价集中在三处。重试消耗预算：一次校验不过就是一次完整重新生成，schema 设计差的 agent 重试两三次，成本翻倍。灵活性受限：被 schema 约束的模型不再能自由发挥总结格式，某些开放式任务反而变差，适合用结构化的任务要有明确的输出定义。维护成本：schema 与下游代码是强耦合接口，改一个字段两边同时改，和任何接口演进同等待遇。

适用判据一句话：输出要进系统（CI 判定、数据库、下游服务）就用结构化；输出给人看（周报、聊天回复）就让它说人话，别为了结构化而结构化。

## schema 的进化与版本管理

结构化输出是接口，接口总会演化，演化就要管理。下面三套实践。

加字段是唯一无损的变更：新字段设可选，旧 agent 产出的数据缺字段，新消费者判空处理。删字段和改语义是破坏性变更：删掉的字段在旧会话恢复时模型还会输出（它记得旧 schema），新消费者收到未知字段；改语义更隐蔽（字段还在、含义变了），是最容易酿事故的一类。变更分级：加可选字段走常规发布，其余走版本化：输出格式带版本号字段，或干脆新任务类型新 schema，旧的下线走通知期。

schema 和下游代码的同步演进靠生成：TS 从 Zod schema 生成给 SDK 的 JSON Schema，业务代码直接 import 同一个 Zod 定义，单一真源；Python 用 Pydantic 类同理。手写 JSON Schema 再手写解析类的双份维护，漂移只是时间问题。

与模型的契约测试：固定一组测试任务，断言输出能通过 schema 校验（回归的是"模型能不能稳定产出合法结构"）。模型升级、提示词改动、schema 改动三类变更都要跑这组测试。结构化输出的失败常常不是校验器的问题而是提示的漂移：某次改动让模型开始偷懒省略可选字段，下游以为必有的数据悄悄没了，契约测试就是抓这个的。

## schema 能力边界的追问

**结构化输出和让模型直接输出 JSON 有什么本质区别？** 校验闭环。自己写提示词要 JSON，模型给你带 markdown 围栏的、带解释文字的、少逗号的，你写解析器和重试逻辑。SDK 的机制把校验和重试做进循环，你只声明形状。省的是那两百行解析代码和它每次模型换版后的维护。

**schema 里能用条件依赖吗（A 字段为某值时 B 必填）？** 基础特性集里没有条件逻辑（if/then 类）。要条件约束就在下游代码里二次校验，或把任务拆成两次结构化调用。别指望 schema 表达业务规则全集，它管形状，规则归代码。

**重试几次，能配吗？** 重试上限是 SDK 内部策略，选项面没有直接暴露。可控的是一次通过率：schema 简单、字段描述清晰、任务提示明确，重试自然少。观察重试是否发生：任务的耗时异常加结果里的错误列表。

**中途要人补数据的任务怎么用结构化输出？** 拆两段：第一段结构化输出"缺少哪些信息"，你的程序收集（问用户、查系统），第二段带上补充数据再跑，输出最终结构。中间的人工环节由宿主编排，agent 两头都是纯结构化任务。

**为什么开了结构化输出后 agent 还是偶尔说了一大段话？** 检查两点：schema 是否合法（非法 schema 在新版本启动即报错，但老行为是静默忽略退回自由文本，版本分界线在 2.1.205）；成功结果里字段是否存在（成功子类型不保证字段，前文的假象一）。两处都排除，再查任务是否在结果前就异常终止。

## 一次结构化任务的全程走查

把审查 agent 的一次完整运行走一遍，看每个环节的数据形态。

任务下发：任务描述加 schema（顶层三字段：问题数组、总评、建议合并的布尔值；问题元素四字段；严重级别枚举三项）。声明同时到达引擎，模型在生成最终回复时已知道要填这张表。

过程自由：agent 中间读了十二个文件、跑了两次检查工具，这些轮次完全不受 schema 影响（约束的只是最终回复）。这是机制的一个重要特性：结构化不牺牲过程灵活性。

最终回复：模型输出一段符合 schema 的 JSON。SDK 拿校验器验收：字段齐、类型对、枚举值合法。第一次就通过的话用户无感；没通过（比如它给严重级别写了"比较严重"这个枚举外的值），SDK 把错误回灌，模型重新输出，这个循环对你是隐式的，只表现为耗时多几秒。

结果落地：成功结果消息里拿到结构化字段，你的代码不做任何字符串解析，直接类型安全地访问字段。落库、驱动 CI 判定（建议合并为假则阻断）、渲染审查报告，三路消费同一份数据。

错误分支演练：模型三次都过不了校验的极端情形，结果以重试超限子类型收场，无结构化数据，你的程序走兜底（降级为自由文本审查、人工介入）。这个分支一年可能只触发几次，但必须写：没写过兜底的结构化任务是裸奔。

全程走查下来，设计要点浮出一个：schema 的质量在"最终回复"这个单点上决定成败，过程再漂亮，表填不对就全盘重来。反过来说，过程里模型读了多少文件、跑了多少工具，都不影响最终验收，这也意味着你优化 schema 的回报全部集中在最后这张表上。这就是前面把 schema 当提示词写的全部理由。

补一个容易忽视的运维事实：结构化任务的耗时里藏着校验重试的隐形成本。监控上给结构化任务单独看耗时分位（与非结构化任务对比），重试率上升（耗时分布右移、错误子类型里出现重试超限）通常意味着提示词或 schema 漂了，把它纳入提示词变更的回归项，结构化通道的稳定性就有了自己的仪表。

## 关键要点

- 选项传 JSON Schema，成功结果消息的专门字段里拿校验过的数据；schema 只认 draft-07，Zod 要显式指定目标版本。
- 校验失败自动重试，超限以专门错误子类型结束；schema 是给校验器的规则和给模型的提示的混合体。
- 两个成功假象：success 子类型不保证字段存在；增量流里的 JSON 是未校验碎片。
- 2.1.205 起 schema 不合法在启动时报错，之前是静默忽略，迁移代码注意分界。
- 枚举宁可宽不可缺，能可选的数组别必填，嵌套越浅重试越少；schema 约束形状不保证内容真伪。
