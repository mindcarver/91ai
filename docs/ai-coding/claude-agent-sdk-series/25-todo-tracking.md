# Todo 追踪：把 agent 的任务清单暴露给你的程序

> 更新日期：2026/10

**TL;DR：** agent 内部有一套任务管理工具，多步任务时它自己写清单、更新状态。SDK 没有专门的"进度事件"，但清单的每次变动都以工具调用和结果的形式出现在消息流里，你的程序解析这些消息就能重建出实时任务面板。这不是花活：长任务的进度可视化是自治 agent 产品的刚需，而这条通道是官方指定的做法。

## agent 也有自己的待办清单

先看一个现象：给 agent 一个多步任务，事件流里会混进一些奇怪的工具调用，名字是创建任务、更新任务、查任务列表之类，参数里是"分析依赖、写测试、跑测试、修失败项"这样的条目。这是 agent 在给自己写待办清单。

它为什么这么做：多步任务里，纯靠对话记忆追踪进度容易丢步骤，写下来的清单成了外化的工作状态。引擎在新一些的模型上默认提供这套任务工具（创建、获取、更新、列表四个），在另一些模型上提供更早的单个清单写入工具，两套形态按模型自动选择，也有开关强制切换。默认不给任务工具的模型，可以按需打开。

任务的生命周期：创建时是待办，开始时转为进行中（带一个进行时标签，比如"正在修复登录校验"），完成时标记完结，也能删除。agent 什么时候用清单有它自己的判断：三步以上的明显多步任务、用户点名的清单、长操作会写，简单请求会跳过。这个"不一定每次都写清单"的自由度后面要处理。

## SDK 视角：没有进度事件，但有全部原料

SDK 的消息流里没有专门的进度事件类型，这是很多想做进度界面的开发者失望的点。原料其实全在流里：清单的每次变动就是一次工具调用（模型消息里的调用块）加一次工具结果（用户消息里的结果块）。解析这两类消息，任务状态就能在宿主程序里重建。

重建的逻辑不复杂，三条规则。其一，创建类调用的结果里带新分配的任务标识，任务从此有了身份证。其二，更新类调用的参数里带标识和新状态，查表更新。其三，模型侧的调用参数是模型的原始输出，字段名有波动可能（标识字段两种拼法、标签字段两种拼法），解析要防御性读取，认字段含义不认死字段名。

一个官方文档明确提到的坑：创建时的调用日志里拿不到分配的标识（它在结果里不在调用参数里），想在创建时就记日志的话只有主题文本没有身份证，标识要等结果回来补。事件流的消息标识配对机制（调用块和结果块共享标识）在这里派上用场。

## 做一个进度面板

把重建逻辑组装成一个进度面板，这是这条通道的典型产品形态。

数据结构：一张任务表，键是任务标识，值含主题、进行时标签、状态、时间戳。三个更新入口：创建结果插入，更新调用改状态，删除调用移除。

渲染策略两层。摘要层：已完成数加总数（"5/8 完成"）加当前进行中任务的进行时标签。进行时标签比主题文本更适合展示（主题是"修复登录校验的空指针"，进行时标签是"正在修复登录校验"，后者是为展示而生的字段）。明细层：完整清单列表，状态着色，点击展开。

刷新时机：每次清单类工具调用或结果到达就重渲染一次，不需要节流（清单变动频率低）。

两个体验设计要点。其一，清单不是每次任务都有（agent 自己判断），面板要处理"无清单"状态：显示通用的轮次进度（第几轮、最近的工具活动）作为降级。其二，清单是 agent 的工作分解不是对用户的承诺，条目中途增删是常态（agent 发现新问题加一条、发现不需要删一条），面板别把清单渲染成合同，渲染成直播。

降级方案补一个：任务工具默认只在新模型上有，你的产品如果跑在没这套工具的配置上，用环境变量或工具列表显式打开；官方也提醒，只有你的应用真的消费这些调用时才值得打开（白占上下文）。

## 三个进阶用法

用法一，长任务的"它还活着"信号。无人值守任务跑四十分钟，用户问"卡了吗"。任务面板的最近变动时间就是答案：进行中条目五分钟前更新过，活着；二十分钟没动，配合链路遥测查它卡在哪（观测篇的审批等待 span 十有八九能解释）。

用法二，任务完成度的业务归因。任务面板的数据（计划了几步、实际几步完成、哪步耗时最长）和成本数据按会话关联，你能回答"哪类任务的步骤结构最复杂""失败任务通常死在第几步"。这比只看总成本细一个维度。

用法三，人工介入的锚点。审批界面里带上当前任务上下文（"agent 正在做：修复登录校验（第 4/7 步），现在要执行删除命令"），批准者从盲批变成知情批。清单数据从流里来，审批请求也从流里来，两边在宿主程序里会师。

## 与会话恢复的配合

任务状态是会话历史的一部分（那些工具调用和结果都在历史里），恢复会话后 agent 的清单延续。但你的宿主程序里的任务表是内存态，重启就没了。两个对策：从会话历史回放重建（管理接口读会话消息，过滤清单类调用重放一遍，表就回来了）；或者把任务表实时落库，重启时直接读。前者数据源单一可靠，后者实现简单，按重启频率选。

## 权衡与局限

这条通道的本质是"从工具调用流里拼状态"，不是为界面设计的推送协议。它的局限随之而来：解析依赖工具调用的形状，SDK 版本更新若调整工具行为，解析层要跟着修（防御性解析减轻但不消除）；没有清单变动的时间戳保证（只能用消息到达时间近似）；高频更新场景下它是拉模式语义（你从流里拉），做不到引擎主动推。

更根本的选择题：这套任务工具是 agent 的自我管理工具，暴露给宿主程序是官方支持的用法但不是它的第一使命。如果你的产品需要强契约的任务管理（任务列表由你的系统定义、状态由你的系统裁决），更干净的设计是自定义任务工具（把任务表放你的数据库，agent 调你的工具更新），agent 内置清单作为它的私人草稿。两套并存：系统任务是合同，agent 清单是草稿，界面分开展示。

## 进度面板的完整数据流

把面板的实现拆成一条完整数据流，四个环节。

采集环节挂在消息分发循环里。分发逻辑每收到一条消息先判类型：模型消息里筛工具调用块，命中任务类的（创建、更新、删除三种调用名）进入提取；用户消息里筛工具结果块，与前面的调用按标识配对。提取出的原子事件只有四种形状：创建请求（带主题）、创建结果（带标识）、更新请求（带标识与状态）、删除请求。每个原子事件带时间戳和消息标识，落进事件队列。

归约环节把事件流折叠成状态表。一张字典从空开始：创建结果插入新行，更新请求按标识改字段，删除请求移行。防御性读取在这一层做：字段名两种拼法的兼容、缺字段的容错、顺序错乱（结果先于调用到达的极端情况）的处理。归约是纯函数式的（同样的事件流永远折出同样的表），这让它可测试：录一段真实会话的事件流做夹具，归约逻辑的回归测试就有了。

渲染环节订阅状态表变更。摘要与明细两层各自订阅需要的字段，变更触发重渲染。一个细节：进行时标签是渲染的黄金字段，但更新调用不一定每次都带它，表里要存"最近一次出现的标签"而不是"最新请求里的标签"。

持久环节决定重启行为。两条路线前面讲过（回放重建或实时落库），补一个混合做法：实时落库但定期用回放校验（两者不一致以回放为准，落库的偏差暴露序列化或覆盖问题）。任务数据在产品里属于"错了会让用户困惑但不至于事故"的等级，校验成本不用拉满。

四个环节里最值得投入测试的是归约：它是唯一有逻辑复杂度的环节，其余三个是管道。归约测好了，面板的行为就稳了。

## 清单数据使用的疑问

**agent 不写清单怎么办？** 两种情况分别处理。模型配置不支持任务工具：按本文的打开方式显式启用。agent 自己判断不需要（简单任务）：这不是故障，降级到轮次进度展示。强制它每次都写清单可以用系统提示或技能下指令，但简单任务被逼着写清单是负体验，一般不建议。

**任务条目和我的业务任务是一回事吗？** 不是。agent 清单是它的工作分解，粒度和命名随它的理解波动。业务任务体系（工单、需求）由你的系统管理，两套用会话标识关联展示，别试图让 agent 的清单直接当业务任务库用，字段语义都对不上。

**能在任务列表上做告警吗？** 可以但间接：某个条目进行中超半小时是常见的卡任务号。实现是状态表加时间监控，注意区分"真卡住"和"子任务本来就长"，配合链路遥测的审批等待和工具执行 span 判断，比纯时间阈值准。

**删除的任务还要展示吗？** 看产品语义。agent 删除条目可能是"做完了合并进别的条目"也可能是"发现不需要"，语义它不说明。展示上软删除（置灰保留）比硬删除信息量大，回放归约时保留删除事件也更容易。

**多会话并行的任务面板怎么做？** 按会话分页面板，全局视图聚合所有活跃会话的摘要层。别做全局单表：不同会话的任务标识空间不保证全局唯一，聚合表用 会话标识加任务标识 的复合键。

## 从清单到交付：进度与结果的闭环

任务面板做到能看之后，下一步是让进度数据参与业务闭环。三个衔接点。

衔接点一，进度驱动的超时策略。不同任务的"合理耗时"不同，静态超时阈值要么误杀快任务要么放过慢事故。用清单做相对判断：条目在推进（有状态更新）说明健康，全部静止超过阈值才告警。一个十二步任务第九步停了一小时可能正常（那步本来就重），一个三步任务第一步停了一小时几乎必然出事。清单给了超时判断一个"任务结构感知"的锚。

衔接点二，完成质量的旁证。任务正常结束时清单的状态分布是个轻量的质量信号：全部完结是圆满；留下半数未完结就出了结果，要么是清单过时（agent 忘了更新）要么是它绕过了计划（跳步交付）。两种都值得抽查。把这个信号接进质量看板，成本零，收获一个行为侧的观测维度。

衔接点三，交付物的引导。清单条目天然映射产出物：条目"写测试"对应测试文件、"写报告"对应报告路径。在会话结束前发一条收尾指令（对照清单逐项确认产出物路径并补齐遗漏），把 agent 的自查和清单对齐。清单从进度展示升级成了交付验收单，这是这套数据能产生的最大业务价值。

三个衔接点的共同逻辑：清单是 agent 侧唯一的结构化自我描述，凡是需要"任务此刻处于什么状态"的下游功能，它都是最便宜的数据源。

## 事件形状速查

归约逻辑要认的原子事件，形状速查备查。

创建请求：主体是任务主题文本，可能带优先级类附属字段；此刻没有标识。创建结果：带新分配的任务标识，这是它进表的钥匙。更新请求：带标识、新状态、可选的进行时标签；状态枚举三种（待办、进行中、完结）加删除。查询类调用：不改状态，渲染面板时可忽略（agent 有时自查清单，别误当用户动作）。

防御性读取的三个要点再压一遍：标识字段认两种拼法（存在即取）；标签字段同样两拼法；一切字段都可能缺席，缺席按"不变"处理而不是报错。归约函数写成一个纯函数（事件列表进、状态表出），配真实会话录制的夹具测试，这块逻辑就再不需要人盯。

夹具的挑选也讲究覆盖：至少录三段真实会话，一段写了完整清单且多次增删条目的，一段简单任务压根没写清单的，一段中途恢复会话后清单延续的。归约的分支（插入、更新、删除、乱序）在三类样本里都有实拍数据，比手造事件可靠。夹具录好之后进版本库，引擎升级时它们就是现成的回归基准。

最后记一条升级纪律：任务工具的行为（字段名、默认开关）随引擎版本演进过多次，SDK 升级后第一件事跑一遍归约测试夹具，字段漂移当场暴露。解析层的测试是这套通道唯一的版本保险，比记住任何具体字段名都可靠。

## 关键要点

- agent 内置任务管理工具写外化清单；新模型默认有，其他模型可显式打开；是否写清单由 agent 按任务复杂度自行判断。
- SDK 无进度事件，原料在工具调用流里：创建结果给标识、更新调用改状态；字段名有波动，防御性解析。
- 面板三件：摘要层用进行时标签、明细层渲染成直播、无清单时降级到轮次进度。
- 进阶三用：活着信号、步骤归因、知情审批；任务态随会话恢复，宿主侧靠回放或落库重建。
- 强契约任务管理用自定义工具建自己的表；内置清单是 agent 的草稿，别当合同。
