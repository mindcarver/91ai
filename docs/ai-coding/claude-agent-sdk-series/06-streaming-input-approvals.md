# 流式输入与人工介入：把审批接进你的程序

> 更新日期：2026/10

**TL;DR：** 无人值守的 agent 迟早撞上"需要有人点头"的时刻。SDK 给了两条介入通道：流式输入让你随时发消息、排队、打断；审批回调让工具调用在执行前停在你的代码里，由你放行、拒绝或改参数。引擎还会通过 AskUserQuestion 工具主动向你提问。三条通道语义不同，混用是事故的主要来源，这篇把每条的触发条件、回答格式和语言差异讲清。

## 会话为什么停住了

先看一个现象。你起了个 agent 让它清理日志文件，日志滚动到一半卡住不动。debug 日志里能看到引擎在等一次工具批准：agent 想执行删除命令，权限模式判定这个调用需要批准，而没有人回答。CLI 里这个时刻弹的是终端确认框，SDK 里它变成一个停在半空的等待，可以无限期等下去。

这个现象定义了本文的问题域：agent 的行为边界上有一类时刻，引擎需要外部输入才能继续。这类时刻有三条入口，分别是你主动说话（流式输入）、引擎请你裁决（审批回调）、引擎向你提问（AskUserQuestion）。三条入口的方向和时机都不同，逐个讲。

## 流式输入：随时开口的能力

单发模式把任务当一个包裹扔过去，会话没有开口的机制。流式输入模式反过来：你传给 SDK 的不是一个字符串而是一个消息来源，会话活着期间它可以持续产出消息。这带来四种动作。

发后续指令。agent 在跑一个长任务，你观察到方向偏了，直接发"跳过测试覆盖那部分，先只改类型错误"。消息排队按序处理，不打断当前轮，下一轮生效。

打断。方向不只是偏而是错，就要打断当前这一轮。打断的语义要精确理解：当前工具调用会被终止，会话本身保持存活，已完成的修改不会自动回滚（回滚是检查点的职责）。打断后你可以发新指令重定向。

补充上下文。agent 不知道的信息（刚才线上又复现了一次、这个客户是 VIP），不用等它问，随时塞进去。

传图。图片输入只支持流式模式，这是两条模式最硬的能力差异。截图、设计稿、报错照片，都以消息内容的形式进入对话。

流式输入的代价是你要为一个消息来源的生命周期负责。TS 里你的输入生成器抛异常，跨进程后被翻译成"用户中止"（引擎视角它只看到输入断了）；Python 里更隐蔽，异常只记进 debug 日志，会话表面健康地停住。所以流式代码的第一守则：生成器内部的异常自己接住、自己记日志、按需发一条"出错了"的消息，不要让异常逃出生成器。

Python 还有一个模式节奏要记：客户端对象上，一条消息配一对发送与接收调用，接收循环在第一条结果消息处停。想要多轮，就循环这对调用。把它当成请求响应的节拍器，而不是一条长河。

## 审批回调：引擎请你裁决

第二条通道解决开头的现象。传一个审批回调（TS 叫 canUseTool，Python 叫 can_use_tool），需要批准的工具调用就不再无限期挂起，而是停在回调里等你的函数返回。

触发规则是理解这条通道的关键，三条。第一，回调只在"权限判定走到需要批准"这一步触发：白名单放行的调用、权限模式自动放行的调用不会经过它。想对每一次工具调用都做逻辑（比如全量审计），用 PreToolUse 钩子，它在权限判定之前跑。第二，dontAsk 模式下回调不会被调用，这个模式的设计意图就是"别问任何人"。第三，回调可以长时间不返回，引擎耐心等，这既给了你接 Slack 审批流的时间，也意味着忘了返回就是挂起，超时机制要建在你自己的代码里。

回答有三种形态，各自带工程含义。

放行，可选择改参数。回调拿到的是工具名和输入参数，放行时可以返回修改过的参数。典型用途是参数消毒：agent 想删一个目录，你把路径收窄到工作目录内再放行。这个能力是审批回调超越"是或否"的地方，你的程序在这一刻拥有了编辑 agent 意图的能力。

拒绝，必须带一句话。被拒的工具不会执行，你的话会作为拒绝原因回给模型，它通常会换一条路。写拒绝信息时把它当成给模型的提示词写："禁止删除 .env 开头的文件，改用归档目录"比"拒绝"两个字有效十倍。

放行并写入记忆。回调参数里会带一组现成的权限规则建议（就是 CLI 里"总是允许"按钮背后那条规则），你把选中的规则通过返回值写回，它会落到本地设置文件里，之后同类调用直接免批。这适合"这次批准代表以后都批准"的稳定规则；对一次性的裁决就不要写规则。

还有一个部署层面的细节：如果你的进程可能在用户回复前退出（比如无状态 worker），别在回调里阻塞等待，改用 PreToolUse 钩子的延迟决定，让等待跨进程存活。

## AskUserQuestion：引擎主动问你的界面

第三条通道方向反过来：不是工具要批准，而是 agent 在任务里需要人做选择，它调用一个叫 AskUserQuestion 的内置工具。你的审批回调会收到这次调用，参数里是结构化的问题：每个问题有标题（限十二个字符）、二到四个选项（各有标签和说明）、是否多选，一次调用最多四个问题。

回答它要把答案塞回工具参数里原样传回：问题列表照抄，附上答案映射（问题文本到选中标签）。用户选了自定义输入（Other），就把用户的原话作为该题的值。还有一个自由回复字段，用了它就整体替代答案列表。多选答案是标签数组。

三个坑。给了它问题就要有回答路径：如果你的工具列表是显式传的，忘了把 AskUserQuestion 放进去，agent 想问也问不了。子代理里这个工具不可用，委派出去的任务要设计成不需要中途提问。TS 侧可以给问题选项配预览内容（markdown 或 html 渲染），做产品界面时这个字段能把选择题升级成对比视图，Python 侧没有这个能力。

把 AskUserQuestion 和审批回调放在同一个处理函数里是常见架构：两者共用一个入口，按工具名分流。审批类走裁决逻辑，提问类走你的 UI。你的产品从此拥有一个会主动提问的 agent，交互的方向从单向指令变成了双向协商。

## 通知与外联

审批等待期间想通知人类（Slack、邮件、推送），用 PermissionRequest 钩子，它在等待发生时触发，适合接通知系统。这个钩子和审批回调的分工：钩子负责"告诉人"，回调负责"接收人的决定"。两者加上 PreToolUse 构成完整的审批链路：事前拦截、事中通知、事后裁决。

## 两个语言各自的暗坑

TS 侧历史遗留少，主要是回调里的 AbortSignal 用法：请求可取消，取消的语义要你自己定义（通常映射成拒绝）。Python 侧有一个官方点名的必备操作：配一个空的 PreToolUse 钩子保持流不关闭，否则审批回调在某些版本下行为不稳；另外 Python 版本要在 0.1.80 以上才有完整的建议回写能力。TS 侧还有一个版本门槛：v2.1.207 之前，放行时漏传原参数会触发校验错误，老版本用户要在放行响应里显式回传参数。

这些坑的共同点是它们都在"你的代码和引擎的握手处"。介入机制做的事，就是把你的程序嫁接进引擎的决策循环，嫁接点两边的版本和语义必须对齐。

## 权衡与局限

介入机制给了你完整的控制权，但每个介入点都是延迟点。一次外呼审批（人不在座位上）就是几十分钟的挂起，预算和轮数上限在这种挂起里不消耗，但你的业务超时要自己管。工程上的平衡做法：把介入分两级，机器可裁决的（路径消毒、规则匹配）全自动，必须人裁决的走异步通知加超时默认拒绝，默认值偏向安全侧。永远不要设计一个"等人一下午"的同步链路。

介入也改变 agent 的行为模式：被频繁打断的 agent 会学会问得更少、做得更保守，这是提示词层面要配合调整的。控制权的代价是你要为每个"谁决定"的边界写清楚规则。

## 审批链路的产品化设计

介入机制用对的前提是把整条审批链当产品设计。一条成熟的链路长这样。

第一层，机器预审：钩子处理所有可规则化的判断（路径消毒、清单匹配、参数修正）。这一层消化九成请求，延迟毫秒级，用户无感。

第二层，异步人审：预审不过的进人工队列，通知走权限等待钩子（Slack、邮件、推送），审批界面带足上下文（任务说明、本次会话已做什么、这个工具调用想干什么、参数预览）。审批的等待期设超时，默认拒绝偏安全侧，超时事件记审计。

第三层，决策回流：批准或拒绝回到回调，同时按需沉淀规则（这次批准的这类操作写进允许规则，下次预审放行）。规则沉淀让审批量随时间递减，这是审批系统的健康曲线：上线第一个月审批多，三个月后只剩真正的长尾。

第四层，兜底：回调进程可能死掉（worker 重启），等待中的请求要有超时和重派机制；全链路的审批耗时进指标，审批慢是产品问题不是用户问题。

四层里最值钱的设计原则：让 agent 的等待变成异步事件，而不是同步阻塞。用户睡觉时 agent 等审批等到天亮不可怕（预算没消耗），可怕的是你的产品把这种等待渲染成"卡死了"。等待状态的透明化（界面写明"agent 正在等待人工批准某操作，已通知值班"）直接决定用户体验的好坏。

## 介入通道的运转疑问

**打断之后 agent 会把做了一半的工作收尾吗？** 不会自动收尾，打断就是硬停。已完成的文件改动留在盘上（回滚靠检查点），任务状态靠你的程序记录（做到哪一步、还剩什么）。打断后重发的指令最好带上"刚才做到哪"的衔接说明，agent 从断点继续比重新理解一遍便宜。

**审批回调能同时收到多个请求吗？** 能，agent 并发调用多个工具时可能多个都等审批。回调要支持并发（每请求独立处理），界面上排队展示。别在回调里串行化处理（一个处理完才看下一个），等待时间翻倍。

**用户拒绝之后 agent 一直换花样重试同一个操作怎么办？** 拒绝消息要写成边界说明而不是情绪表达："禁止删除 .env 文件，这不是本任务需要的操作，请继续配置检查"。仍然缠打的话加一条拒绝规则（权限层硬拦），或在提示词层面收敛任务范围。拒绝的原因写得好，多数时候模型一次就转向。

**图片输入在产品里怎么用最值钱？** 两类高频：用户拍屏问报错（客服场景），监控图表异常解读（运维场景）。都走流式输入模式。注意图片进上下文后常驻（缓存能缓解），高图频的产品要评估视觉 token 的成本占比。

**Python 的空钩子变通具体是什么？** 官方文档点名的必备操作：配一个什么都不做的调用前钩子，保持流不提前关闭，审批回调才能稳定工作。这是版本相关的过渡方案，升级 SDK 时核对它是否仍需要（看官方文档的对应条目），别让它变成没人记得为什么存在的祖传代码。

## 一次介入密集的会话时序

把三条通道放进同一条时间线，看它们如何交错：

```
用户: "清理构建产物"          [你的程序]
  │
  ├─ 模型: 调用删除命令 ──► 权限链走到批准 ──► 审批回调
  │       (你的程序自动校验路径范围, 放行)
  ├─ 模型: 调用提问工具 ──► 同一回调 ──► 你的界面渲染选择题
  │       (用户选"只清一周以上的")          ◄─ 用户输入
  ├─ 你的程序: 流式输入发补充 "临时目录是 /tmp/build"
  │       (排队, 下一轮生效)
  ├─ 模型: 继续执行...
  └─ 结果消息收尾
```

时间线上三处值得标注。删除命令走的是回调的裁决分支（第六道门），提问工具走的是提问分支（渲染界面），补充信息走的是输入通道（不经回调）。三条通道在一次任务里各出场一次，方向不同、格式不同、生效时机不同：裁决即时、提问等用户、输入排队到下一轮。

这张图也是回调实现的架构提示：一个回调函数同时服务两种调用（裁决与提问），按工具名分流后进入完全不同的处理管线，别让它们共享状态（一次提问的选择不该污染下一次裁决的判断）。

## 关键要点

- 三条介入通道：流式输入（你主动）、审批回调（引擎请你裁决）、AskUserQuestion（引擎向你提问），方向与时机各不相同。
- 审批回调只覆盖走到批准步骤的调用；全量审计用 PreToolUse；dontAsk 模式下回调静默。
- 回调三种回答：放行可改参数（消毒能力）、拒绝必带原因（给模型的提示词）、放行可写规则（持久免批）。
- 图片输入、打断、排队只在流式模式；生成器异常要自己接住，逃出去会变成"用户中止"或静默卡死。
- 审批链三件套：PreToolUse 事前、PermissionRequest 通知、审批回调裁决；等待可无限期，超时责任在你的代码。
