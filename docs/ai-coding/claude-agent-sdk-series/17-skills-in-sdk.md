# Skills 在 SDK 里：给产品化 agent 装上可插拔的专长

> 更新日期：2026/10

**TL;DR：** Skill 是一个目录加一个 SKILL.md 的可插拔能力包：启动时只加载一行描述，被调用时正文才进上下文。SDK 会话经由配置来源发现它们，用 skills 选项控制启用面。它是"把领域知识打包复用"的标准载体，但有两条硬边界：只能以文件形态存在没有编程注册接口，发现完全依赖文件系统布局。这篇讲清发现机制、控制选项、给 SDK agent 写技能的要点和验证方法。

## Skill 在 SDK 语境下的定位

先重申继承篇的结论再往下走：SDK 会话对 Skills 的支持是原生继承的，会话里自动有调用技能的工具，发现的技能默认全部可用。也就是说"用不用 Skills"不是接入问题，是治理问题：默认全开的发现面可能不是你的产品想要的。

Skill 解决的问题值得再精确一次。系统提示里塞进所有领域知识，上下文成本固定且高昂；Skill 把知识切成惰性块，agent 遇到匹配任务时才取用。五十个技能的 agent，启动成本只相当于五十行目录，这在 SDK 的长会话场景里经济性更明显：会话越长，省下的固定成本越多。

贯穿案例：给一个运维 agent 配三个技能（事故响应流程、发布检查清单、值班交接规范），每个是一份结构化文档加步骤。agent 收到"线上 5xx 涨了"的任务，识别到匹配事故响应技能，调取正文，按步骤执行。

## 发现：一切取决于文件在哪

技能的发现规则是纯文件系统的：配置来源启用时，用户目录和当前工作目录及向上的父目录（到仓库根）里的技能目录都被扫描。追加目录选项也能扩大项目发现范围。

三条推论直接从规则导出。其一，配置来源显式设置了列表却不含项目或用户来源，技能一个都不会加载，"目录里明明有"和"会话里看不到"的矛盾十有八九在这里。其二，工作目录的位置决定了能发现哪些技能，目录布局本身就是配置：把技能放在仓库根，仓库里任何位置起会话都能发现；放在深层子目录，只有从那以下起会话才看得到。其三，多租户部署里技能发现跟着每租户的工作目录走，配合每租户的配置目录环境变量，技能面天然按租户隔离。

验证发现的手段是初始化系统消息里的技能数组，启动后立刻核对它和你预期的差异，比事后从行为倒推快得多。这个数组只列用户可调用的技能，标了不可调用的技能不出现在这里但 agent 能用，两个口径别混。

## 控制：skills 选项的四个档位

省略：全部发现的技能可用，等于 CLI 行为，个人工具的默认。

全部：显式声明全开，和省略效果相同但意图明确，代码可读性更好。

名单：只启用列出的名字。名单有输入校验：空串、括号逗号、通配符都会被当场拒绝（抛错而不是静默忽略），这是少见的严格校验选项，写错了立刻知道。名单外的技能对模型不可见，调用工具会拒，但注意文件本身仍可被读文件工具读到：技能的"不可见"是调用层不可见，不是文件层不可访问，机密内容别指望靠技能名单保密。

空数组：全禁，会话完全没有技能能力。

配套陷阱第三次出现（前两次是继承篇和工具篇）：设置 skills 选项会自动把调用技能的工具加进允许列表，但你显式传了工具列表时它不会自动出现，自己加。这个陷阱在三个选项上重复出现（技能、子代理、提问），可以总结成一条通用规则：**显式工具列表是全量声明，一切依赖都要自己列**。

## 用户直发：斜杠语法

任务文本里写斜杠加技能名，就是直接指定执行那个技能，不经模型判断。这个语法在 SDK 里同样有效，且有个宽松的语义边界：它不受 skills 名单限制（名单管的是模型自主调用，直发是用户意志），未知名字也不报错，整段文本当作普通提示词发给模型。

这两个语义组合出实用模式：产品界面上的"执行发布检查"按钮，实现就是发一条直发消息，确定性触发技能，绕过模型的选择不确定性。名单收紧自主调用的口子，直发保留产品控制的通道，互不挡道。

## 给 SDK agent 写技能的要点

技能的正文是 markdown 加前置元数据，描述字段决定模型什么时候想到它，写作标准和子代理的描述一样按"任务画像"写。SDK 场景有三个特别要点。

其一，技能是流程与知识的载体，不是代码的载体。发布检查清单、事故响应步骤、领域术语表，这些是技能的本职；需要执行逻辑的部分做成工具，技能指导何时用哪个工具。技能和工具的配合模式：技能教方法，工具给能力。

其二，为无人值守环境补上下文。CLI 里的技能可以假设用户在场补话，SDK 会话里的技能要自足：步骤写到不需要人确认也能走的程度，遇到必须人决策的点显式写"停下等待输入"而不是含糊带过。

其三，版本化。技能是文件，天然可以进 git、做评审、走发布流程。把团队技能库当一个小产品维护：谁改的、为什么改、什么时候生效，全在版本历史里。这比"系统提示里的那段规则是哪个版本加的"可追溯得多，也是很多团队把产品规则从系统提示迁到技能库的原因。

## 与其他扩展点的分工

四个扩展点摆在一起看分工。系统提示：全局人格与规则，常驻上下文，改它是产品级变更。技能：流程与知识包，按需加载，文件形态可复用可分发。自定义工具：代码能力，函数形态，你的系统能力出口。子代理：带独立上下文的角色，重任务的隔离与并行。

一个能力该落在哪，问两个问题：它是知识还是代码？知识进技能，代码进工具。它需要独立上下文吗？需要就上子代理，不需要技能或工具就够。四件套各司其职，SDK 的扩展体系就完整了。

## 权衡与局限

技能的最大局限是它锁死在文件形态：没有编程注册接口，运行时动态生成的"技能"做不到（动态内容走自定义工具），部署时要把技能目录分发到每个工作节点（容器镜像或挂载）。这条限制的另一面是简单可靠：文件即技能，没有注册中心、没有依赖解析、没有运行时冲突，复制目录就是安装。

技能的可信边界也要想清楚：它本质是注入给模型的指令。谁能在技能目录里放文件，谁就能影响 agent 行为。多租户场景技能目录的写权限要和应用代码同级管控，仓库根的技能目录变更走代码评审，当成提示词注入面管理。

## 一个技能的完整解剖

把贯穿案例的事故响应技能拆开看，每个部分的写法都有讲究。

前置元数据两个必填字段：名字（目录名即名字，用短横线连英文小写，别用中文和空格，调用和直发都要打这个名字）和描述（决定模型什么时候想到它）。描述的写法模板是"当出现什么情况时，用这个技能做什么"：当用户报告线上服务异常（错误率上涨、响应变慢、功能不可用）时，用这个技能按标准流程组织响应。把触发信号写具体（错误率上涨比服务出问题可匹配性强得多），把能力边界写清楚（组织响应，不是直接修 bug）。

正文的开头一段是重头戏：模型决定调用技能后，第一眼读的就是它。这一段要把技能的核心流程浓缩成可执行的路线图，先确认影响面，再定位，再决策止血还是修复，再通报。路线图之后是分节展开：每步做什么、判断标准是什么、哪些情况要停下问人。

步骤的写法有个隐性标准：写到"新的执行者照着能做"的程度。反面例子是"评估影响范围"（怎么评估？看什么？），正面例子是"评估影响面：查监控面板的 5xx 比率和 P99 延迟，和过去七天基线对比，涨幅超过两倍即标记为受影响服务，列出受影响的服务清单供后续步骤使用"。多写的两句话换来的是执行质量的方差缩小。

"停下问人"的标注在 SDK 场景格外重要：无人值守会话里，agent 遇到需要决策的点，技能里写了"到此暂停并上报等待指示"，它才会真的停；没写，它倾向自己猜着往下走。把所有的决策点显式标出来，是给自治 agent 上缰绳。

配套文件的放置：面板地址、联系人表这类引用数据放技能目录里当附件，正文里写相对路径引用。附件改动不影响技能逻辑，比写死在正文里好维护。

## 技能选用与生效的疑问

**技能和子代理都装"专家知识"，怎么选？** 需要独立上下文和专属工具集就上子代理（重调研，读一百个文件别污染主上下文），只需要流程和知识就上技能（轻、快、可直发）。一个常见组合：子代理当人，技能当它的工作手册，子代理的定义里预载对应技能。

**改了技能文件，进行中的会话生效吗？** 元数据在启动时读，正文在调用时读。改正文，下次调用就用新版；改描述或增删技能文件，要新会话才发现列表变化。发布流程上把"改描述"当成需要滚动重启的变更。

**怎么验证一个技能被正确加载和调用？** 加载看初始化消息的技能数组。调用看消息流里的技能工具调用块。想做技能级的命中率统计（哪些技能从没被调过），从事件流里统计调用即可，零成本的技能审计。

**技能正文里能放代码吗？** 能（markdown 里什么都放得了），但代码的正确用法是"给 agent 看的参考实现"，不是"会被执行的程序"。要执行逻辑就注册成工具，技能指导何时用工具。把大段可执行代码放技能里，agent 会试图理解并改写它，上下文成本高且易错。

**直发语法和技能名单的关系再确认一遍？** 名单管模型自主调用；直发不受名单限制，未知名不当错当普通文本。产品里正确的搭配：名单收紧（只放业务必需的技能），常用操作走产品按钮直发，两个口子都可控。

## 技能库的组织结构

技能上量之后，目录怎么摆、怎么命名、怎么防退化，一套参考结构。

目录按领域分桶：技能目录下先分领域子目录（运维、审查、文档），每个技能在领域内一个目录。发现机制扫的是整棵树，领域层纯粹为人和工具服务（浏览、统计、批量操作），但这一层让技能库从"一百个平铺目录"变成可维护的结构。

命名三段式：领域加动词加对象（运维-响应-事故，审查-核对-发布清单）。调用名和直发语法用的是技能名（目录名或元数据名），保持它短而稳定；描述里再用完整句子展开。中文团队常见纠结是技能名用中文还是英文：名字走英文小写短横线（调用兼容性最好），描述和正文随便中文，两层各取所长。

防退化的三件小事：每季度清点调用率（事件流统计，零调用的技能进待删除评审，是删除还是描述写得差到检索不到，各占一半）；技能变更走 PR 评审（它是指令注入面，评审标准对齐代码而非文档）；版本记录写在正文末尾（一段变更史，纯给人看）。

这三件事指向同一个方向：把技能库当内容资产去运营（有结构、有命名规范、有生命周期管理），而不是当一堆文件夹放着。堆放式技能库一年的典型归宿是两百个技能、没人敢删、没人知道哪些在用。

## 技能管理的进一步追问

**技能能带自己的工具授权吗？** 技能元数据里的工具授权字段是预授权语义（写进去的工具调用免批），配合会话的允许规则一起生效。高危工具别在技能里预授权，让审批链兜着。

**同一个技能在不同项目目录里要有不同版本怎么办？** 项目级技能目录本来就按项目隔离（发现机制按目录链走），同名的项目技能在各自项目里生效，这正是目录布局承担的版本职责。跨项目要统一版本时，把技能放进插件（打包篇的正题）。

**技能和输出风格有关的部分放哪？** 输出格式要求写进技能正文（本技能的产出按什么格式给）。但它只在技能被调用时生效，全程统一的输出风格归系统提示（追加文本的第六段骨架里有它的位置）。判断标准还是那句话：全程的归提示，做某类任务时的归技能。

**技能目录究竟能放在哪些位置？** 配置来源启用时，扫描范围覆盖用户目录、当前工作目录及其向上的父目录（到仓库根），追加目录选项还能再挂额外路径。想扩大项目内的发现范围就靠目录链和追加项，想完全关掉某个来源就动配置来源列表，位置本身就是开关。

**技能能引用别的技能吗？** 正文里可以提到"完成后按发布核对技能走一遍"，模型会接着调用那个技能。这是技能间的软链接（靠模型遵守，不是强制的调用图），用于流程接力足够可靠；强制的流程约束别指望它，那是你宿主程序的编排职责。软链接的好处是技能库能自然长出流程网络，坏处是删除被引用的技能会留死链，清点时把引用关系一并查。

## 关键要点

- 发现纯文件系统：配置来源含项目或用户才加载，工作目录位置决定发现范围，验证看初始化消息的技能数组。
- 四档控制：省略全开、全部显式、名单严校验、空数组全禁；名单管调用不管文件读取，机密别靠它。
- 直发语法不受名单限制、未知名字不当错处理：产品按钮的确定性触发通道。
- 写作三要点：流程知识而非代码、为无人值守补足自足性、进版本库当产品维护。
- 四件套分工：提示管人格、技能管知识、工具管能力、子代理管隔离；技能目录当注入面管控。
